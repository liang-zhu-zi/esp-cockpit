# ESP-Cockpit 组件需求与初步设计

> 状态：需求整理稿，供设计讨论使用。本文不代表已实现的功能，也不视为最终接口定义。

## 1. 项目概述

ESP-Cockpit 是一个通用的 ESP-IDF 组件，用于帮助基于乐鑫芯片的设备快速构建 Web Portal。组件面向 ESP-IDF v6.1，支持范围限定为本文列出的原生 Wi-Fi 和/或集成 Ethernet MAC 目标芯片；暂不支持通过 SPI 等接口接入的外部以太网控制器。

组件应以独立、可配置、易扩展为目标。设备应用负责业务逻辑和硬件控制，ESP-Cockpit 提供 Web 前后端基础设施及二者之间的通用交互机制。

### 1.1 硬件与目标芯片支持

#### 1.1.1 支持原则与网络接口范围

- 组件面向 ESP-IDF v6.1；仅支持本节明确列入清单、且经确认属于 ESP-IDF v6.1 有效 target 的芯片。未来新增芯片不自动纳入，须经兼容性验证后更新清单。
- 当前支持的**原生以太网 MAC**：ESP32-S31、ESP32、ESP32-P4；允许这些芯片的集成 Ethernet MAC 通过 RMII/MII 连接外部 PHY。
- 当前支持的**原生 Wi-Fi 接口**：ESP32-S31、ESP32-S3、ESP32-S2、ESP32-C6、ESP32-C61、ESP32-C5、ESP32-C3、ESP32-C2、ESP32。
- **暂不支持外部以太网控制器**，例如通过 SPI 接入的 Ethernet 控制器。应用负责具体板级 MAC/PHY 接线、PHY 型号配置及相应 ESP-IDF 驱动集成；组件支持范围仍限于上述芯片集成的 Ethernet MAC，不因此扩展到任意外部网络控制器。
- ESP32-P4 通过外部协处理器获得的远程 Wi-Fi 不属于上述原生 Wi-Fi 支持范围；若需要，须作为单独的应用集成需求讨论。
- 用户已手动确认 ESP32-S31 受 ESP-IDF v6.1 支持，项目目标映射为 `esp32s31`。所引用的 [ESP-IDF release/v6.1 COMPATIBILITY.md](https://github.com/espressif/esp-idf/blob/release/v6.1/COMPATIBILITY.md) 主要描述 SoC 修订版与 ESP-IDF 版本兼容关系，不是完整 `IDF_TARGET` 清单，因此该文件没有 S31 条目不构成不支持的证据。

#### 1.1.2 支持等级与验收标准

组件的核心功能范围限定为：提供基础 WebUI、混合通信架构（JSON-RPC over HTTP/WebSocket、可选 SSE、原生 HTTP 流）及基础安全防护，为应用注册和扩展设备功能提供通用入口。Wi-Fi Manager、协议转换、设备参数和业务控制属于可选模块或应用扩展，不因此自动成为所有目标上的验收项。

| 芯片 | IDF Target | 当前支持的原生接口 | 验收等级 |
|---|---|---|---|
| ESP32-S31 | `esp32s31` | Wi-Fi、以太网 | ESP-IDF v6.1 支持已确认；核心功能验证 + 5+5 并发连接验证 |
| ESP32 | `esp32` | Wi-Fi、以太网 | 核心功能验证 |
| ESP32-P4 | `esp32p4` | 以太网 | 构建兼容 + 5 HTTP + 5 WebSocket 并发验证 |
| ESP32-S3 | `esp32s3` | Wi-Fi | 构建兼容 + 5 HTTP + 5 WebSocket 并发验证 |
| ESP32-S2 | `esp32s2` | Wi-Fi | 构建兼容；2 客户端并发为设计目标，暂不要求实机验收 |
| ESP32-C6 | `esp32c6` | Wi-Fi | 核心功能验证 |
| ESP32-C61 | `esp32c61` | Wi-Fi | 构建兼容；2 客户端并发为设计目标，暂不要求实机验收 |
| ESP32-C5 | `esp32c5` | Wi-Fi | 核心功能验证 |
| ESP32-C3 | `esp32c3` | Wi-Fi | 构建兼容；2 客户端并发为设计目标，暂不要求实机验收 |
| ESP32-C2 | `esp32c2` | Wi-Fi | 构建兼容；2 客户端并发为设计目标，暂不要求实机验收 |

**核心功能验证**要求必须构建，并在对应开发板/网络接口上验证基础 WebUI、按配置启用的 HTTP JSON-RPC/WebSocket/文件流、应用扩展接入及最低安全防护。安全验收范围和具体测试用例仍需定义。

**并发连接验证**要求满足下述连接数，并在对应板卡上验证并发连接场景；它本身不表示完成完整 WebUI 功能、安全和性能验证。与核心功能验证等级重叠时，两类验收要求都适用。

**构建兼容**要求能使用 ESP-IDF v6.1 为该 target 完成组件构建；不承诺该等级已完成完整运行时、功能、安全或性能验证。对仅要求构建兼容的目标，至少 2 个客户端是设计目标，不作为当前已验证的验收承诺；除非未来用户反馈相关问题，否则不安排该并发目标的实机验收。

#### 1.1.3 并发连接要求

- ESP32-S31、ESP32-S3、ESP32-P4：支持至少 **5 个同时进行的短 HTTP 请求**，并同时支持 **5 个持续 WebSocket 客户端**。WebSocket 是默认并发验收基线；若产品启用且要求验收 SSE，再单独增加 SSE 场景。
- 其他已列入清单的芯片：**2 个并发客户端是设计目标**；当前验收只要求构建兼容，不安排该并发目标的实机验收。只有未来用户反馈相关问题时，才重新评估是否进行实机验证。该并发能力并非已经通过验证的性能承诺。
- 5+5 并发验收应覆盖认证、请求/通知处理和资源限制，并确认资源不足时能有序拒绝或断连，不发生崩溃。HTTP 并发定义为同时处理的短请求数，不是 5 个长期占用的 HTTP keep-alive 连接。

#### 5+5 并发测试建议基线

- **突发并发场景**：5 个客户端同步发起短 HTTP 请求，验证服务端同时处理 5 个请求；此项用于验证并发处理能力，不能仅以持续平均 RPS 替代。
- **HTTP 持续负载场景**：建议 5 个客户端各以约 1 request/second 发起只读、可重复的短请求（总计约 5 RPS），持续 30 分钟。突发并发验证应独立于该持续负载测试。
- **长连接基线**：以 5 个 WebSocket 客户端持续连接 30 分钟作为本项目默认并发验收方式；可建议每个客户端以约 1 notification/second 接收测试通知。只有产品明确启用 SSE 并需要验收时，才另加 SSE 测试，不以 SSE 替代默认 WebSocket 基线。
- **安全配置条件**：管理面默认使用 HTTPS/WSS，验证 TLS 下的身份认证、授权、来源校验和证书身份；出站 TLS 客户端应验证服务器证书链及主机名。并发与资源验收必须记录 TLS 配置。受限的明文 HTTP 仅可用于物理触发或限时开放的首次配网引导，不得静默降级承载常规管理接口。
- **结果记录**：至少记录成功率、延迟分布、连接断开/重连情况、空闲与峰值 RAM、测试前后资源变化，以及是否发生崩溃、断言、持续内存增长或非预期断连。暂不预设 p95/p99 延迟门槛，应先在核心验证板测量基线后再决定。
- 上述速率、持续时间及通知频率作为建议的可重复测试基线，最终压测参数仍需确认。并发目标不等于底层 socket 数，测试报告应记录 target、板卡、IDF 版本、网络接口、PSRAM 配置、TLS 配置、请求类型及通知频率。

## 2. 系统架构

### 2.1 架构原则

- 采用前后端分离架构。
- Web 前端以静态资源形式部署，可使用 Vue、React、Svelte 或原生 HTML/CSS/JavaScript 开发。
- 组件提供随组件编译并链接进固件的默认前端资源，作为基础回退内容。
- 应用可将自定义默认前端资源随应用编译并链接进固件；若应用提供该资源，构建产物使用应用资源替换组件默认资源，作为运行时文件系统资源不可用时的保底前端。
- 前端静态资源可部署到 Flash 文件系统并在设备运行时更新，资源包采用单一 gzip 压缩文件。若文件系统前端存在，运行时优先使用它；文件读取或 gzip 解压失败时，回退到固件内嵌前端。若文件系统前端不存在，则使用应用编译前端（若有），否则使用组件默认前端。
- 建议将前端构建为自包含的单页 HTML，再生成 gzip 文件，以维持单文件更新和回退语义；HTTP 服务应按最终响应内容正确设置 `Content-Type` 与 `Content-Encoding`，使浏览器透明解压。此内容组织与响应实现仍需验证。
- 后端基于 ESP-IDF 网络服务提供 Web Portal 能力。
- 前后端通信采用按流量类型选择的混合架构：控制/配置使用 JSON-RPC 2.0 over HTTP 或 WebSocket，实时双向交互优先使用 WebSocket 通知，OTA 和大文件导入/导出使用独立的原生 HTTP 流式接口。
- WebSocket 是传输通道，JSON-RPC 2.0 是消息协议，TLS 或其他经过设计的机制属于安全层；三者分别决策，不将其视为必须捆绑替换的单一协议方案。
- SSE 仅作为可选的单向只读事件流传输，不与 WebSocket 默认重复提供相同订阅；若启用，应明确其用途、认证、连接资源和背压限制。
- 参数和状态由组件提供的注册/分发机制与设备应用交互；组件不直接实现具体业务或硬件控制。
- NVS 持久化属于可配置的集成能力；具体配置的存储责任和安全策略需由组件与应用的接口设计明确。

### 2.2 组件与应用的职责边界

核心 Web Portal 负责通用 Web 接入和扩展机制：

- HTTP/HTTPS 服务、WebSocket 连接、JSON-RPC 2.0 传输适配及方法分发。
- 身份认证与授权基础设施。
- 前端静态资源服务及应用替换资源的约定。
- 应用可注册的方法、参数、状态、能力和通知接口。
- 对请求和连接实施资源限制，并向扩展模块提供一致的错误处理与生命周期约定。

以下能力可作为可选模块或由应用通过注册接口接入，不应成为核心 Web Portal 对特定业务组件的强制依赖：

- Wi-Fi 配网与网络配置是可选插件能力：实例选择托管 Wi-Fi 模式且固件编译了 Wi-Fi 配网能力时，由插件管理 SSID/Password、Wi-Fi 接口及其连接生命周期；DHCP/静态 IP 配置仅应用于插件拥有或获授权管理的接口。
- 实例选择外部网络模式时，ESP-Cockpit 不启用或调用内置 Wi-Fi 配网和网络管理能力；ESP-Cockpit 只使用现有网络运行 Web 服务，不接管接口、凭据或 IP 配置。
- 以太网网络接口及其参数由应用或网络组件管理；ESP-Cockpit 可观察网络就绪事件以协调 Web 服务生命周期，但不管理 Ethernet 驱动或接口。
- mDNS 等其他网络能力可作为独立可选插件或由应用通过注册接口提供。
- 参数持久化及 NVS 配置管理。
- 设备业务逻辑、传感器/执行器控制及具体协议（如 MQTT、BACnet、Modbus）。
- HTTP OTA、日志和芯片/固件运行信息等附加功能。

可选模块应能通过编译配置禁用。每个实例必须且只能选择托管 Wi-Fi 或外部网络模式之一；模式由实例配置显式选择，Kconfig 只控制相关能力是否编译。编译了 Wi-Fi 配网能力不代表实例自动进入托管模式；同一固件可由实例选择两种模式，外部模式不调用内置配网能力。默认配置不指定模式，应用必须显式选择；非法/缺失配置返回 `ESP_ERR_INVALID_ARG`，选择未编译能力返回 `ESP_ERR_NOT_SUPPORTED`。ESP-Cockpit 可订阅或接收网络状态以启动 Web 服务，但状态观察不代表接管网络资源。

网络集成采用互斥的“托管 Wi-Fi”与“外部网络”模式。应用通过创建实例显式且唯一地选择模式、注册扩展并启动一次生命周期控制器；模式在实例生命周期内不可切换。Kconfig 控制 Wi-Fi 配网等能力是否编译，所选模式与未编译能力不匹配时创建实例应明确失败。首版每个进程最多创建一个托管 Wi-Fi 实例，且最多一个 ESP-Cockpit 实例可同时持有活动 HTTP/WebSocket 服务资源；端口与应用自有服务的冲突须明确报错，不得覆盖已有服务。外部网络模式由应用主动报告 ready/not-ready：就绪时组件启动 Web 服务，失效时停止监听、关闭现有连接并释放活动服务资源；网络恢复后自动重新启动，实例本身保持运行。应用无需再次调用 Web Server 启动 API或逐一转发底层网络事件。`start()` 成功表示控制器已运行，不保证网络或 Web 页面已就绪；状态通过查询和高阶事件报告。`stop()` 停止组件服务及其拥有的托管 Wi-Fi 资源，但不触碰外部网络或共享全局设施。详细 API 生命周期见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)。

### 2.4 应用交互模型

- 应用可注册参数、状态、能力及其元数据。
- Web Portal 可读取应用当前状态，并通过注册的操作接口请求修改参数或执行设备操作。
- 修改请求由组件校验并分发至应用回调；应用执行实际业务或硬件控制，并向组件返回操作结果。
- 实时状态变化默认通过 WebSocket JSON-RPC 通知推送至已订阅的客户端；若产品只需要单向只读事件流，可选择 SSE 作为替代传输。
- 组件应定义参数读取、写入、状态通知、错误返回、并发调用和资源生命周期等约定。

## 3. 功能需求

### 3.1 核心功能

- 配置和呈现各类物联网设备参数。
- 展示传感器、执行器等设备的实时状态。
- 展示和修改设备内部控制逻辑参数。
- 接收用户操作并请求设备应用执行相应控制。
- 提供可扩展的参数、状态、方法及设备能力注册机制。

### 3.2 可选功能

所有内置可选功能均应能够通过编译配置启用或禁用。

#### 芯片与固件运行信息

- 静态信息：ESP-IDF 版本、芯片内核及版本、Bootloader 名称与版本、固件名称与版本等。
- 动态信息：任务及优先级、RAM 与 PSRAM 使用量等。

#### 日志

- 可选的日志查看或转发能力。

#### OTA

- HTTP OTA 是 ESP-Cockpit 内置的可选插件，可通过 Kconfig 启用或禁用；启用后支持网页端上传固件并执行 OTA。
- 支持固件下载（如产品场景需要）。
- 固件数据传输与 JSON-RPC 控制接口分离；具体 HTTP 上传端点、请求格式、分块方式、状态查询接口及安全策略待定。固件数据不得编码进 JSON-RPC 消息。

#### Wi-Fi Manager

- Wi-Fi 配网是组件的可选能力，可通过 Kconfig 控制是否编译。实例创建时必须显式选择托管 Wi-Fi 或外部网络之一；托管 Wi-Fi 实例只有在该能力已编译时才能使用插件管理 STA 的 SSID/Password、Wi-Fi 接口及连接生命周期。
- DHCP/静态 IP 配置仅作用于 ESP-Cockpit 拥有或明确获授权管理的接口；外部网络模式下，IP 配置由应用或外部网络管理组件负责。
- 插件内部处理 Wi-Fi 生命周期事件，并在配网 SoftAP 可提供服务或 STA 网络就绪时协调启动 Web 服务；应用不需要重复订阅并转发 Wi-Fi 底层事件。
- 首次启动或按产品策略触发时，可进入 SoftAP 配网模式。
- 可提供 Captive Portal 和 DNS 引导，使客户端连接配网 AP 后访问配网页面。
- 配网凭据持久化并支持重启后自动连接；凭据保护依赖设备安全配置（例如 NVS 加密）的具体设计。
- 配网成功并连接路由器后关闭 SoftAP。
- 再次进入配网模式应有物理触发机制（例如长按按键）或明确的自动关闭超时。
- 配网 AP 不得使用免密访问，应使用随机或设备独立的凭据。

#### 网络配置

- 显示和配置静态或动态 IP、子网掩码、网关及 DNS。
- 支持 IPv4；IPv6 能力按芯片、ESP-IDF 和网络接口支持情况确定。
- 可选支持 mDNS 和设备名称配置。

#### 网络协议配置

- 可选支持 BACnet MS/TP、BACnet/IP、Modbus RTU、Modbus/IP、MQTT 等协议的设备侧配置。
- 具体协议功能由独立模块或应用集成提供，核心组件不应因此与特定协议耦合。

## 4. 通信与接口设计

### 4.1 混合通信架构

- JSON-RPC 2.0 是控制/查询的消息协议；HTTP 与 WebSocket 是其可选承载方式。请求、参数校验、授权、方法分发和结果语义应尽量由同一 RPC 核心处理，传输适配层负责连接、认证凭据传递、消息帧及错误封装差异。
- 采用 JSON-RPC 的主要理由是统一动作/调用语义及方法分发，不预设其在所有实现中必然比 REST 更快或更省内存。HTTP 头部、JSON 解析和业务处理成本仍然存在；性能收益需在 ESP-IDF 目标配置下测量。HTTP 也可以承载 JSON-RPC，不应把“使用 HTTP”与“采用 REST”混为一谈。
- 当前主通道采用 WebSocket + JSON-RPC 2.0；不因使用 WebSocket 而放弃 HTTP 静态资源、HTTP JSON-RPC 请求/响应或原生 HTTP OTA/大文件流。传输通道、消息协议和安全层是独立的架构层次。
- 当前不以 CBOR-RPC 替代 JSON-RPC 2.0，也不自行设计新的密码协议。管理面默认采用 HTTPS/WSS；设备使用唯一身份凭据，客户端必须按产品定义的信任机制验证设备身份。经授权可配置产品/企业证书，证书配置失败不得静默降级为明文管理服务。设备出站连接独立采用 TLS 客户端验证。
- 不预设 CBOR 必然能显著降低本项目的资源开销。只有目标板测量显示 JSON 编码/解析或传输量是关键瓶颈时，才重新评估二进制协议；评估应比较代表性消息的编码大小、解析时间、峰值内存、Flash 占用和维护/调试成本。
- 统一定义 HTTP RPC 入口、WebSocket 连接地址、认证流程、方法命名、参数结构、错误码、通知事件和版本兼容策略。
- 请求/响应使用 JSON-RPC 2.0 的 `id` 关联；服务端主动推送使用不带 `id` 的通知消息。
- JSON-RPC 方法应覆盖认证/会话撤销、凭据设置与修改、网络配置、设备参数读写、重启及能力查询等操作；认证可由传输挑战响应完成，不强制定义独立的登录 RPC。
- **HTTP JSON-RPC** 可提供单一 RPC 入口（例如 `POST /rpc`），用于配置读写、低频控制和请求/响应式查询；**WebSocket JSON-RPC** 用于双向长连接交互及设备主动通知。服务端通知使用不带 `id` 的 JSON-RPC Notification。
- JSON-RPC 2.0 定义 Batch 数组请求；若实现支持，必须限制最大条数并定义执行/错误语义。客户端是否可依赖 Batch 需纳入接口配置文件，不应仅凭协议名称假设可用。
- **SSE（可选）** 仅用于单向、只读事件推送。若启用，不应默认与 WebSocket 对同一数据集重复广播；需定义认证、重连、事件丢失恢复、客户端数量和发送缓冲上限。SSE 不是 JSON-RPC 双向传输。
- **原生 HTTP 流** 用于固件上传/下载及大型配置、点表等导入/导出文件，不将二进制或大型文件内容编码为 JSON-RPC 参数。上传应分块处理并实施大小/速率/身份校验；导出应使用有界缓冲。实际 RAM 上限由 Web Server、TLS、文件系统、Flash 写入和并发负载共同决定，不能仅凭采用分块就承诺固定内存数。
- 静态前端资源、RPC、OTA 与其他管理接口默认通过 HTTPS/WSS 提供。所有管理接口使用一致的身份、授权和来源校验策略；协议差异（例如 HTTP 凭据头与 WebSocket 握手后的认证）需在详细设计中定义。明文 HTTP 仅作为受限的首次配网引导例外。
- 接口需支持能力发现，使前端能够获知当前设备启用的功能及可用方法。
- JSON-RPC 2.0 不定义认证机制；认证凭据或会话令牌如何随 HTTP 请求及 WebSocket 握手/后续消息传递、如何续期与撤销，需在详细设计中明确。
- 管理面默认采用 HTTPS/WSS，避免在明文链路上传输管理内容或加载可被替换的前端代码；TLS 不能替代应用层身份认证、授权、来源校验和速率限制。入站 TLS 身份与出站 TLS 信任配置分别管理。
- 每种传输都应设置消息/请求大小、并发操作、连接数、超时及待发送数据上限。HTTP JSON-RPC 不应因短连接而绕过资源保护；WebSocket/SSE 客户端也需有界管理。
- 大型 Schema 或参数集合应评估分页/游标式 RPC。若采用流式或分帧传输，必须定义应用层消息边界和完整性，确保客户端只处理完整、合法的 JSON-RPC 消息；HTTP Chunked 响应接口不适用于已经升级的 WebSocket 连接。
- 断线后客户端应能重新认证、读取一致状态快照并重新订阅；慢客户端应触发可预测的合并、丢弃非关键事件或断连策略。

### 4.2 方法范围（初步）

以下为逻辑方法范围，不是最终 JSON-RPC 方法名或参数定义：

| 功能 | 逻辑操作 |
|---|---|
| 用户认证 | 挑战响应认证、撤销会话、设置或修改管理凭据 |
| Wi-Fi Manager | 获取模式、提交配网凭据、清除 Wi-Fi 配置、切换模式 |
| 网络配置 | 查询网络状态，读取或更新 IPv4/IPv6 配置 |
| 网络协议 | 读取或更新 MQTT、BACnet、Modbus 等可选配置 |
| OTA | 查询 OTA 状态、开始或结束更新；固件数据走单独的传输通道 |
| 设备控制 | 重启设备、读取板级信息、读取或修改设备参数 |
| 实时数据 | 订阅或取消订阅状态/遥测更新，接收服务端通知 |
| 文件操作 | OTA 固件、点表或配置文件的导入/导出；大文件使用专用 HTTP 流式接口 |
| 能力发现 | 查询设备当前启用的能力和接口 |

具体参数类型、授权要求、错误码和状态机应在接口设计阶段另行定义。

配网操作应采用异步状态机。提交凭据的 RPC 应尽快返回“已接受/连接中”结果，实际连接在网络管理任务中继续执行；不得依赖固定延时确保响应送达。考虑到单射频 AP+STA 模式下 STA 切换信道可能导致 SoftAP 客户端断开，客户端应能够重新连接并查询当前/上次配网结果，或在重连后接收状态通知。认证失败、超时、用户取消、成功及再次进入配网模式的行为应分别定义；不能假定连接失败后总能恢复到原无线信道。

### 4.3 Schema 驱动前端

- 后端除参数当前值外，可提供参数元数据，例如类型、范围、单位、显示名称和读写权限。
- 前端可基于元数据自动生成表单和状态展示界面。
- Schema 版本、校验规则、国际化显示文本及自定义控件扩展方式需进一步设计。
- 对大型 Schema 和参数集合，应定义分页/游标、最大单页尺寸及版本一致性策略。避免一次性创建包含全部参数的 JSON DOM；流式序列化也需为单个参数、临时缓冲和发送队列设定上限，不能假设内存峰值与参数数量无关。

### 4.4 Matter-inspired 交互模型（待决）

- 可评估借鉴 Matter Interaction Model 的 **Read / Write / Invoke / Subscribe** 四类交互语义：Read/Write/Invoke 可由 JSON-RPC 2.0 over HTTP 或 WebSocket 承载；Subscribe 默认在 WebSocket 上以一次 JSON-RPC 响应建立订阅，后续通过无 `id` 通知推送。SSE 仅为可选的单向只读事件流替代方案。JSON-RPC 负责请求/响应与通知封装，Endpoint/Cluster/Attribute/Command 路径作为参数中的数据模型寻址。
- 该方向不代表实现 Matter 协议或具备 Matter 互操作性。Matter 原生编码使用 Matter TLV；本组件仍使用 JSON-RPC JSON 消息。
- Subscribe 应定义取消、过期、快照/增量一致性、重连及背压。大型文件不通过 JSON-RPC 传输，应使用独立 HTTP 流接口。
- 批量操作应在 `result` 中表达逐目标状态，并定义原子性；协议封装错误与交互层部分失败需区分。
- 业务具名 RPC、Endpoint 标识规则、Matter ID 复用及兼容适配器是否需要，仍待设计决策。详细分析见[Matter 交互模型与 JSON-RPC 映射](./esp-cockpit-interaction-model.md)。

## 5. 质量属性

### 5.1 性能与资源

- 并发设计目标按芯片分级：ESP32-S31、ESP32-S3、ESP32-P4 为 5 个并发短 HTTP 请求加 5 个 WebSocket 持续连接客户端；其他清单内目标为至少 2 个并发客户端，但当前只要求构建兼容，不要求实机验证该目标。建议的请求速率、持续时间和结果指标见 1.1.3 节。
- 按目标芯片和配置建立资源预算；若启用 TLS，覆盖握手峰值和空闲 TLS 连接，同时覆盖 WebSocket 会话、消息解析/序列化、订阅队列及 OTA 并发场景。至少验证无 PSRAM 的低内存核心验证目标。
- 对请求/消息大小、并发请求、连接数、订阅数、通知频率、待发送数据量和空闲超时设置明确上限，并定义达到上限时的错误或断连行为。
- TLS 缓冲区大小、动态缓冲配置、record 上限及 PSRAM 分配策略应基于 ESP-IDF v6.1 的实际配置和目标板测量决定。不得把单连接固定内存量或某个内存节省比例视为所有目标的保证。
- OTA 期间应对资源使用进行协调，例如拒绝并发 OTA、降低非必要广播频率，并避免非必要的高内存操作。

验收时应记录该目标规定并发数量下的空闲、握手及持续收发内存峰值，并确认系统在资源不足时拒绝新连接/请求而非发生崩溃。Kconfig 默认上限不得低于对应目标等级的并发要求；若硬件无法满足，需重新评估该目标的支持等级或产品要求。

### 5.2 可重用性与扩展性

- **REU-1**：前后端模块化、低耦合，便于跨 ESP-IDF 项目复用。
- **REU-2**：内置功能可通过编译配置选择启用或禁用。
- **REU-3**：应用无需修改组件源码即可注册新的 Web Portal 能力。
- **REU-4**：应用可替换默认前端。
- **REU-5**：前端模块化，并能与后端可选功能保持一致。

### 5.3 安全性

安全目标：防止未授权控制、固件被恶意篡改，以及恶意请求导致内存耗尽或系统崩溃。安全设计以管理面默认启用 TLS 为基线；这是一项产品安全架构选择，不等同于对 EN 18031-1/RED 适用性或符合性的法律结论。产品投放市场前应由合规评估方确认适用法规、标准版本、产品分类及符合性评估路径。

安全验收至少应验证：未认证客户端不能执行状态修改/设备控制；登录尝试有速率限制；HTTP/RPC/长连接输入及队列有上限；选定的传输/会话保护策略得到执行；配网门户仅开放经批准的受限操作。启用 OTA 时还应验证镜像完整性/签名策略。各项测试在核心功能验证目标上执行。

#### 传输安全与配网

- **第一层——默认入站管理面**：静态前端、HTTP JSON-RPC、WebSocket JSON-RPC、OTA 及其他管理接口默认使用 HTTPS/WSS。TLS 启用失败、证书不可用或握手失败时，不得自动回退为明文管理服务。TLS 之外仍须实现应用层身份认证、授权、请求来源校验、限速和输入/资源限制。
- **设备身份与密钥**：生产设备应使用设备唯一的证书和私钥，由产品选定的厂商 PKI 或企业 PKI 签发；设备不得持有 CA 签名私钥，也不得在设备间共享同一设备私钥。证书和私钥的产线注入/生成、受保护存储、更新轮换、吊销/失效、恢复出厂设置及设备退役流程需定义。Secure Boot、Flash Encryption 和调试接口保护可作为纵深防御要求评估，不能彼此替代，也不能单独替代密钥生命周期管理。
- **浏览器信任与动态地址**：TLS 加密不自动意味着浏览器已验证设备身份。客户端必须同时验证可信证书链及与访问地址匹配的设备身份；用户绕过浏览器证书警告不得视为已建立可信身份。产品必须选择可执行的信任建立方式（例如受信任根证书的安全分发/安装、企业 PKI 或受信任的配套客户端），并解决动态 IP 下稳定名称发现及证书 SAN 匹配。通过未认证的明文页面下载根证书，不能单独作为可信根的分发方式。
- **第二层——受控首次配网引导**：若配网流程确需明文 HTTP，只允许在设备独立密码保护的 SoftAP 或等效隔离网络中，经物理触发或受限时窗开放；只提供最小必要的初始配置操作，不开放常规管理 RPC，不传送长期管理凭据。配网完成、超时或安全配置失败时应关闭引导入口；重新开放须有明确的物理恢复/维护流程。TLS 未准备好时的失败状态和用户提示需定义，不得以明文静默接管常规服务。
- **第三层——出站 TLS**：设备作为 TLS 客户端访问云端、MQTT Broker、HTTPS Webhook 等时验证对端证书链和主机名；必要时允许应用配置受信任 CA。出站 TLS 独立于入站 Web Server 的设备证书与信任生命周期。
- **产品证书配置**：可为企业 PKI 或用户运维场景提供经授权的证书/私钥更换接口；验证证书与私钥匹配，限制访问，保护私钥存储，并支持失败回滚、清除和更新。配置失败不得静默降级到明文。
- TLS 握手、并发连接、证书解析及会话资源必须在目标芯片和配置上实测，并纳入并发、内存和故障恢复验收。
- WebRTC DataChannel 和 PAKE+AEAD 不列为首版默认路径。若后续提出远程点对点或端到端加密需求，再依据威胁模型独立评估，不得将其视为 TLS 的无条件替代。
- 参考[免证书安全通信方案](../ref/嵌入式设备免证书安全通信方案.pdf)中的架构讨论可供背景参考；其安全结论、Shelly 产品行为及示例协议/代码均须以一手资料和独立评审核实，不作为本组件规范。
- 配网完成后关闭 SoftAP；重新开放配网应受物理触发或有界时窗策略控制。
- 配网 AP 必须使用随机或设备独立密码，不得开放免密 AP。
- Captive Portal 的探测请求与 HTTPS 不应通过伪造证书或透明 HTTPS 重定向拦截。可评估仅在 SoftAP 配网阶段开放受限的明文 HTTP 门户，并为常见客户端探测提供适配响应；探测路径因操作系统而异，不能依赖单一路径。该明文门户仅用于受保护 AP 上的初始配置，其可访问操作和生命周期应受限制。

#### 身份认证与会话

- 初始凭据的配置、首次登录流程及用户修改用户名/密码的能力需定义。
- 管理面须在 HTTPS/WSS 上执行应用层身份认证与授权；TLS 不能替代账户/凭据策略，也不能据此开放未认证控制接口。
- 管理凭据应设备独立且足够强，通过安全的产品流程设置/交付；不得使用固件共享默认密码。认证速率限制、凭据修改/重置和会话撤销需纳入设计。
- 不得将设备控制接口暴露为无认证或无授权接口。
- 对登录失败进行速率限制，并定义失败计数、锁定时长和恢复策略。
- 若采用 Session/Token，定义其安全传输、存储、过期、并发隔离、撤销及设备重启后的行为；不得仅依赖 TLS 会话本身决定应用层授权。

#### OTA 安全

- 上传前校验固件头部及目标设备兼容性，防止错误固件或无效镜像写入。
- 生产环境应验证固件数字签名，并结合芯片支持情况启用 Secure Boot。
- OTA 操作应互斥并具备明确状态管理；进行中拒绝其他 OTA 请求。
- OTA 期间协调内存和后台任务，降低上传过程中的 OOM 风险。

#### Web 请求防护

- 对请求体、固件分块、并发连接、JSON 深度和字段长度实施上限。
- 防范 CSRF；HTTP JSON-RPC/文件接口及 WebSocket 握手和消息处理均应校验来源及授权，避免仅依赖浏览器同源假设。
- 配置适当的 HTTP 安全响应头。
- 对输入进行结构、范围和长度校验；错误响应不得泄露敏感信息。

## 6. 配置与技术选型

### 6.1 已明确方向

1. ESP-IDF v6.1。
2. 目标为具备 Wi-Fi 或以太网接口的乐鑫芯片，具体兼容性受硬件和 ESP-IDF 支持范围约束。
3. 前端采用 Vue 3、Svelte 或其他可生成静态资源的技术；组件和应用可分别提供编译期嵌入的默认资源，Flash 文件系统资源可在运行时覆盖。
4. 控制/配置使用 JSON-RPC 2.0，可经 HTTP 或 WebSocket 承载；WebSocket 默认承担双向实时通知。
5. SSE 可作为可选单向只读事件流，不与 WebSocket 默认重复实现。
6. OTA 固件和大型配置文件与 JSON-RPC 控制面分离，使用有界的原生 HTTP 流式上传/下载。
7. 后端通过 Kconfig 选择编译功能，例如 OTA、Wi-Fi 配网、可选 SSE 等。
8. 核心组件避免依赖特定业务协议或前端框架。

### 6.2 待评估事项

**网络服务与协议**

- ESP-IDF `httpd` 对 HTTP JSON-RPC、WebSocket、SSE（若需要）及原生流式接口的支持、并发资源和各目标芯片兼容性。
- JSON-RPC over HTTP 与 WebSocket 的方法覆盖范围、Batch 策略、鉴权传递、错误码、订阅模型、Schema 分页及大结果集传输方式。
- 是否需要 SSE；若采用，确定其与 WebSocket 的职责边界、重连和事件恢复语义。
- JSON 解析库选择：比较 cJSON、jsmn 等方案的内存占用、校验能力和维护成本。
- 是否需要二进制 RPC 编码仅在目标板实测证明 JSON 是关键瓶颈后再评估；若评估 CBOR，需作为独立协议候选并定义兼容边界，不应假设它是 JSON-RPC 2.0 的直接替代编码。

**网络安全与凭据**

- 确认 TLS 后端、证书格式/算法、握手与连接资源预算，以及 HTTPS/WSS 服务在证书缺失、无效或更新失败时的明确失败行为。
- 定义设备唯一证书/私钥的生成或注入、受保护存储、轮换、吊销/失效、恢复出厂设置和退役流程；评估 Secure Boot、Flash Encryption 与调试接口保护的组合要求。
- 决定浏览器信任建立方式及动态 IP 下的稳定设备命名、发现与证书 SAN 匹配策略；定义安装指引及用户遇到证书错误时的处理，不把绕过警告当作安全成功。
- 定义受授权的产品/企业证书更换接口、证书与私钥匹配校验、保护、回滚、清除和失败处理。
- 定义出站 TLS 客户端的信任库、服务器证书链/主机名校验及可选用户 CA 配置；其生命周期与入站证书配置分离。
- 确认 SoftAP 首次配网是否需要明文 HTTP、物理触发/限时边界、隔离方式、允许操作和关闭条件；常规管理服务不得因配网或证书错误降级为明文。
- 由产品合规评估方确认 RED/EN 18031-1 的适用性、适用版本及符合性评估路径；本需求文档的 TLS-first 设计不构成标准符合性结论。

**文件系统与前端资源**

- 文件系统选择：SPIFFS 与 LittleFS 的可用性、空间需求、资源包打包/校验、写入及升级方式。
- 单一 gzip 前端资源包的内部内容组织（建议自包含单页 HTML）、HTTP `Content-Encoding`/浏览器解压方式，以及缓存、更新和内存行为。
- 固件内嵌前端资源的构建集成方式（建议应用通过构建配置提供资源路径，构建时检查资源存在并替换组件默认资源，不要求修改组件源码）、Flash 文件系统 gzip 资源包校验方式，以及与后端 RPC/API 的版本兼容检查和浏览器缓存失效策略。

**持久化**

- 参数持久化 ID 的长度/命名规则、首版是否只接受显式短 ID、去抖与最大写回等待时间、立即写入参数范围及批量一致性策略。

**芯片兼容性**

- ESP-IDF v6.1 官方 target 名称核验，以及“原生以太网”是否允许 MAC 外接 PHY 的定义。

### 6.3 配置持久化与写入语义

- 持久化为可选能力；仅应用显式标记为持久化的参数写入 NVS。参数的显示名称、JSON/RPC 路径和持久化身份应分离，改动 UI 名称或 RPC 路径不应改变已保存数据的身份。
- 建议首版由应用为每个持久化参数提供独立、稳定且在组件持久化范围内唯一的短 `persist_id`，其长度符合 ESP-IDF NVS key 限制（最多 15 个字符）。不要直接截断长名称或只用 CRC32 自动生成 key；碰撞检查不得省略。暂不需要任意长 ID 时，不引入额外映射注册表。
- 若未来需要支持任意长 ID 或动态映射，再引入带版本的“完整 ID → NVS key”映射表，并定义唯一性、碰撞处理、损坏恢复和迁移语义。组件专用数据应使用明确归属的 NVS namespace，避免与应用数据混用。
- `persist_id` 一旦发布应保持稳定。改名或数据结构变化需显式、版本化迁移：读取旧值与版本、校验/转换、成功写入新值后再清理旧记录。迁移应可重复执行；中断或失败时保留仍可用的旧副本，不得把无迁移规则的旧值静默解释为新格式。
- 建议提供 `volatile`、`debounced`、`immediate` 等持久化策略。默认采用 RAM 即时生效并合并延迟写回；具体去抖时间和最大写回等待时间需按写入频率、Flash 磨损及可接受的数据丢失窗口确定。对少量必须立即保存的参数可单独选择 `immediate`。
- 状态与 API 应区分运行值已更新（`Applied`）、等待写回（`Pending`）、NVS 提交成功（`Persisted`）和持久化失败（`Persistence error`）。写入失败时运行值可能已经生效，但不得报告为已持久化；建议提供显式 `flush/save` 操作，并返回可诊断错误。
- 写回调度应在受控任务上下文执行，不得在中断或定时器回调中直接写 Flash；只有值实际变化时才标记为待写回。掉电、复位或强制断电可能丢失尚未提交的变更，不能依赖关机回调保证保存。
- 多参数批量修改默认逐项报告持久化结果，不承诺全有或全无；若一组参数必须保持一致，应另行设计版本化记录、双槽或 journal 等原子恢复机制。还需明确 NVS 空间不足、提交失败和数据损坏时的恢复行为。

### 6.4 前端资源与固件版本一致性

- 组件默认前端静态资源随组件编译并链接进固件；应用可以提供自己的编译期默认前端资源，构建时由应用资源替换组件默认资源。应用编译资源是文件系统资源不可用时的产品级保底前端。
- 建议在构建期选择应用前端或组件默认前端，避免将两份编译期资源同时打入固件；应用应通过受支持的 CMake 构建配置或 Kconfig 选项提供自定义资源，不应修改组件源码。具体注入机制待确定，且构建时应检查指定资源存在和可读。
- Flash 文件系统可存放独立于固件、运行时可更新的前端资源；资源包为单一 gzip 压缩文件。运行时优先级为：**可读取并成功解压的 Flash 文件系统前端 > 应用编译前端 > 组件编译前端**。
- 文件系统前端存在时，运行时尝试使用该资源；文件读取或 gzip 解压失败时，回退到固件内嵌前端（应用资源优先于组件资源）。文件系统资源不存在时，直接使用固件内嵌前端。版本兼容校验失败时的处理策略仍需明确。
- 建议将 Web 前端构建为自包含的单页 HTML，再生成一个 gzip 文件，避免多文件前端更新不完整或文件版本不一致；HTTP 服务应设置正确的 MIME 类型和 `Content-Encoding: gzip`，由浏览器解压。需在目标芯片上验证传输、缓存及解压行为。
- 文件系统资源加载应能在 HTTP 响应头发送前确认资源可读且 gzip 流有效；若采用边读边发送，则响应开始后发生的 I/O/解压错误无法替换为固件内嵌资源，因此需选择有界的预验证/缓存策略，避免为支持回退而无界占用 RAM。
- 建议更新流程为：接收至临时文件 → 检查长度/边界并验证 gzip 完整性 → 执行资源完整性及版本检查 → 原子替换正式资源。任一步骤失败应保留旧资源；具体文件系统是否支持所需原子操作须验证。
- gzip 自带 CRC 可辅助发现压缩数据损坏，但不证明发布来源可信。可采用 SHA-256 做完整性核验；若威胁模型要求防止恶意替换，还需数字签名或等效真实性验证。算法、密钥管理和是否强制签名仍待安全设计决定。
- 需要定义前端资源包内容组织、存在性判定、兼容性策略、单文件 Flash 更新原子性、升级失败恢复及浏览器缓存失效策略。前端资源以单一文件打包，避免运行时出现多文件资源不一致。
- 应定义前端与后端的协议/能力版本协商，并考虑浏览器缓存失效、单文件资源的原子更新、外部文件系统升级失败及固件回滚后的兼容性。
- 前端构建资源的注入机制、版本标识及校验方式应由组件构建配置或应用接口明确；不能仅依赖文件路径存在来判定资源兼容。

## 7. 兼容性验证与测试范围

完整测试框架和 CI/CD 暂不纳入当前交付范围，后续再制定；但不能因此省略本节规定的最低兼容性验收。构建检查适用于所有目标，核心功能和并发连接实机验证仅适用于表中相应等级。

- 单元测试：Unity / CMock。
- 集成测试和系统测试：包括 pytest-embedded。
- 测试环境：Host/Linux、模拟器或 QEMU（按目标支持情况）、实际硬件。
- 辅助机制：Mock、日志及逻辑分析仪 / sigrok-cli。
- 前端构建与 ESP-IDF 构建的自动化集成；应避免污染应用顶层工程的构建配置。

### 7.1 必需的兼容性验收

- **所有支持目标**：确认 IDF Target 映射有效，并以 ESP-IDF v6.1 对该 target 完成组件构建。SoC 修订版与 IDF 版本兼容性参考官方 [ESP-IDF v6.1 COMPATIBILITY.md](https://github.com/espressif/esp-idf/blob/release/v6.1/COMPATIBILITY.md)；该兼容性表不替代 target 清单核验。
- **核心功能验证目标（ESP32-S31、ESP32、ESP32-C6、ESP32-C5）**：实机验证基础 WebUI、按配置启用的 HTTP JSON-RPC/WebSocket/文件流、应用扩展接入及最低安全防护。
- **并发连接验证目标（ESP32-S31、ESP32-S3、ESP32-P4）**：实机验证 5 个短 HTTP 请求并发处理，同时维持 5 个 WebSocket 客户端连接；按 1.1.3 节的建议基线执行并记录结果。若产品启用且要求验收 SSE，再增加独立 SSE 场景。
- **其他目标**：本阶段只承诺构建兼容，不承诺尚未执行的运行时、功能安全或性能验证。
- 测试结果应记录芯片/模组/板卡、IDF 版本、构建配置、网络接口、PSRAM 配置、连接组合及测试结论，供后续变更回归。

## 8. 初步待决事项

以下事项需要在接口和模块设计前达成一致：

按主题分类的未决事项如下；具体协议和网络状态细节分别见对应设计补充文档。

### 芯片兼容与验收

- 其他已列芯片的 IDF Target 映射按兼容性验收要求通过 ESP-IDF v6.1 构建确认；ESP32-S31（`esp32s31`）的 v6.1 支持已由用户手动确认，不属于待核验项。未列入当前支持清单的新芯片需走新增目标验证流程。
- 确认 1.1.3 节建议的 5 RPS、30 分钟和每客户端 1 notification/second 是否作为正式验收阈值；如启用 SSE，确认是否需要单独验收。延迟门槛应依据目标板基线另行决定。

### 网络生命周期与接口

- 每个实例必须且只能选择托管 Wi-Fi 或外部网络模式；Kconfig 控制能力编译，实例配置选择模式。仍需确定 Kconfig 选项的具体名称/依赖，以及外部网络就绪状态 API 的具体参数（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。
- 首版每进程一个托管 Wi-Fi 实例、单个活动 ESP-Cockpit HTTP/WebSocket 服务及事件资源所有权约束已确定；需在实现阶段验证并发启动保护、HTTP 端口冲突错误传播和资源回滚（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。
- Wi-Fi 配网异步状态机、SoftAP 客户端断连后的恢复和状态查询方式。
- 公共 API 的最终 C 类型/函数签名、外部网络就绪通知参数、插件禁用时错误码及停止后是否允许同一实例重新启动；生命周期所有权与“单次启动控制器、组件协调 Web 服务”的原则已明确（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。

### JSON-RPC、数据模型与扩展 API

- JSON-RPC 通知订阅和状态广播的粒度、频率及背压处理方式。
- 参数注册、Schema、持久化 ID/策略和业务回调的公共 API 形态。
- 大型 Schema/参数集合的分页或分帧协议、快照一致性及最大响应预算。
- JSON-RPC over HTTP 与 WebSocket 的方法覆盖范围、Batch 支持及认证一致性；是否需要可选 SSE。
- 是否采用 Matter-inspired Read/Write/Invoke/Subscribe 模型、Endpoint/Cluster/Attribute/Command 标识及其与具名 RPC 的边界（详见[Matter 交互模型与 JSON-RPC 映射](./esp-cockpit-interaction-model.md)）。

### 认证、安全与信任边界

- WebSocket 的鉴权握手、Token 生命周期和同一设备的用户/角色模型。
- TLS 后端与 HTTPS/WSS 资源预算、设备身份凭据生命周期、浏览器信任建立方式，以及动态 IP 下的设备命名/发现和证书 SAN 匹配。
- 入站设备证书/私钥的产线生成或注入、保护、轮换、吊销/失效、恢复出厂设置和退役流程；产品/企业证书更换接口的授权、回滚及错误处理。
- 出站 TLS 客户端的信任锚配置、主机名校验、可选 CA 生命周期与资源验收。
- SoftAP 首次配网的物理触发/时间边界、允许操作、隔离及关闭条件；Captive Portal 探测适配不得引入常规明文管理接口。
- 核心安全验收用例，包括 TLS 证书链/身份与地址匹配、错误证书拒绝、无明文降级、授权/限速、并发 TLS 资源、证书更新失败回滚和受限配网窗口。
- RED/EN 18031-1 对本产品的适用性、采用标准版本及最终符合性评估结论，由产品合规评估流程确认。
- 参考[嵌入式设备免证书安全通信方案](../ref/嵌入式设备免证书安全通信方案.pdf)仅作为背景资料；其 Shelly 行为和安全结论需以一手资料核实，不作为规范。

### OTA 与大文件传输

- HTTP OTA 已确定为组件内置、可由 Kconfig 启停的可选插件；其 HTTP 上传端点、请求/分块格式、状态接口及安全策略仍待设计。
- OTA 与大文件导入/导出的 HTTP 流式接口、大小限制、鉴权、断连和原子性策略。

### 前端资源与固件兼容

- 编译期组件/应用前端资源的注入机制，以及 Flash 文件系统 gzip 单文件资源包的内容组织、校验和更新接口。
- 固件与前端版本兼容策略、gzip 文件系统资源的完整性/真实性校验、原子更新，以及版本不兼容时的处理和诊断流程。

### 持久化与数据一致性

- `persist_id` 的字符集/长度规则、去抖与最大写回等待时间、立即写入适用范围，以及需要原子性的批量参数保存机制。
