# ESP-Cockpit 组件需求与初步设计

> 状态：需求整理稿，供设计讨论使用。本文不代表已实现的功能，也不视为最终接口定义。

## 1. 项目概述

ESP-Cockpit 是一个通用的 ESP-IDF 组件，用于帮助基于乐鑫芯片的设备快速构建 Web Portal。首版目标范围限定为 ESP-IDF v6.1、`esp32s31` target 和 ESP32-S31-Function-CoreBoard-1 板卡上的 Wi-Fi 与板载以太网接口；其他 SoC target、板卡和外部网络控制器均不在首版支持范围。目标范围已收敛不等于验证通过；逐接口实测及证据登记前，不得宣称该配置已获得生产支持。

组件应以独立、可配置、易扩展为目标。设备应用负责业务逻辑和硬件控制，ESP-Cockpit 提供 Web 前后端基础设施及二者之间的通用交互机制。

### 1.1 硬件与目标芯片支持

#### 1.1.1 支持原则与网络接口范围

- 首版只支持本节列出的 ESP32-S31-Function-CoreBoard-1 硬件配置与 ESP-IDF v6.1；target/板卡配置以外的同 SoC 变体不得推定支持。未来新增芯片或板卡须经兼容性及资源验证后更新清单。
- 首版网络接口限定为该板的 Wi-Fi 与板载 Ethernet PHY/RJ45。以太网板级链路使用 ESP32-S31 的 RGMII 接口；不得将其他 target 的 RMII/MII 配置或验证结果外推到本板。
- **不支持外部以太网控制器**（例如 SPI Ethernet）、外接 Wi-Fi 协处理器以及其他板卡网络接口；应用如自行集成，须另行验证且不属于本组件首版支持声明。
- 用户已手动确认 ESP32-S31 受 ESP-IDF v6.1 支持，项目目标映射为 `esp32s31`。所引用的 [ESP-IDF release/v6.1 COMPATIBILITY.md](https://github.com/espressif/esp-idf/blob/release/v6.1/COMPATIBILITY.md) 主要描述 SoC 修订版与 ESP-IDF 版本兼容关系，不是完整 `IDF_TARGET` 清单，因此该文件没有 S31 条目不构成不支持的证据。

#### 1.1.2 支持等级与验收标准

组件的核心功能范围限定为：提供通用 WebUI、JSON-RPC over HTTP/WebSocket 通用机制及基础安全防护，为应用注册和扩展设备功能提供通用入口。原生 HTTP 流仅由需要大文件传输的可选插件按需使用，不属于首版独立交付功能。首版不提供 SSE 或 JSON-RPC Batch 数组。产品具体设备参数、业务逻辑和协议由应用或可选插件提供，不因此自动成为所有目标上的验收项。

**首版交付边界**：首版交付组件通用 WebUI、插件扩展机制和一个独立可构建运行的示例工程。示例必须通过 JSON-RPC 2.0 实际读取状态、修改并持久化一个示例设置，并呈现加载、成功和失败状态；示例设置的持久化由示例应用负责。首版默认采用外部网络模式：由应用提供并管理设备的 Wi-Fi/Ethernet 接入、网络凭据和网络就绪状态；示例使用应用已建立的网络运行。首版安全核心也属于组件交付与验收范围，包括 HTTPS/WSS TLS、无明文降级、认证与会话安全、请求来源和资源防护，以及通用设备证书装载/校验、设备本地 CSR 生成、签发证书安全更新和本地身份恢复导入/导出机制；准确 API 签名在 API 设计阶段确定。首版不实现 Wi-Fi 配网、OTA、日志、运行信息、网络配置或通用文件导入/导出等功能插件，只提供后续接入所需的扩展机制；设备身份专用的 CSR/证书更新及身份恢复接口属于上述安全核心 API，不是通用文件传输插件。OTA 的详细设计、支持矩阵与验收要求仅在后续产品版本选择启用 OTA 时适用，不构成组件首版交付或发布门槛。Wi-Fi 首次配网如产品需要，由产品应用或外部网络管理器另行实现，不属于 ESP-Cockpit 首版开箱即用能力。产品 CA、签发/恢复运营、factory ID 生产绑定、根证书分发与标签等由产品/制造方承担，并在相应产品试产/发布阶段验收；不作为组件独立交付前置依赖。插件未编译或未启用时，WebUI 隐藏相应入口。该边界可先交付并验证完整的通用 WebUI 和 RPC 集成，而不把产品网络流程绑入组件核心。

| 芯片 / 板卡 | IDF Target | 首版网络接口 | 当前状态 |
|---|---|---|---|
| ESP32-S31-Function-CoreBoard-1（ESP32-S31-WROOM-3） | `esp32s31` | Wi-Fi 6；板载 RGMII Ethernet PHY/RJ45 | 目标范围已确认；Wi-Fi 与 Ethernet 分别待构建、核心功能、安全及 5+5 性能实测；未形成生产支持声明 |

上表定义首版唯一候选硬件配置，不代表 Wi-Fi 或 Ethernet 已获得支持声明。每种网络接口是独立的验收配置；正式发布时须分别将实测配置、等级、结果和证据登记到仓库支持矩阵，矩阵未记录且未通过对应验收的接口不得宣称受支持。

**核心功能验证**要求必须构建，并在对应开发板/网络接口上验证基础 WebUI、HTTP JSON-RPC/WebSocket、应用扩展接入及首版安全核心。原生 HTTP 文件流及 OTA 仅在后续启用相应插件时纳入该插件的专项验收；产品 PKI/制造/远程恢复运营另按产品试产/发布验收，不阻塞组件独立交付。

支持等级须绑定到经过记录的具体产品配置，不得仅凭芯片 target 推定所有模组、板卡或构建配置均受支持。配置记录至少包含 SoC target/revision、模组/板卡、PSRAM 配置、网络接口/驱动、ESP-IDF 精确版本、TLS 后端及安全构建选项；每项声明标注其构建、核心功能和性能验证等级及证据引用。没有对应配置与证据记录的组合不得从同 target 的其他结果外推。

**并发连接验证**对首版每个明确生产配置（Wi-Fi、Ethernet 分别验收）要求满足下述 5+5 连接数和负载验收；它本身不表示完成完整 WebUI 功能和安全验证。每个接口还须分别通过核心功能和安全验收。

**构建兼容**要求能使用 ESP-IDF v6.1 为 `esp32s31` 目标完成生产配置构建；该项单独不表示完整运行时、功能、安全或性能验证通过。首版不接受“仅构建兼容”作为生产支持声明；Wi-Fi 和 Ethernet 两条配置均须完成对应实机验收。

#### 1.1.3 并发连接要求

- 首版每个网络接口配置（Wi-Fi、Ethernet 分开计）须支持至少 **5 个同时进行的短 HTTP 请求**，并同时支持 **5 个持续 WebSocket 客户端**。WebSocket 是默认并发验收基线。
- 5+5 并发验收应覆盖认证、请求/通知处理和资源限制，并确认资源不足时能有序拒绝或断连，不发生崩溃。HTTP 并发定义为同时处理的短请求数，不是 5 个长期占用的 HTTP keep-alive 连接。

#### 5+5 并发正式验收基线

- **突发并发场景**：5 个客户端同步发起短 HTTP 请求，验证服务端同时处理 5 个请求；此项用于验证并发处理能力，不能仅以持续平均 RPS 替代。
- **HTTP 持续负载场景**：5 个客户端各以约 1 request/second 发起只读、可重复的短请求（总计约 5 RPS），持续 30 分钟。所有通过认证、输入有效且处于已公布资源上限内的请求均须成功完成；突发并发验证应独立于该持续负载测试。
- **长连接基线**：5 个 WebSocket 客户端持续连接 30 分钟，每个客户端以约 1 notification/second 接收测试通知。测试期间不得发生非预期连接断开。首版不提供 SSE。
- **安全配置条件**：管理面默认使用 HTTPS/WSS，验证 TLS 下的身份认证、授权、来源校验和证书身份；出站 TLS 客户端应验证服务器证书链及主机名。并发与资源验收必须记录 TLS 配置。受限的明文 HTTP 仅可用于后续产品应用/可选插件所提供、物理触发或限时开放的隔离配网/身份恢复引导，不得静默降级承载常规管理接口；此类配网不属于首版。
- **结果记录与门槛确定**：至少记录有效负载请求成功数、延迟分布、连接断开/重连情况、空闲/握手/持续收发的 RAM 与 PSRAM 峰值、测试前后资源变化，以及是否发生崩溃、断言、持续内存增长或非预期断连。对每个明确生产配置测量基线后，逐配置确定请求/消息大小、队列、连接/订阅容量、超时、p95/p99 和最低空闲内存安全余量；不预设未经实测的跨芯片统一数值。若未达门槛，先优化或收紧并公布该配置的资源上限；仍未达标则降低或暂停该配置的支持等级，不得以平均值掩盖失败。
- 上述突发并发数、速率、持续时间及通知频率是首版 Wi-Fi 与 Ethernet 两种生产配置各自的正式验收基线。资源上限外请求可按契约以稳定资源错误拒绝或有序断连，不计为有效负载成功请求；不得崩溃、断言或静默丢弃。并发目标不等于底层 socket 数，测试报告应记录 target、板卡、IDF 版本、网络接口、PSRAM 配置、TLS/KDF 配置、请求类型及通知频率。

## 2. 系统架构

### 2.1 架构原则

- 采用前后端分离架构。
- Web 前端以静态资源形式部署，可使用 Vue、React、Svelte 或原生 HTML/CSS/JavaScript 开发。
- 组件提供随组件编译并链接进固件的默认前端资源，作为基础回退内容。
- 应用可将自定义默认前端资源随应用编译并链接进固件；若应用提供该资源，构建产物使用应用资源替换组件默认资源，作为运行时文件系统资源不可用时的保底前端。
- 通用 WebUI 根据组件和应用注册的能力及 Schema 呈现通用状态和设置界面；可选插件的界面入口只在相应能力实际启用时显示，未编译或未启用的插件入口隐藏。
- 提供独立示例工程验证端到端使用：经 JSON-RPC 2.0 读取状态、修改并持久化示例设置，并显示加载、成功和失败状态。示例应用负责示例设置的持久化。
- 前端静态资源可部署到 Flash 文件系统并在设备运行时更新，资源包采用单一 gzip 压缩文件。资源包 manifest/摘要须由产品密钥签名；组件验证签名及资源完整性后才原子启用资源包。若签名、完整性、读取、解压或固件兼容性检查失败，回退到固件内嵌前端并提供诊断；若文件系统前端不存在，则使用应用编译前端（若有），否则使用组件默认前端。
- 建议将前端构建为自包含的单页 HTML，再生成 gzip 文件，以维持单文件更新和回退语义；HTTP 服务应按最终响应内容正确设置 `Content-Type` 与 `Content-Encoding`，使浏览器透明解压。此内容组织与响应实现仍需验证。
- 后端基于 ESP-IDF 网络服务提供 Web Portal 能力。
- 前后端通信采用按流量类型选择的混合架构：控制/配置使用 JSON-RPC 2.0 over HTTP 或 WebSocket，实时双向交互优先使用 WebSocket 通知；启用需要大文件传输的可选插件时，固件或文件数据使用独立的原生 HTTP 流式接口。
- WebSocket 是传输通道，JSON-RPC 2.0 是消息协议，TLS 或其他经过设计的机制属于安全层；三者分别决策，不将其视为必须捆绑替换的单一协议方案。
- 首版状态订阅统一使用 WebSocket，不提供 SSE；组件不自动持久化应用注册的通用属性，参数存储和迁移由应用负责。
- 参数和状态由组件提供的注册/分发机制与设备应用交互；组件不直接实现具体业务或硬件控制。
- 通用 Schema 属性的持久化和迁移由应用负责；组件内部或其他可选模块的配置持久化策略独立管理，不隐式套用于应用注册属性。

### 2.2 组件与应用的职责边界

核心 Web Portal 负责通用 Web 接入和扩展机制：

- HTTP/HTTPS 服务、WebSocket 连接、JSON-RPC 2.0 传输适配及方法分发。
- 提供通用 JSON-RPC 机制、能力/Schema 注册与方法分发；具体设备业务方法由应用提供。
- 身份认证与授权基础设施。
- 前端静态资源服务及应用替换资源的约定。
- 应用可注册的方法、参数、状态、能力和通知接口。
- 对请求和连接实施资源限制，并向扩展模块提供一致的错误处理与生命周期约定。

以下能力可作为可选模块或由应用通过注册接口接入，不应成为核心 Web Portal 对特定业务组件的强制依赖：

- Wi-Fi 配网与网络配置是可选插件能力：实例选择托管 Wi-Fi 模式且固件编译了 Wi-Fi 配网能力时，由插件管理 SSID/Password、Wi-Fi 接口及其连接生命周期；DHCP/静态 IP 配置仅应用于插件拥有或获授权管理的接口。
- 实例选择外部网络模式时，ESP-Cockpit 不启用或调用内置 Wi-Fi 配网和网络管理能力；ESP-Cockpit 只使用现有网络运行 Web 服务，不接管接口、凭据或 IP 配置。
- 以太网网络接口及其参数由应用或网络组件管理；ESP-Cockpit 可观察网络就绪事件以协调 Web 服务生命周期，但不管理 Ethernet 驱动或接口。
- mDNS 等其他网络能力可作为独立可选插件或由应用通过注册接口提供。
- 参数持久化及 NVS 配置管理。
- 设备业务逻辑、传感器/执行器控制及具体协议（如 MQTT、BACnet、Modbus）。
- HTTP OTA、日志和芯片/固件运行信息等附加功能。

可选模块应能通过编译配置禁用。每个实例必须且只能选择托管 Wi-Fi 或外部网络模式之一；模式由实例配置显式选择，Kconfig 只控制相关能力是否编译。编译了 Wi-Fi 配网能力不代表实例自动进入托管模式；同一固件可由实例选择两种模式，外部模式不调用内置配网能力。默认配置不指定模式，应用必须显式选择；非法/缺失配置返回 `ESP_ERR_INVALID_ARG`，选择未编译能力返回 `ESP_ERR_NOT_SUPPORTED`。ESP-Cockpit 可订阅或接收网络状态以启动 Web 服务，但状态观察不代表接管网络资源。

网络集成采用互斥的“托管 Wi-Fi”与“外部网络”模式。应用通过创建实例显式且唯一地选择模式、注册扩展并启动一次生命周期控制器；模式在实例生命周期内不可切换。Kconfig 控制 Wi-Fi 配网等能力是否编译，所选模式与未编译能力不匹配时创建实例应明确失败。首版每个进程最多创建一个托管 Wi-Fi 实例，且最多一个 ESP-Cockpit 实例可同时持有活动 HTTP/WebSocket 服务资源；端口与应用自有服务的冲突须明确报错，不得覆盖已有服务。外部网络模式由应用主动报告 ready/not-ready：就绪时组件启动 Web 服务，失效时停止监听、关闭现有连接并释放活动服务资源；网络恢复后自动重新启动，实例本身保持运行。应用无需再次调用 Web Server 启动 API或逐一转发底层网络事件。`start()` 成功表示控制器已运行，不保证网络或 Web 页面已就绪；状态通过查询和高阶事件报告。`stop()` 停止组件服务及其拥有的托管 Wi-Fi 资源，但不触碰外部网络或共享全局设施。详细 API 生命周期见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)。

### 2.4 应用交互模型

- 应用可注册参数、状态、能力及其元数据。
- Web Portal 可读取应用当前状态，并通过注册的操作接口请求修改参数或执行设备操作。
- 修改请求由组件校验并分发至应用回调；应用执行实际业务或硬件控制，并向组件返回操作结果。
- 独立示例工程通过 JSON-RPC 2.0 读取状态并修改示例设置；示例应用负责将该设置持久化，组件不替应用持久化通用注册属性。
- 实时状态变化通过 WebSocket JSON-RPC 通知推送至已订阅的客户端；首版不提供 SSE。
- 组件应定义参数读取、写入、状态通知、错误返回、并发调用和资源生命周期等约定。

## 3. 功能需求

### 3.1 核心功能

- 配置和呈现各类物联网设备参数。
- 展示传感器、执行器等设备的实时状态。
- 展示和修改设备内部控制逻辑参数。
- 接收用户操作并请求设备应用执行相应控制。
- 提供可扩展的参数、状态、方法及设备能力注册机制。

### 3.2 可选功能

所有内置可选功能均应能够通过编译配置启用或禁用。首版只提供这些插件的扩展机制，不实现下列具体插件功能；插件未编译或未启用时，WebUI 隐藏对应入口。

#### 芯片与固件运行信息

- 静态信息：ESP-IDF 版本、芯片内核及版本、Bootloader 名称与版本、固件名称与版本等。
- 动态信息：任务及优先级、RAM 与 PSRAM 使用量等。

#### 日志

- 可选的日志查看或转发能力。

#### OTA

- HTTP OTA 是 ESP-Cockpit 内置的可选插件，可通过 Kconfig 启用或禁用；启用后支持网页端上传固件并执行 OTA。
- 支持固件下载（如产品场景需要）。
- 固件数据传输与 JSON-RPC 控制接口分离；具体 HTTP 上传端点、请求格式、分块方式、状态查询接口及安全策略待定。固件数据不得编码进 JSON-RPC 消息。

#### Wi-Fi Manager

- Wi-Fi 配网是组件的可选能力，可通过 Kconfig 控制是否编译。实例创建时必须显式选择托管 Wi-Fi 或外部网络之一；托管 Wi-Fi 实例只有在该能力已编译时才能使用插件管理 STA 的 SSID/Password、Wi-Fi 接口及连接生命周期。
- DHCP/静态 IP 配置仅作用于 ESP-Cockpit 拥有或明确获授权管理的接口；外部网络模式下，IP 配置由应用或外部网络管理组件负责。
- 插件内部处理 Wi-Fi 生命周期事件，并在配网 SoftAP 可提供服务或 STA 网络就绪时协调启动 Web 服务；应用不需要重复订阅并转发 Wi-Fi 底层事件。
- 首次启动或按产品策略触发时，可进入 SoftAP 配网模式。
- 可提供 Captive Portal 和 DNS 引导，使客户端连接配网 AP 后访问配网页面。
- 配网凭据持久化并支持重启后自动连接；凭据保护依赖设备安全配置（例如 NVS 加密）的具体设计。
- 托管 STA 关联路由器并取得有效 IP、Wi-Fi Manager 进入 `ONLINE` 后，启动有界过渡窗口；窗口到期自动关闭 SoftAP。`ONLINE` 不要求互联网或云服务可达。若连接尝试失败，在配网门户自身的限时窗口内保持 SoftAP 可用以便查询、修正和重试；失败不清除已有有效凭据。门户总时限到期仍关闭；设备曾进入 `ONLINE` 后再断网不得自动重开 SoftAP。
- 再次进入配网模式应有物理触发机制（例如长按按键）或明确的自动关闭超时。
- 配网 AP 不得使用免密访问，应使用随机或设备独立的凭据。

#### 网络配置

- 显示和配置静态或动态 IP、子网掩码、网关及 DNS。
- 支持 IPv4；IPv6 能力按芯片、ESP-IDF 和网络接口支持情况确定。
- 可选支持 mDNS 和设备名称配置。

#### 文件导入/导出

- 文件导入/导出属于可选插件能力；首版只提供插件扩展机制，不实现相应端点或界面入口。

#### 网络协议配置

- 可选支持 BACnet MS/TP、BACnet/IP、Modbus RTU、Modbus/IP、MQTT 等协议的设备侧配置。
- 具体协议功能由独立模块或应用集成提供，核心组件不应因此与特定协议耦合。

## 4. 通信与接口设计

### 4.1 混合通信架构

- JSON-RPC 2.0 是控制/查询的消息协议；HTTP 与 WebSocket 是其可选承载方式。请求、参数校验、授权、方法分发和结果语义应尽量由同一 RPC 核心处理，传输适配层负责连接、认证凭据传递、消息帧及错误封装差异。
- 采用 JSON-RPC 的主要理由是统一动作/调用语义及方法分发，不预设其在所有实现中必然比 REST 更快或更省内存。HTTP 头部、JSON 解析和业务处理成本仍然存在；性能收益需在 ESP-IDF 目标配置下测量。HTTP 也可以承载 JSON-RPC，不应把“使用 HTTP”与“采用 REST”混为一谈。
- 当前主通道采用 WebSocket + JSON-RPC 2.0；不因使用 WebSocket 而放弃 HTTP 静态资源、HTTP JSON-RPC 请求/响应或可选插件所需的原生 HTTP OTA/大文件流。传输通道、消息协议和安全层是独立的架构层次。
- 当前不以 CBOR-RPC 替代 JSON-RPC 2.0，也不自行设计新的密码协议。管理面默认采用 HTTPS/WSS；设备使用唯一身份凭据，客户端必须按产品定义的信任机制验证设备身份。经授权可配置产品/企业证书，证书配置失败不得静默降级为明文管理服务。设备出站连接独立采用 TLS 客户端验证。
- 不预设 CBOR 必然能显著降低本项目的资源开销。只有目标板测量显示 JSON 编码/解析或传输量是关键瓶颈时，才重新评估二进制协议；评估应比较代表性消息的编码大小、解析时间、峰值内存、Flash 占用和维护/调试成本。
- 统一定义 HTTP RPC 入口、WebSocket 连接地址、认证流程、方法命名、参数结构、错误码、通知事件和版本兼容策略。
- 请求/响应使用 JSON-RPC 2.0 的 `id` 关联；服务端主动推送使用不带 `id` 的通知消息。
- JSON-RPC 方法应覆盖会话登录/撤销、凭据设置与修改、网络配置、设备参数读写、重启及能力查询等操作；具体登录/认证 API 形态待详细设计，但浏览器会话使用 Cookie，不通过 URL 传递长期 Token。
- **HTTP JSON-RPC** 可提供单一 RPC 入口（例如 `POST /rpc`），用于配置读写、低频控制和请求/响应式查询；**WebSocket JSON-RPC** 用于双向长连接交互及设备主动通知。服务端通知使用不带 `id` 的 JSON-RPC Notification。
- 首版仅接受单条 JSON-RPC Request/Notification，拒绝 Batch 数组；多路径 Read/Write 是单条 RPC 内的交互模型，不属于 JSON-RPC Batch。这样可减少解析、执行顺序、错误映射与峰值内存复杂度；只有性能证据支持时才重新评估 Batch。
- 首版不提供 SSE；状态订阅统一使用 WebSocket，避免额外维护连接、认证、重连和背压路径。若将来出现明确的只读订阅兼容需求，再评估 SSE。
- **原生 HTTP 流** 用于固件上传/下载及大型配置、点表等导入/导出文件，不将二进制或大型文件内容编码为 JSON-RPC 参数。上传应分块处理并实施大小/速率/身份校验；导出应使用有界缓冲。实际 RAM 上限由 Web Server、TLS、文件系统、Flash 写入和并发负载共同决定，不能仅凭采用分块就承诺固定内存数。
- 静态前端资源、RPC、OTA 与其他管理接口默认通过 HTTPS/WSS 提供。所有管理接口使用一致的身份、授权和来源校验策略；WebSocket 复用 HTTPS 登录会话 Cookie，并在握手及后续调用中校验会话/授权与精确 Origin。明文 HTTP 仅作为受限的首次配网引导例外。
- 接口需支持能力发现，使前端能够获知当前设备启用的功能及可用方法。
- JSON-RPC 2.0 不定义认证机制；浏览器端通过 HTTPS 会话 Cookie 认证，WebSocket 握手复用该 Cookie，不在 URL/query 中传递长期 Token。
- 管理面默认采用 HTTPS/WSS，避免在明文链路上传输管理内容或加载可被替换的前端代码；TLS 不能替代应用层身份认证、授权、来源校验和速率限制。入站 TLS 身份与出站 TLS 信任配置分别管理。
- 每种传输都应设置消息/请求大小、并发操作、连接数、超时及待发送数据上限。HTTP JSON-RPC 不应因短连接而绕过资源保护；WebSocket 客户端也需有界管理。
- 大型 Schema 或参数集合使用有界分页；Schema 分页采用绑定 Cluster Schema 修订号的不透明游标。若采用流式或分帧传输，必须定义应用层消息边界和完整性，确保客户端只处理完整、合法的 JSON-RPC 消息；HTTP Chunked 响应接口不适用于已经升级的 WebSocket 连接。
- 断线后客户端应重新认证、重新订阅并获取新快照；订阅不跨 WebSocket 连接恢复。慢客户端使用有界队列并按路径合并为最新状态、携带版本/序号；持续溢出时终止订阅或连接，不无限缓存。
- 首版不提供通用 JSON-RPC Batch、SSE、通用幂等键或“恰好一次”保证。JSON-RPC `id` 仅关联请求/响应；各 Command 须说明能否安全重试，客户端不得盲目重放非幂等操作。
- HTTP JSON-RPC 仅接受 `POST` 与 `application/json`；`GET` 不承载 RPC 且不得修改状态。状态变更请求必须携带 CSRF token 并通过精确 Origin 校验。

### 4.2 方法范围（初步）

以下为逻辑方法范围，不是最终 JSON-RPC 方法名或参数定义：

| 功能 | 逻辑操作 |
|---|---|
| 管理员认证 | Cookie 会话认证、撤销会话、设置或修改管理员密码 |
| Wi-Fi Manager | 获取模式、提交配网凭据、清除 Wi-Fi 配置、切换模式 |
| 网络配置 | 查询网络状态，读取或更新 IPv4/IPv6 配置 |
| 网络协议 | 读取或更新 MQTT、BACnet、Modbus 等可选配置 |
| OTA | 查询 OTA 状态、开始或结束更新；固件数据走单独的传输通道 |
| 设备控制 | 重启设备、读取板级信息、读取或修改设备参数 |
| 实时数据 | 订阅或取消订阅状态/遥测更新，接收服务端通知 |
| 文件操作 | OTA 固件、点表或配置文件的导入/导出；大文件使用专用 HTTP 流式接口 |
| 能力发现 | 查询设备当前启用的能力和接口 |

具体参数类型、授权要求、错误码和状态机应在接口设计阶段另行定义。

配网操作应采用异步状态机。提交凭据的 RPC 应尽快返回“已接受/连接中”结果，实际连接在网络管理任务中继续执行；不得依赖固定延时确保响应送达。考虑到单射频 AP+STA 模式下 STA 切换信道可能导致 SoftAP 客户端断开，客户端应能够重新连接并查询当前/上次配网结果，或在重连后接收状态通知。认证失败、超时、用户取消、成功及再次进入配网模式的行为应分别定义；不能假定连接失败后总能恢复到原无线信道。

### 4.3 Schema 驱动前端

- 使用 C 侧静态注册、运行时可查询的受限 Schema 子集，不在设备端实现完整 JSON Schema 引擎。首版通用 UI 仅支持标量字段：布尔、整数/数值、字符串、枚举及基本范围/长度约束和展示元数据；枚举值使用稳定字符串标识，显示名称独立本地化，列表顺序不作为值；整数固定为有符号 `int32_t` 范围，确保浏览器可精确表示并简化跨平台转换；普通字符串采用全局字节上限，字段 Schema 可声明更小的上限，字段长度约束按 UTF-8 字节数计算，WebUI 必须采用相同单位校验；不支持数组、对象、条件规则、引用或组合 Schema，复杂界面由应用定制。该限制控制解析复杂度、峰值 RAM 和通用 UI 复杂度；字符串、消息和分页上限由目标资源测试确定。
- Endpoint、Cluster、Attribute、Command 均使用小写 ASCII 字符串标识，仅含字母、数字、下划线和连字符；禁止空白、控制字符和 Unicode，以避免大小写/Unicode 归一化造成路径混淆。子标识在父对象内唯一，完整路径负责消歧，因此这些数据路径标识不另设全局反向域名注册表；应用命名空间则单独使用小写 ASCII 反向域名风格（至少三个点分标签，每段仅含字母、数字和连字符，且不得以连字符开头/结尾）来标记应用方法、能力和错误码归属，不嵌入数据路径。标识长度上限待资源测试。Cluster 各自版本化，路径标识保持稳定，兼容新增与破坏性变更通过版本演进区分。
- 应用 capability ID 在完整应用命名空间后以点连接至少一个后缀标签；各标签仅含小写 ASCII 字母、数字和连字符，不能空或以连字符开头/结尾。沿用命名空间标签规则可简化校验，必需的后缀使应用身份与具体能力易于区分。
- 每个属性声明只读、读写或只写；Read/Write 处理器按 Cluster 提供，并通过属性标识分发。回调使用带类型标记的 C `union` 标量值，不接收原始 JSON；整数使用 `int32_t`，带小数的数值使用 `double`，两者使用不同类型标记。当 Schema 允许 JSON `null` 时，值类型使用明确的 `NULL` 标记，否则拒绝 `null`。字符串使用指针和 UTF-8 字节长度表示；`STRING` 类型必须提供非空指针，长度为 `0` 表示空字符串，JSON `null` 则使用 `NULL` 类型标记。组件负责 JSON 与 C 值之间的转换及 Schema 校验；Read 回调返回非法 UTF-8 或非有限 `double`（`NaN`、正负无穷）时拒绝该值并报告错误，不做有损替换或数值替换。属性 Read 字符串由应用在同步保护下复制到组件提供的有界缓冲区，并取得对应版本；缓冲区不足时明确报错，不截断。组件保持快照稳定至序列化完成，避免应用并发修改导致值与版本不一致。Write 回调收到的字符串仅在回调期间有效，应用若需保留须自行复制。组件在每次调用中强制检查属性权限，不能依赖 UI 限制；启动时按属性权限校验该 Cluster 必需的处理器。只写敏感值不能通过 Read/API 回显。Schema 提供类型、范围、单位和权限等元数据；参数持久化及迁移由应用负责，组件不自动写 NVS。
- 有只写属性写入权限的客户端可通过 Read 获取该属性的当前值版本及必要元数据，但不得获取属性值；无写入权限的客户端不得以此读取版本。Write 仍使用版本检查并发冲突，避免敏感值无法读取时失去覆盖保护；版本本身可能暴露属性变化，因此读取须执行授权。
- 只写属性的版本由 Cluster 的 Read 处理器通过明确的“只取版本”模式提供，应用无需读取或返回属性值。即使 Cluster 只有只写属性，也必须提供支持该模式的 Read 处理器；启动时缺失则报告错误并拒绝启动。复用 Read 处理器可避免增加专门的版本查询回调。
- Read 处理器结果使用独立的值存在标记：只取版本时不提供值；实际值为 JSON `null` 时仍标记为已提供值并使用 `NULL` 类型。这样可以区分未返回值和返回空值，并检查只写值是否被意外返回。
- 应用负责同步维护属性值及版本，所有修改来源共用同一同步规则；Write 在应用侧原子比较版本并更新，过期则拒绝。Read 的值与版本须来自同一一致状态，只写属性不返回值。组件的 RPC 回调串行化不覆盖应用其他任务，应用侧同步才能避免并发覆盖。
- Write 成功表示对应路径的新值已被应用逻辑接受，不自动表示已持久化；持久化策略和迁移由应用负责。若应用选择同步持久化，回调只有在满足该持久化承诺后才能报告成功；失败须作为该路径的明确失败返回，不得伪报已持久化。若采用延迟持久化，应用须通过可读状态明确表达 Applied/Pending/Persisted/Failed，持久化失败应可见；掉电可能丢失待写值，产品须说明此语义。多路径 Write 仍逐项报告并允许部分成功，前端不得把整体请求表述为全有或全无。
- 应用回调执行失败须返回稳定业务错误码；排队时间超过公布上限而尚未开始执行时返回稳定 `busy`。组件不强制中断已开始的回调；长时操作使用 Operation。RPC `id` 不提供幂等保证，Write/Invoke 的响应未知时 WebUI 提示用户刷新实际状态或由用户决定是否重试，不自动重放非幂等操作。
- 只写属性不可订阅；Subscribe 请求包含只写路径时整体报错且不创建部分订阅，防止订阅快照或通知泄露只写值。
- 应用调用 `new()` 时通过单个类型化描述符整体提交 Cluster、属性、命令、方法、能力和回调；根描述符始终声明一个稳定的小写 ASCII 反向域名风格应用命名空间（例如 `com.acme.greenhouse`），即使描述符没有应用注册项也必须提供。这样应用身份不会随注册项是否为空而改变，后续增加方法或能力时也无需另换命名空间。描述符按 Schema/Cluster、方法、能力、事件/回调及扩展职责分组注册内容；应用方法、capability ID 和业务错误码范围均归属于该命名空间。应用自行分配 capability ID 后缀，并在该命名空间内保持 ID 稳定且唯一，不从 RPC 方法名推导，以便分别演进功能标识和调用接口。该命名空间只是标识，不进行 DNS 查询；应用负责保证它稳定且唯一。描述符指针必填，但允许包含零个注册项。组件在 `start()` 时统一校验并冻结注册表，服务启动后注册表不可变。描述符及其引用的注册元数据由应用持有，并须在组件实例销毁前保持有效且不可变；典型用法是静态只读数据，组件只保留引用、不深拷贝。回调的 `user_ctx` 由应用持有，组件只借用且不释放；应用须保持其有效，直至 `del()` 成功返回。组件统一校验描述符中的标识、Schema 和必需回调；有重复标识、无效声明或缺失回调时拒绝启动管理服务并报告明确错误，不接受部分注册。能力发现由经认证的只读接口提供，返回已注册能力、Schema 版本和支持操作，并限制响应尺寸。
- 显示文本使用本地化 key，英文是组件必备基线；locale 资源随固件离线打包，按浏览器语言选择已打包语言，未匹配时回退英文，不使用在线翻译。产品须声明实际随固件提供的语言集合。标签、帮助文本和枚举名称以纯文本渲染，不允许 Schema 注入 HTML。
- 前端基于 Schema 自动生成常见控件；应用可将同源自定义页面在构建时随固件打包。禁止运行时安装/加载任意脚本插件或第三方 CDN 脚本；受控的固件/Flash 文件系统静态资源仍按既定前端资源策略提供。对大型 Schema/参数集合使用有界分页/游标与版本一致性策略；避免不受控 JSON DOM 和无界缓冲。
- 首版核心管理流程以 WCAG 2.2 AA 为验收目标，至少验证键盘可操作、可见焦点、控件标签与错误信息关联、颜色对比度及主流屏幕阅读器使用；自动化扫描不能替代手动验收。

### 4.4 Matter-inspired 交互模型

- 首版采用混合模型：通用路径化 **Read / Write / Invoke / Subscribe** 服务常见状态读写和订阅，专用工作流可注册具名 RPC；两条入口共用授权、校验和一致的业务语义。Read/Write/Invoke 可经 HTTP 或 WebSocket，Subscribe 仅经 WebSocket；JSON-RPC 只接受单条消息，不支持 Batch 数组，首版不提供 SSE。
- 该方向不代表实现 Matter 协议或具备 Matter 互操作性。Matter 原生编码使用 Matter TLV；本组件使用 JSON-RPC JSON 消息。
- Subscribe 与当前 WebSocket 连接同生命周期；断线后重新订阅并获取新快照，不补发断线期间的通知。状态通知采用有界队列、按路径合并最新值并携带版本/序号；持续溢出时终止订阅或连接。该机制不承诺逐条传送中间状态；可靠业务事件须另行设计。
- 多路径 Read 逐路径返回状态及可用版本，不承诺原子快照；多路径 Write 逐项授权/校验并返回结果，允许部分成功。必须全有或全无的业务操作由专用 Command/RPC 实现。请求整体不可执行的协议、认证/授权或资源错误使用顶层 JSON-RPC `error`；多路径单项失败放入 `result` 的逐项状态。错误码稳定，消息不得泄露堆栈、凭据或内部状态。
- JSON-RPC `id` 仅用于请求/响应关联，首版不提供通用去重或“恰好一次”；各 Command 声明是否可安全重试。业务回调由有界队列投递到单一执行上下文串行运行；回调须短时、非阻塞，长操作异步化，队列满时明确返回忙碌/资源不足。
- 长操作可创建设备级 Operation，返回 ID、状态和可选进度；首版状态为 `running`、`succeeded`、`failed`，不提供通用取消语义；需要取消的具体操作由该操作单独定义取消接口。任一有效管理员会话可查询；登出、会话失效或客户端断线不自动取消任务。状态表有界，达到活动任务上限时拒绝新任务，终态记录可淘汰，绝不静默丢弃活动任务。Operation 仅驻留 RAM；设备重启后旧 ID 变为未知，客户端须重新读取实际设备状态，不假设任务成功或安全重试。
- 详细分析见[Matter 交互模型与 JSON-RPC 映射](./esp-cockpit-interaction-model.md)。
- JSON-RPC 客户端契约的实现级定义见[ESP-Cockpit JSON-RPC 协议契约](./esp-cockpit-json-rpc-contract.md)；本文档记录设计理念和取舍，具体方法/字段以契约文档为准。

## 5. 质量属性

### 5.1 性能与资源

- 首版 Wi-Fi 和 Ethernet 生产配置分别以 5 个并发短 HTTP 请求加 5 个 WebSocket 持续连接客户端为并发目标；建议的请求速率、持续时间和结果指标见 1.1.3 节。
- 针对 ESP32-S31-Function-CoreBoard-1 的每种网络接口配置分别建立资源预算；若启用 TLS，覆盖握手峰值和空闲 TLS 连接，同时覆盖 WebSocket 会话、消息解析/序列化及订阅队列。首版不启用 OTA。
- 对请求/消息大小、并发请求、连接数、订阅数、通知频率、待发送数据量和空闲超时设置明确上限，并定义达到上限时的错误或断连行为。
- TLS 缓冲区大小、动态缓冲配置、record 上限及 PSRAM 分配策略应基于 ESP-IDF v6.1 的实际配置和目标板测量决定。不得把单连接固定内存量或某个内存节省比例视为所有目标的保证。
- OTA 期间应对资源使用进行协调，例如拒绝并发 OTA、降低非必要广播频率，并避免非必要的高内存操作。

验收时应记录该目标规定并发数量下的空闲、握手及持续收发内存峰值，并确认系统在资源不足时拒绝新连接/请求而非发生崩溃。Kconfig 默认上限不得低于对应目标等级的并发要求；若硬件无法满足，需重新评估该目标的支持等级或产品要求。

### 5.2 可重用性与扩展性

- **REU-1**：前后端模块化、低耦合，便于跨 ESP-IDF 项目复用。
- **REU-2**：内置功能可通过编译配置选择启用或禁用。
- **REU-3**：应用无需修改组件源码即可注册新的 Web Portal 能力。
- **REU-4**：应用可替换默认前端。
- **REU-5**：前端模块化，并能与后端可选功能保持一致。

### 5.3 安全性

安全目标：防止未授权控制、固件被恶意篡改，以及恶意请求导致内存耗尽或系统崩溃。安全设计以管理面默认启用 TLS 为基线；这是一项产品安全架构选择，不等同于对 EN 18031-1/RED 适用性或符合性的法律结论。产品投放市场前应由合规评估方确认适用法规、标准版本、产品分类及符合性评估路径。

安全验收至少应验证：未认证客户端不能执行状态修改/设备控制；登录尝试有速率限制；HTTP/RPC/长连接输入及队列有上限；选定的传输/会话保护策略得到执行；配网门户仅开放经批准的受限操作。启用 OTA 时还应验证镜像完整性/签名策略。各项测试在核心功能验证目标上执行。

#### 传输安全与配网

- **管理访问范围**：ESP-Cockpit 管理面面向设备所在的本地网络，不提供云端中继、端口映射、远程代理或厂商代管通道。产品或部署方如需异地管理，必须由独立的 VPN、企业网络或其他受控网络服务提供连通性；ESP-Cockpit 仍按设备 TLS 身份、证书名称、认证和授权规则提供管理服务，不承诺跨公网可达，也不因远程路由而放宽安全校验。设备侧监听可达范围及外围防火墙策略由产品集成和部署负责。
- **第一层——默认入站管理面**：静态前端、HTTP JSON-RPC、WebSocket JSON-RPC、OTA 及其他管理接口默认使用 HTTPS/WSS。TLS 启用失败、证书不可用或握手失败时，不得自动回退为明文管理服务。TLS 之外仍须实现应用层身份认证、授权、请求来源校验、限速和输入/资源限制。
- **设备身份与密钥**：生产设备使用设备唯一的证书和私钥；设备不持有 CA 签名私钥，也不与其他设备共享设备私钥。制造流程必须在受控工厂工位触发设备本地生成私钥和 CSR，由厂商 PKI 签发，工厂安装证书并将设备证书、SAN 与唯一 factory ID 绑定校验；设备私钥不得从设备导出或由工厂/云端保存。产品厂商对该工厂流程及其委托方的安全和追溯负责。各目标芯片必须验证是否具备满足量产威胁模型的密钥保护能力；Secure Boot、Flash Encryption 和调试接口保护属于纵深防御措施，不能彼此替代，也不能单独替代密钥生命周期管理。
- **组件证书 API 边界**：组件负责 HTTPS/WSS TLS 服务和通用设备身份操作：由应用/工厂提供初始设备身份；组件在设备本地生成私钥和 CSR 并提供 CSR 导出；接收签发后的证书时，校验其与本地密钥匹配、SAN/设备身份、TLS server authentication 用途及有效期，再原子切换身份，失败时保留原有效身份。组件不得导出设备私钥，不内置 CA 签名能力，也不访问厂商云端签发或恢复服务。证书句柄、密钥存储/provider 及 CSR/证书导入导出的具体公共 C API 形态留待 API 设计；实现必须提供等价能力并满足上述失败语义。
- **设备专用 PKI**：产品厂商负责运营 ESP-Cockpit 专用根 CA、受控中间 CA、证书签发/恢复服务及应急响应；允许委托受控服务商执行，但厂商仍对信任根安全、签发审计和服务连续性承担端到端责任。根 CA 仅用于 ESP-Cockpit 设备 HTTPS，不与厂商网站、其他产品或通用业务证书共用；根 CA 私钥离线保护，日常设备证书由受控中间 CA 签发；签发系统限制证书用途为 TLS server authentication，并保留签发审计。企业部署可采用企业 PKI，但证书 SAN 必须匹配企业 DNS 名称。
- **产品身份运营责任**：CA 运营、证书签发决策及授权、factory ID 分配与工厂身份绑定、根证书/标签指纹分发、签发/恢复门户、恢复码和账户/订单核验、授权维修/RMA 及 PKI 服务连续性，均由产品厂商、制造商或其受控委托方负责；委托不转移产品厂商的端到端责任。这些运营能力不属于 ESP-Cockpit 组件实现或云端依赖。
- **浏览器信任建立**：普通浏览器直连是主要使用场景，不以官方 App 作为建立信任的前提。用户首次使用时从厂商官方 HTTPS 页面获取厂商根证书，并按平台指引安装到操作系统/浏览器信任库；设备或包装标签提供相同根证书的指纹，供用户独立核验。选择此流程是为了让浏览器验证设备证书链而不依赖忽略警告；根证书本身不是秘密，关键是可信分发和核验。具体主流桌面/移动平台的安装行为及浏览器信任范围必须实测并提供指引。不能只从未认证的设备本地网页下载根证书，也不能把用户忽略证书警告视为已验证设备身份。
- **首版浏览器平台范围**：首版目标平台为 Windows、macOS、iOS/iPadOS 和 Android 上经验证的主流系统浏览器。支持矩阵须记录受支持的操作系统和浏览器确切版本；以产品发布时仍由厂商维护的稳定版本为支持候选，只有完成证书信任及核心管理流程实测的组合才列为正式支持。不得承诺未经验证的组合，也不得建议用户忽略证书警告作为替代。
- **稳定网络身份**：家庭网络优先使用 mDNS 主机名 `esp-<factory-id>.local`；`factory-id` 由工厂配置流程分配并校验唯一，不使用 MAC 地址或可读序列号。这样可避免在局域网名称中暴露硬件地址或容易枚举的序列号，同时将工厂唯一性检查作为防止不同设备重名的主要措施。该主机名写入设备证书 SAN，出厂后不可由用户修改；用户可修改独立的显示名称而不改变访问身份。固定名称可避免 DHCP 地址变化破坏书签和证书名称校验；mDNS 只负责发现设备，不构成设备身份认证。企业网络可使用企业 DNS 名称及 SAN 与之匹配的企业 PKI 证书，作为 mDNS 被禁用时的路径。
- **mDNS 名称冲突**：若运行时发现 `esp-<factory-id>.local` 冲突，设备不得自动追加后缀、更改证书身份或回退到明文 HTTP/IP 管理；应保留证书绑定的名称并报告名称冲突及服务不可用，避免浏览器访问地址与证书 SAN 不一致。企业环境应配置企业 DNS 名称，并使用包含该名称的证书 SAN。工厂唯一性检查与运行时冲突检测分别用于降低冲突概率和明确处理异常。
- **首次使用标签与二维码**：产品制造商负责生成并交付包装/说明书通用二维码，以及每台设备的标签内容；通用二维码指向厂商 HTTPS 首次设置指南，设备标签提供可读的设备 HTTPS 地址 `https://esp-<factory-id>.local`、设备专属直达二维码和厂商根证书指纹。厂商负责指南、根证书分发、指纹核验说明和各平台安装指引，并保证标签数据与出厂设备身份绑定。若产品应用另行提供 SoftAP 配网，其唯一强随机凭据也由制造商安全交付并与设备绑定。用户先通过厂商 HTTPS 页面取得根证书并与标签指纹核对，再访问设备地址。这样普通浏览器无需依赖 App，设备地址也不必从未认证的明文设备页面取得；保留可读地址便于桌面用户手动输入。二维码只负责打开指南或地址，不能替代证书链验证；mDNS 被禁用时使用管理员配置的企业 DNS 地址及匹配证书。
- **首次使用流程**：首版由应用负责使设备接入局域网，ESP-Cockpit 不提供 Wi-Fi 配网或 SoftAP 引导；产品应用可按自身需求提供网络设置流程，或使用已配置的 Wi-Fi/Ethernet。用户先扫描包装/说明书上的通用二维码，打开厂商 HTTPS 指南，下载根证书、核对设备标签上的根证书指纹并按平台指引安装；设备接入局域网并发布固定 mDNS 名称后，用户扫描设备专属二维码或输入标签地址，以 HTTPS/WSS 访问管理面。首次管理员凭据通过设备物理触发的 10 分钟初始化窗口建立，窗口仅允许一个客户端原子完成，成功或超时即关闭。试产前须在 Windows、macOS、iOS/iPadOS 和 Android 的目标系统浏览器逐项实测并提供可操作指引；只有可靠建立设备身份的平台/浏览器组合才能列入正式支持，未通过的平台不得以忽略证书警告替代。若产品应用另行提供 SoftAP 配网，其网络配置门户必须受设备独立密码和有界时窗保护；若必须使用明文 HTTP，只能提交完成初始联网所必需的数据，不开放常规控制/RPC，不传送管理密码或会话 Token，配网完成或时限结束即关闭。mDNS 冲突或 TLS 证书验证失败时须明确报告并停止访问，不得降级到 HTTP 或 IP 管理。
- **首次引导边界**：首次安装根证书和信任建立不得依赖未认证的明文设备页面。若配网流程确需明文 HTTP，只允许在设备独立密码保护的 SoftAP 或等效隔离网络中，经物理触发或受限时窗开放；只提供最小必要的初始配置操作，不开放常规管理 RPC，不传送长期管理凭据。配网完成、超时或安全配置失败时关闭引导入口；TLS 未准备好时须明确报告失败，不得以明文静默接管常规服务。重新开放引导须有明确的物理恢复/维护流程。
- **设备身份生命周期**：恢复出厂设置清除 Wi-Fi、管理凭据和用户数据，但保留出厂设备证书/私钥及稳定网络主机名。这样用户无需重新安装根证书，且设备身份不会因普通重置而变化；原有用户权限必须同时失效。更换设备时新设备必须使用自己的新身份，禁止复制旧设备私钥。
- **离线与证书有效期**：产品厂商承担至少 15 年离线本地管理目标所需的证书轮换和恢复支持责任；该目标不要求单张设备证书具有 15 年有效期，也不要求设备持续连接厂商服务器才能续期。设备须在证书有效期内提示管理员并支持离线 CSR/证书文件轮换；证书过期后关闭常规管理端点，不得降级为明文管理，仅保留物理触发、限时且受设备独立密码保护的身份恢复文件通道。产品 PKI 负责人必须在试产前批准证书有效期、到期告警提前量、续期服务支持期限及恢复 SLA；系统/硬件集成负责人须指定可信时间来源、断电后的重获时间策略和不可信时间行为。组件按显式可信/不可信时间状态实施边界检查，不得以未经验证的设备时钟接受过期证书；时钟倒退、长期断电和无网络场景须按产品批准的策略验证。
- **离线设备证书轮换**：轮换时设备在本地生成新私钥和 CSR，私钥不离开设备；用户可用另一台联网设备将 CSR 提交厂商运营的 HTTPS 签发门户，再把签发证书文件导回本地设备，因此设备本身不必联网。厂商负责门户可用性、签发流程和证书生命周期支持；常规轮换请求须由当前设备私钥签名，厂商验证当前设备证书链、旧密钥签名和设备状态后才签发；仅提交 CSR 或公开序列号不足以授权签发。设备导入时校验证书链、SAN/设备身份、TLS server authentication 用途、有效期及证书公钥与本机新私钥匹配，通过后才原子切换；切换前保留当前有效凭据，失败时回滚，避免证书更新导致管理服务中断。该文件往返方式兼顾离线使用和私钥不导出，代价是需要用户/管理员执行轮换操作。
- **旧身份私钥不可用时的恢复**：正常轮换的旧密钥签名流程不可用时，厂商负责提供并运营受控的远程恢复/签发流程，签发授权不得仅依赖公开序列号。设备使用唯一的一次性高熵恢复码，并要求核验原购买账户/订单；恢复码置于包装内密封卡片或刮涂层下，不印在设备外部标签，厂商服务端仅保存用于验证的安全摘要。该双重核验是为了降低公开编号、单一账户或单份恢复码泄露导致冒用的风险；成功签发后恢复码立即作废、旧证书停用、操作留审计记录并通知原购买账户。恢复码遗失或远程核验不通过时，由厂商提供授权服务点维修或 RMA 流程，不以公开序列号替代恢复凭据。
- **本地身份恢复通道**：旧 HTTPS 身份私钥不可用时，首版组件须提供设备本地身份恢复 API/受限文件通道：用户通过物理按键开启设备独立密码保护且限时的 SoftAP 恢复窗口；本地页面仅允许导出 CSR 和导入厂商签发的证书文件，不提供普通管理/RPC，也不收集恢复码、账户密码或会话 Token。由于原 HTTPS 身份不可用，文件交换可能需要受限 HTTP；物理触发、独立 AP 密码、时间窗口和文件操作白名单共同限制其暴露面。设备仍在本地生成并保留新私钥；导入验证成功后才切换身份，恢复结束或超时即关闭入口。恢复码与账户核验、签发授权及远程恢复仅由厂商 HTTPS 门户提供，不属于组件责任。
- **CA 轮换与泄露处置**：ESP-Cockpit 专用根 CA 长期稳定并严格离线保护，日常计划轮换签发用中间 CA；这样可减少普通用户重复安装根证书的运维负担。仅在根私钥泄露或密码算法淘汰等重大事件时更换根，并准备新旧信任重叠、经认证的迁移指引及停止旧根信任的应急流程。设备证书或私钥疑似泄露时按受影响设备处置，不因单台设备事件轮换所有设备的根信任锚。
- **吊销的离线限制**：吊销单台设备证书是生命周期要求，但不能假设普通浏览器在隔离或长期离线的局域网内会立即获知吊销状态。因此不能将在线吊销检查作为唯一控制措施；需结合设备私钥保护、软件/证书更新和适合离线部署的恢复/封禁流程，并在威胁模型中明确吊销生效延迟。
- **第三层——出站 TLS**：设备作为 TLS 客户端访问云端、MQTT Broker、HTTPS Webhook 等时验证对端证书链和主机名；必要时允许应用配置受信任 CA。出站 TLS 独立于入站 Web Server 的设备证书与信任生命周期。
- **产品证书配置**：可为企业 PKI 或用户运维场景提供经授权的证书/私钥更换接口；验证证书与私钥匹配，限制访问，保护私钥存储，并支持失败回滚、清除和更新。配置失败不得静默降级到明文。
- TLS 握手、并发连接、证书解析及会话资源必须在目标芯片和配置上实测，并纳入并发、内存和故障恢复验收。
- WebRTC DataChannel 和 PAKE+AEAD 不列为首版默认路径。若后续提出远程点对点或端到端加密需求，再依据威胁模型独立评估，不得将其视为 TLS 的无条件替代。
- 参考[免证书安全通信方案](../ref/嵌入式设备免证书安全通信方案.pdf)中的架构讨论可供背景参考；其安全结论、Shelly 产品行为及示例协议/代码均须以一手资料和独立评审核实，不作为本组件规范。
- 配网 STA 关联路由器并取得有效 IP、进入 `ONLINE` 后，经有界过渡窗口自动关闭 SoftAP；该成功判定不要求互联网或云端可达。连接失败时，门户限时窗口未结束前保留 SoftAP 供状态查询、修正和重试，不清除已有有效凭据；窗口到期后关闭。设备曾进入 `ONLINE` 后发生断网，不自动重开 SoftAP；重新开放配网应受物理触发或已认证操作控制。
- 若产品应用或后续可选插件提供配网 SoftAP，仅在物理触发后于有界时窗内开放，并使用每台设备唯一的强随机密码；密码可印在设备标签/二维码上，以支持包装遗失或二手转让后的配网。物理触发、密码和限时共同限制接入窗口；不得开放免密 AP 或使用全产品共享密码。成功后按 `ONLINE` 过渡窗口策略关闭，失败时保持至门户窗口到期。此流程不属于 ESP-Cockpit 首版交付。
- 若产品应用或后续可选插件提供 Captive Portal，其探测请求与 HTTPS 不应通过伪造证书或透明 HTTPS 重定向拦截。可评估仅在 SoftAP 配网阶段开放受限的明文 HTTP 门户，并为常见客户端探测提供适配响应；探测路径因操作系统而异，不能依赖单一路径。该明文门户仅用于受保护 AP 上的初始配置，其可访问操作和生命周期应受限制。

#### 身份认证与会话

- 产品约束为仅一个本地管理员身份，允许该身份建立多个并发会话；不提供只读访客或角色/RBAC，也不按个人区分管理员活动。审计对已认证操作统一归因于“管理员”，登录失败记录为未认证尝试；不得据此宣称识别实际操作者。该模型意味着共享管理员凭据的人员无法按个人分别授权、审计或撤销；若未来产品要求个人级问责，须先重新定义产品身份与权限模型，而非将共享管理员凭据当作多用户方案。
- 固件不得包含共享默认管理员密码。产品约束是不设置用户名，用户仅使用管理员密码登录；单管理员模型不需要额外账户标识，可减少无效配置和兼容负担。用户首次通过已验证 HTTPS 设备地址访问时，须先物理触发一次性初始化窗口；窗口持续 10 分钟，期间不开放常规管理/RPC，仅允许一个客户端原子完成初始化，成功或超时即关闭入口，重新开放须再次物理触发。不另设 claim code，以降低凭据交付复杂度；接受的风险是窗口内同一局域网客户端可能抢先初始化。若初始化时间窗、所有权边界或可信客户端可验证性不足，后续应重新评估是否引入独立 claim 凭据。
- 管理员密码至少 12 个字符，采用 ASCII 输入，允许空格，不强制大小写/数字组合。校验时仅移除首尾 ASCII 空格，保留内部空格；移除后必须为 12–128 字节，拒绝控制字符，超长明确报错，不静默截断。创建与登录执行完全相同的规范化规则。使用随固件更新的离线拒绝列表，覆盖常见弱密码和产品通用默认词条；不联网查询，也不按设备个体信息动态拒绝。这样兼顾密码管理器/粘贴输入与设备离线可用，且避免规则随设备身份变化。
- 密码不得以明文或可逆形式保存；在 ESP32-S31-Function-CoreBoard-1 的生产 PSRAM 配置上基准测试 Argon2id 与经过审查的标准密码 KDF（例如 PBKDF2-HMAC-SHA-256），依据实测的延迟、RAM 占用和安全预算确定首版 KDF，不自创算法。每个密码使用密码学随机盐，并保存算法版本和参数，以支持后续升级。Flash/NVS 加密仅属纵深防御，不能替代密码 KDF；算法、成本、盐和参数编码方式须在目标板验证后冻结。
- 管理面须在 HTTPS/WSS 上执行应用层身份认证与授权；TLS 不能替代账户/凭据策略，也不能据此开放未认证控制接口。不得将设备控制接口暴露为无认证或无授权接口。
- 浏览器登录和设置密码支持密码管理器自动填充与粘贴，使用正确的 `autocomplete` 语义，不阻止复制/粘贴，也不试图控制浏览器是否保存密码；设备仍只保存 KDF 验证材料。
- 浏览器会话使用 `Secure`、`HttpOnly` Cookie，并设置 `SameSite`（优先 `Strict`，须在正式支持浏览器上验证兼容性）；不得把长期会话 Token 放入 URL 或 Web Storage。允许同一管理员建立多个并发会话。空闲 30 分钟或绝对有效期 24 小时后会话失效。仅成功的用户发起认证操作/RPC 重置空闲计时；WebSocket ping/pong、后台轮询和自动重连不续期，绝对期限不变。会话只保存在易失内存，设备任何重启（包括 OTA 重启）后全部失效，要求重新登录，不将会话凭据写入 NVS。登出撤销当前会话；管理员修改密码、恢复出厂或重新初始化时撤销所有会话，相关 WebSocket 立即关闭。这样避免后台心跳无限延长会话，并简化重启与撤销语义，代价是重启后需要重新登录。
- HTTP 管理 API 与前端同源提供；精确校验 HTTP `Origin`（scheme/host/port）和 WebSocket 握手 `Origin`，不接受不匹配的浏览器来源；拒绝带凭据的宽泛 CORS。所有改变状态的 HTTP 请求必须携带 CSRF token 并通过精确 Origin 校验；`GET` 等安全方法不得修改状态。Cookie 会由浏览器自动附带，故单靠身份认证不足以阻止跨站请求；CSRF token、Origin 和 SameSite 共同限制跨站操作。非浏览器客户端的来源策略另行定义。
- 不得将设备控制接口暴露为无认证或无授权接口。
- 密码修改必须重新验证当前管理员密码；修改成功后撤销所有会话（包括当前会话），要求使用新密码重新登录。这样可降低遗留或被接管的会话被用来更改凭据的风险，并立即使所有旧会话句柄失效。忘记密码时使用已定义的物理恢复出厂/重新初始化流程，不允许仅凭仍有效的登录 Cookie 绕过当前密码验证。
- 登录失败采用渐进式延迟并设置上限；在执行高成本密码 KDF 前实施限速，并限制全局并发验证数量和排队长度；资源不足时明确拒绝，不得永久锁定唯一管理员账号。渐进延迟降低在线猜测速度，全局有界验证资源可防止更换来源绕过单客户端限制并缓解 KDF 导致的 CPU/RAM 耗尽；不全局锁死可避免攻击者造成长期拒绝服务。应先在 ESP32-S31-Function-CoreBoard-1 的生产配置上测量候选 KDF 的时间/RAM 成本，再通过攻击负载和正常误输测试确定失败阈值、延迟曲线、并发/队列上限、计数恢复及重启行为。
- 恢复出厂/设备转手允许现场人员通过明确的物理操作在未登录旧管理员账号时清除本地数据；这只允许擦除 Wi-Fi、管理凭据、会话和用户数据并进入受限重新配网流程，不恢复或泄露旧配置，也不直接授予常规管理权限。这样二手设备可由新持有人接管且不依赖旧所有者；接受的代价是实际接触设备者可造成配置清除型拒绝服务。具体按键时长、防误触和提示策略由产品 UX 定义。设备转手不改变设备证书/私钥及固定网络身份；产品云账户解绑如有需要，由具体产品另行处理。

#### OTA 安全

- 首版由用户在电脑/手机上取得固件文件，经设备本地 HTTPS 管理页面上传；设备无需访问互联网，适配长期离线管理。OTA 操作只允许有效管理员会话，不额外要求重新输入密码。首版采用两阶段安装：先上传并在设备端校验，再展示设备从映像中读取的应用版本、目标兼容性、固件大小及完整性/签名校验状态，由管理员明确确认安装并重启。上传前不可信任文件名、MIME 类型或浏览器声明；分阶段确认可避免误选文件未经设备校验便成为启动映像。所有状态变更请求均执行会话授权、CSRF token 和精确 Origin 校验。
- OTA 使用独立 HTTPS 任务接口，与 JSON-RPC 控制面分离；建议的资源操作为创建任务、上传映像、查询状态、确认安装和取消任务，具体 URL/字段在 API 设计阶段确定。创建请求只接受正整数 `expected_bytes` 及短期 `request_id`，不接受客户端声明的版本、目标芯片或文件名作为可信字段。创建前校验分区容量和配置上限；创建成功取得设备级 OTA 互斥，并返回 `task_id`、当前状态及开始上传的剩余时长。任务须在创建后 2 分钟内开始上传，否则记为 `timed_out` 并释放互斥。相同管理员会话对同一 `request_id` 重试时返回原任务，不同创建请求在槽位被占用时返回稳定 `busy`；去重记录只绑定当前会话和活动任务，任务结束或过期即删除。截止时间使用单调时钟，不依赖设备 UTC。映像使用 `application/octet-stream` 原始字节流有界上传，以减少 multipart 解析、复制和峰值内存。上传必须提供与 `expected_bytes` 完全相同的 `Content-Length`；上传前检查大小，接收期间再次按实际字节数强制执行上限，且结束时确认总字节数精确匹配。上限取非活动分区可容纳大小和组件配置上限的较小值，避免映像超出容量或耗尽设备资源。只读状态查询使用受管理员会话保护的 HTTP `GET`、`Cache-Control: no-store`，不要求 CSRF token 且不改变状态；任务 ID 仅用于状态关联，不是授权凭据。
- 上传过程采用有界流式处理，写入非活动 OTA 分区；完成接收后按 ESP-IDF/目标原生机制检查镜像、签名、目标芯片/硬件兼容性及版本，再进入待安装确认状态。若特定目标的签名仅能在 bootloader 阶段最终验证，确认页和状态必须明确标注该验证阶段，不得声称安装前已完成签名验证。首版不自创固件容器、manifest 签名格式或密码学机制；按各目标 ESP-IDF v6.1 实际提供的格式和 API 实现，IDF 原生校验未覆盖的普通兼容性字段再明确补充校验。
- 正式应用版本使用严格 `MAJOR.MINOR.PATCH` 数值比较；生产版本不使用预发布标记或构建元数据。ESP-IDF 的 `esp_app_desc_t.version` 是最长 32 字符的字符串，并不替组件定义 SemVer 解析或排序，因此生产构建须显式设置并校验 `PROJECT_VER`，确保版本值符合严格格式且能放入该字段；组件负责严格解析和比较各数值段。低于当前运行版本的映像拒绝安装；同版本映像仅在设备完成校验且管理员明确确认后允许重装。每个正式版本号必须始终对应同一不可变固件制品，避免用相同版本号替换不同内容。这样可以避免字符串排序歧义并保持版本标识可审计。应用版本与芯片反降级使用的 `secure_version` 是两个独立概念；安全版本下限仅在确需时提升，不随普通发布版本递增，以保留回滚空间并避免消耗有限的 eFuse 更新能力。参见 ESP-IDF v6.1 [App Version 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/api-reference/system/misc_system_api.html#app-version)及 [OTA Anti-rollback 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/api-reference/system/ota.html#anti-rollback)。
- 首版使用 A/B OTA 分区和 ESP-IDF 原生 bootloader 回滚机制。新应用启动后执行有界的本地关键健康检查：关键驱动及固件初始化成功、配置迁移仍可回退、管理员管理服务可启动；不依赖云端、互联网或非关键功能。检查通过后立即确认新应用，失败则使用原生拒绝/回滚流程。立即确认可避免非关键功能故障扩大成整机回滚；本地检查则使长期离线设备仍能完成更新验收。应用负责 NVS/配置格式的版本化迁移；健康确认前须保留旧固件可读取的配置，并使用可回退/暂存迁移。A/B 分区只回滚固件，不自动回滚 NVS 或其他应用数据，因此组件不承诺备份/还原应用配置。
- 映像校验完成后，任务进入最多 10 分钟的待安装确认期限；期间断开浏览器连接不触发自动安装，重新登录后可查询并继续明确确认。期限到达后释放 OTA 会话锁、记录 `timed_out`，候选映像不得成为启动目标；再次更新须重新上传。上传开始前管理员会话失效/撤销时，立即将任务记为 `cancelled`、清除该会话的 `request_id` 绑定并释放互斥；上传期间会话失效或连接空闲超时则中止并终结任务。完整收到与预期完全一致的字节数后，上传请求返回 `202 Accepted` 并进入异步 `validating` 阶段；长度不符、传输中断或分区写失败时任务记为 `failed`，不允许续传，也不切换启动分区。断连/取消/设备重启均不支持断点续传，新的上传从头开始。未确认的映像不切换启动分区，当前有效固件继续运行。仅设上传空闲超时而不设总上传时限，以兼容慢速移动端；具体空闲时长按最慢受支持网络和目标板测试确定。不持久化逐块进度，以减少闪存写入。OTA 插件 Kconfig 默认关闭，产品显式启用；可由构建确定的必要项缺失时硬性失败，运行时分区缺失或容量无效时明确禁用 OTA 并返回稳定配置错误，但不阻断其他管理功能。不能在构建期证明的设备熔丝状态和量产行为须明确标记未验证，不得宣称生产 OTA 支持。组件不提供接受未签名映像的 OTA 旁路；开发调试通过串口或调试工具刷写。
- OTA 状态由专用任务记录表示，不复用仅驻留 RAM 的通用 Operation，以便跨设备重启查询健康确认或回滚结果。状态接口使用单一稳定 `status` 标识阶段：`receiving`、`validating`、`awaiting_install_confirmation`、`setting_boot_partition`、`rebooting`、`health_check`；终态为 `succeeded`、`failed`、`rolled_back`、`cancelled` 或 `timed_out`。接收阶段报告 `received_bytes` 和 `total_bytes`；创建阶段要求已知预期长度并使用匹配的 `Content-Length`，不接受未知长度请求。其他阶段只报告阶段，不提供虚构的百分比。状态响应包含 `task_id` 和 `status`；完成映像检查后提供设备解析的 `app_version`、目标兼容结果、`image_size` 和 `integrity_status`，只有全部适用检查完成后才标记 `verified`，签名最终验证所在阶段须如实表达。失败终态才附稳定错误码、失败阶段和安全用户消息；时间仅在 UTC 可信时附带可信标记。只持久化阶段变化和终态，不持久化每个分块的字节进度；设备只保留当前任务及最近一次终态结果。任务 ID 使用不可猜测的短期标识，但不承担认证授权；未知或已过期 ID 明确返回未知/过期，不回退展示其他任务。
- 重启后须依据实际运行分区和 ESP-IDF OTA/bootloader 状态校正任务记录：新映像启动后进入 `health_check`；旧映像因回滚启动时记录 `rolled_back`；在接收、校验或待安装确认阶段重启时记录 `failed`/中断错误，释放互斥且不自动续传或安装。状态持久化与分区切换之间可能发生掉电，因此恢复逻辑不得只信任应用记录。状态查询为受管理员会话保护的只读 `GET`，不改变状态且不延长会话空闲期限，避免后台轮询悄悄维持登录；活动阶段浏览器约每秒轮询，设备重启断连时按 1、2、4、8 秒退避，超过重试后只提示设备暂时不可达，不把网络中断判作 OTA 失败。时间字段仅在 UTC 可信时提供，并明确标记可信度。
- 对已知任务，即使任务终态为失败也返回正常状态文档；接口级认证、授权、参数和未知任务错误单独响应并提供稳定机器码。OTA 对外错误码由组件定义，映射 ESP-IDF 错误，不直接透出原始 `esp_err_t` 或内部枚举；错误类别按可采取的恢复动作区分，包括上传过大/中断、映像或签名校验失败、目标不兼容、应用版本降级、安全版本下限拒绝、维护忙碌/资源不足、确认超时/取消、启动分区切换失败及健康检查失败/回滚。目标 API 无法可靠区分时使用较宽泛的校验失败码。失败结果保留候选版本、失败阶段、稳定错误码和安全用户消息；仅保留最近一次 OTA 结果，时间仅在可信时记录。原始底层诊断不进入浏览器响应，需要时仅作设备本地受限诊断。这样使客户端协议不依赖 IDF 内部错误实现，并避免暴露堆栈、凭据或内部状态。
- 最终安装确认及取消均按任务当前状态处理重复请求：确认只在 `awaiting_install_confirmation` 且会话有效时接受；先持久化 `setting_boot_partition`，再设置启动分区并重启，以便在掉电后与实际 OTA 状态对账。响应丢失后的重复确认只返回当前任务状态，不重复切换或重启。取消只允许在安装确认前执行，重复取消返回现态；进入 `setting_boot_partition` 后拒绝取消。设置新启动分区成功后先返回明确的重启响应，再立即重启；浏览器跟踪设备重连，仅在新固件通过健康检查后报成功，回滚时显示最近失败结果。所有改变状态的请求仍执行 CSRF token 和精确 Origin 校验。
- 同一设备最多允许一个 OTA 任务。组件提供设备级维护互斥，OTA 与其他固件/资源分区升级或恢复操作共用；应用可通过公共 acquire/release API 将大规模 Flash 维护操作纳入同一互斥。锁冲突时以稳定 `busy` 错误立即拒绝，不排队、不抢占。普通管理操作和短小 NVS 配置写入不默认阻塞。这样将资源限制在高风险维护操作，而不使设备管理面整体不可用；API 的句柄、所有权和重复调用规则留待接口设计确定。
- 固件签名信任与设备 HTTPS 证书/CA 分离。ESP-IDF 支持的固件签名私钥由受控发布环境管理，不嵌入设备/固件，也不复制到普通应用构建产物；设备依据对应目标的原生 Secure Boot/签名验证机制校验映像。ESP-IDF v6.1 [Secure Boot v2 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/security/secure-boot-v2.html)说明该方案的签名私钥保留在设备外，设备侧保存公钥摘要；例如该文档描述的经典 ESP32 v3.0 方案在芯片上仅保存一个公钥。因此该说明用于厘清私钥角色并展示目标差异，不能当作全系列能力保证。
- 量产前建立逐目标/修订版能力矩阵，核实 ESP-IDF v6.1 的镜像签名验证、A/B 回滚、反降级、安全版本提升及签名密钥更新/吊销能力。首版仅使用 ESP-IDF/芯片原生支持，不自行增加第二套应用层签名协议；若目标原生机制不支持安全密钥轮换，明确记录产品风险并采用工厂、授权维修或 RMA 恢复路径，不承诺通用的设备端自动换钥。仅在目标能力验证通过后，才能承诺该目标的生产 OTA 安全能力。

#### Web 请求防护

- 对请求体、固件分块、并发连接、JSON 深度和字段长度实施上限。
- 防范 CSRF；所有改变状态的 HTTP 请求要求 CSRF token 和精确 Origin，WebSocket 握手校验精确 Origin；所有 RPC 和文件操作均执行认证/授权，不能仅依赖浏览器同源假设。
- 配置适当的 HTTP 安全响应头。WebUI 使用限制性 CSP，默认禁止 `eval` 和内联脚本，不加载第三方 CDN 脚本；所需资源随固件本地提供，例外须经评审，以减少脚本注入和第三方供应链风险。
- 认证响应和敏感配置响应设置 `Cache-Control: no-store`；管理凭据、会话/CSRF token 和敏感配置不写入 URL、`localStorage` 或 `sessionStorage`，降低共享设备残留和会话泄露风险。版本化静态资源可采用独立缓存策略。
- 对输入进行结构、范围和长度校验；错误响应不得泄露敏感信息。

#### 本地安全审计

- 设备保留有界持久化安全事件日志，供认证管理员查看/导出；至少覆盖初始化、登录结果、密码修改、会话撤销、恢复出厂和证书轮换/恢复。已认证事件统一归因于单一“管理员”身份，未成功认证的登录记录为未认证尝试；不提供访客身份或个人级操作者区分。不得记录密码、恢复码、Cookie/CSRF token、Wi-Fi 凭据或客户端 IP。
- 设备时钟可信时记录 UTC；时间不可信时记录启动标识、单调运行时间并标记 `time_valid=false`，不把未校准时间当作准确 UTC。
- 日志容量满时覆盖最旧记录并保留丢弃计数；重复高频事件限频或聚合，避免每次失败都立即写闪存。恢复出厂清除全部旧审计记录，避免设备转手泄露前任用户操作历史；复位完成事件可写入新日志，不保留任何前任记录。
- 日志大小、保留行为、写入节流和掉电一致性须结合目标闪存预算与实机测试确定。

## 6. 配置与技术选型

### 6.1 已明确方向

1. ESP-IDF v6.1。
2. 目标为具备 Wi-Fi 或以太网接口的乐鑫芯片，具体兼容性受硬件和 ESP-IDF 支持范围约束。
3. 前端采用 Vue 3、Svelte 或其他可生成静态资源的技术；组件和应用可分别提供编译期嵌入的默认资源，Flash 文件系统资源可在运行时覆盖。
4. 控制/配置使用 JSON-RPC 2.0 单条消息，可经 HTTP 或 WebSocket 承载；WebSocket 默认承担双向实时通知。
5. 首版不支持 JSON-RPC Batch 数组或 SSE；只有出现明确需求或性能证据时才重新评估。
6. OTA 固件和大型配置文件与 JSON-RPC 控制面分离，使用有界的原生 HTTP 流式上传/下载。
7. OTA 首版通过本地 HTTPS 专用任务接口上传原始固件流，设备无需联网；采用两阶段校验/安装确认、非活动分区、目标原生 A/B 回滚与固件签名校验，插件默认关闭并由产品显式启用。
8. 后端通过 Kconfig 选择编译功能，例如 OTA、Wi-Fi 配网等。
9. 核心组件避免依赖特定业务协议或前端框架。

OTA 版本与制品规则：

- 应用版本采用严格三段非负十进制 SemVer（`MAJOR.MINOR.PATCH`）；除单独的 `0` 外，不允许前导零，正式版本不带 prerelease 或 build metadata。构建/CI 校验 `PROJECT_VER` 格式、各字段长度及镜像版本元数据一致性；数值比较必须避免整数溢出。严格格式可避免排序歧义，构建期校验则防止错误版本进入发布制品。
- 若设备当前固件版本不是有效的上述 SemVer，OTA 拒绝更新并返回稳定错误码 `current_version_unrecognized`；用户须先通过串口或受控维修流程刷入有效 SemVer 基线。拒绝而非猜测或放宽解析规则，可避免旧版本格式导致错误的升级/降级判断。
- 签名制品的不可变标识由产品、target/revision 范围、构建配置和 SemVer 共同确定；发布/CI 登记对应签名制品摘要，同一标识出现不同摘要时拒绝发布。设备不再实现第二套摘要协议，以发布侧一致性约束保证版本可追溯，避免增加设备端协议和状态复杂度。
- OTA 大小上限由产品按 target/revision 构建配置一个有限的 Kconfig 值，实际生效上限取该值与非活动分区容量的较小者；按完整签名制品的原始字节数计量。若目标分区无法容纳产品承诺的最大制品，CI/发布验收失败并重新评估该目标或产品上限，避免容量不足被误当作运行时异常。
- 上传空闲超时使用有限的产品 Kconfig 值，并以最大映像、最慢受支持网络的多轮实测确定；测试覆盖慢速传输、网络抖动、Flash 写入背压和断连。候选值至少为 P99 最大正常停顿间隔的两倍。仅实际固件字节进展重置空闲计时；持续有进展时不另设总上传时限，以兼顾慢速网络并及时回收停滞任务。
- 映像兼容性优先依赖 ESP-IDF/目标原生检查；产品可选板级兼容性回调只补充原生检查未覆盖的板级差异。回调只读解析映像元数据，须短时、非阻塞，不得联网或写 Flash；回调失败即拒绝，且不得覆盖原生检查的拒绝结果。这样保留目标原生安全边界，同时允许产品表达板级约束而不在通用组件中硬编码。

OTA 支持等级按每个 target/revision 分别标记：

- **构建兼容**：组件可为该 target 构建；不代表 OTA 已通过运行时或硬件验证。
- **OTA 验证中**：该 target/revision 的 OTA 实机验证尚未完成；不得据此作生产 OTA 支持声明。
- **生产 OTA 支持**：该 target/revision 的适用 OTA 验收已完成；只有此等级可用于生产支持声明。分级可明确区分“能编译”“正在验证”和“已验证可用于生产”，避免把构建成功误报为 OTA 能力承诺。
- 生产 OTA 支持绑定到明确的产品生产构建配置；生产声明不可从同一 target/revision 的其他构建配置推定。可能影响升级、签名/映像校验或启动/回滚行为的配置变化须重新执行适用验收；与这些行为无关的界面变化不要求重跑 OTA 验收。这样既避免错误泛化测试结果，也不因无关改动重复完整测试。
- 每个 target/revision 进入“生产 OTA 支持”前，须在对应生产配置下留存硬件验收记录，至少覆盖：有效签名映像升级并健康启动；签名无效或产品/硬件不匹配映像被拒绝；失败回滚或掉电恢复；配置的映像大小和上传超时边界。只有全部适用项目通过，才可作生产支持声明，以免单次成功升级掩盖拒绝、恢复或资源边界缺陷。
- 每个正式发布版本须在每个适用的已支持生产配置上至少实测一次升级成功并正常启动；OTA 代码或可能影响升级、签名/映像校验或启动/回滚行为的配置变化时，须重跑完整适用 OTA 验收。这样可确认每次交付的基本升级可用性，并将完整故障/边界测试集中在风险实质变化时执行。
- 每款产品须为每个正式版本明确列出允许直接迁移的数据格式版本；只有对应迁移测试通过的格式才能列入，并随该版本发布说明公布。这样兼容范围代表经过验证的能力，而非未经测试的承诺，也避免无限期维护所有历史格式。
- 允许从受支持的数据版本直接升级到最新版本，但新固件必须安全识别并迁移该版本的数据。未列入该版本支持名单的数据格式须拒绝直接升级；只有经过实际验证的中间固件升级路径才能作为替代方案公布，没有已验证路径时提示用户联系受控维修。这样免除逐版升级的普遍要求，同时不引导用户尝试未经验证的升级顺序。
- 数据迁移失败时必须保留升级前的原始配置，不得将部分迁移结果当作有效新配置；新固件不得完成健康确认，须触发旧固件回滚。这样避免迁移中途失败造成配置丢失，并保留旧固件可用的数据状态。
- 映像必须匹配预期产品型号和适用硬件版本，不得只以 SoC/target 匹配作为充分条件；不匹配时拒绝安装。不同产品可能共用芯片但有不同板级外设或配置，精确匹配可避免安装“芯片可运行但硬件不适用”的固件。
- “OTA 验证中”的 target/revision 可在明确标记的测试构建中启用 OTA，以支持开发和验收；正式产品构建仅允许启用已达到“生产 OTA 支持”的配置。构建边界保留验证能力，同时防止未验收 OTA 能力进入产品发布。
- 仓库维护[OTA 支持矩阵](./esp-cockpit-ota-support-matrix.md)，记录 target/revision、产品生产配置、支持等级及详细验收证据位置；完整报告和测试日志作为相应正式发布的附件保存。矩阵便于审核和维护支持声明，详细记录留在发布附件可避免源码仓库膨胀并保留可追溯证据。
- 验收未通过的候选固件不得按该配置发布。若完整验收发现升级、签名/映像校验或回滚能力回归，受影响生产配置的 OTA 等级暂时退回“OTA 验证中”；修复并通过完整验收后才恢复“生产 OTA 支持”。支持矩阵保留最后一个已知可用的正式版本和验收记录，避免把失败候选误作可发布版本，也不丢失历史可用性依据。

### 6.2 待评估事项

**网络服务与协议**

- ESP-IDF `httpd` 对 HTTP JSON-RPC、WebSocket 及原生流式接口的支持、并发资源和各目标芯片兼容性。
- JSON-RPC over HTTP 与 WebSocket 的最终方法名/参数、HTTP 状态码映射、错误码、Schema 分页及大结果集传输方式；单条消息、无 Batch、无 SSE 已确定。
- JSON 解析库选择：比较 cJSON、jsmn 等方案的内存占用、校验能力和维护成本。
- 是否需要二进制 RPC 编码仅在目标板实测证明 JSON 是关键瓶颈后再评估；若评估 CBOR，需作为独立协议候选并定义兼容边界，不应假设它是 JSON-RPC 2.0 的直接替代编码。
- 逐目标核验 ESP-IDF v6.1 原生 OTA/安全启动、签名验证、A/B 回滚、反降级及密钥更新能力；分区表、Kconfig、版本提升顺序和签名密钥轮换策略不得跨 SoC 推定。

**网络安全与凭据**

- 确认 TLS 后端、证书格式/算法、握手与连接资源预算，以及 HTTPS/WSS 服务在证书缺失、无效或更新失败时的明确失败行为。
- **组件首版验收**：用测试身份验证 HTTPS/WSS TLS 和无明文降级、应用提供的初始设备身份装载、设备本地私钥/CSR 生成与导出、签发证书导入及匹配/SAN/用途/有效期校验、失败不切换和原子更新回滚；同时验证认证、会话、CSRF/Origin、限速及资源边界。无需依赖真实厂商 CA、签发门户或恢复服务即可完成组件独立验收。
- **产品试产/发布验收**：产品厂商负责 CA 和证书签发/授权、根证书 HTTPS 分发、设置指南及签发/恢复门户；制造商负责 factory ID 分配与身份绑定、包装/设备标签二维码、设备地址和根指纹的生成及出厂核对；厂商负责恢复码核验、服务连续性、授权服务点/RMA。试产验证端到端责任链、数据对应关系和服务可用性；这些运营能力是采用该 PKI 方案的产品发布条件，不是组件单测或组件独立交付的前置依赖。
- 在 Windows、macOS、iOS/iPadOS、Android 上验证根证书安装后的主流浏览器信任行为，并提供逐平台指引；无法可靠建立信任的平台/浏览器组合不得列入正式支持，不得以忽略证书警告替代。
- 首版网络验收使用外部网络模式：由示例应用建立/管理网络并报告网络就绪状态；确认 ESP-Cockpit 不读取或修改应用网络凭据、接口或 IP 配置。
- 若产品应用或后续可选插件提供 SoftAP 配网，验证物理触发、设备唯一密码、标签/二维码交付、限时关闭和仅初始联网配置的门户；定义用户转手/忘记密码时的物理恢复出厂交互及防误触措施。
- 验证物理触发的 10 分钟管理员初始化窗口、单客户端原子完成、超时/完成后关闭，以及窗口内局域网抢先初始化的风险提示。
- 验证单管理员无用户名产品约束、无只读访客/角色、多个并发会话及审计统一归因规则；并验证 Secure/HttpOnly/SameSite Cookie、30 分钟空闲/24 小时绝对超时、用户活动续期、设备重启撤销全部会话、凭据变更撤销以及 WebSocket Cookie 鉴权/立即关闭。
- 验证 CSRF token 与精确 Origin、HTTP `GET` 无副作用、限制性 CSP、无第三方 CDN、敏感响应 `no-store`、Web Storage 禁止存储敏感值，以及支持密码管理器自动填充/粘贴。
- 在 ESP32-S31-Function-CoreBoard-1 的生产 PSRAM 配置上基准比较 Argon2id 与可选标准密码 KDF 的验证延迟、峰值 RAM 和并发行为；确定随机盐、版本化参数格式及升级策略，不实现自定义密码哈希算法。
- 验证密码修改必须校验当前密码，成功后撤销全部会话并要求重新登录；确认过期/撤销 Cookie 和现存 WebSocket 均不能继续访问。
- 在候选 KDF 基准结果基础上确定认证前限速、渐进延迟、全局并发/队列上限及拒绝行为；通过攻击负载和正常误输测试验证不永久全局锁定，且登录失败不能耗尽设备资源。
- 验证管理员密码 12–128 字节 ASCII、首尾 ASCII 空格 trim、控制字符拒绝、不截断及创建/登录一致性；测试固件内置常见弱密码和产品通用默认词条拒绝列表。验证上述哈希/KDF 参数满足目标芯片 RAM、延迟和安全预算。
- 验证有界持久化安全审计、敏感字段排除、可信/不可信时钟标记、日志满覆盖与丢弃计数、高频事件聚合，以及恢复出厂清除旧日志。
- 建立各 ESP-IDF v6.1 target/revision 的 OTA 安全能力矩阵，验证本地 HTTPS 上传、签名和目标检查、A/B 分区、启动回滚、健康确认与反降级顺序；确认签名私钥只存在受控发布环境、且与 HTTPS CA 分离。
- 验证 OTA 严格 SemVer 解析、数值段比较、低版本拒绝、同版本确认后重装及版本号与不可变制品的对应；验证应用版本比较与 `secure_version` 反降级相互独立。
- 验证两阶段上传/安装确认、每项本地健康检查、通过后立即确认、失败回滚以及配置迁移在健康确认前可回退；检查不得依赖云端或互联网。
- 验证中断/掉电时当前固件仍可启动、未确认映像不会被选中；按 ESP-IDF 实际 OTA 状态恢复跨重启任务，检查阶段/终态持久化、失败回滚与最近结果查询。
- 验证任务接口会话/CSRF/Origin/`no-store` 行为、任务 ID 不授权、会话失效处理、确认/取消重复请求、10 分钟确认超时和未知任务响应；轮询不续期会话且重启断连不误判为任务失败。
- 验证创建任务 2 分钟未开始上传时超时释放互斥；`request_id` 在同会话重试返回同一任务，不同创建请求返回 `busy`；只接受 `expected_bytes`，且 `Content-Length` 与实际接收字节数完全匹配。
- 验证目标分区与配置大小双重限制、接收期间实际字节数校验、空闲超时、有界资源使用及设备级维护互斥；冲突操作须返回稳定 `busy`，不得排队或抢占。
- 验证 OTA Kconfig 默认关闭；缺少构建期必要条件时构建失败，运行时分区无效只禁用 OTA；OTA 不提供未签名映像旁路。
- 对原生不支持安全密钥轮换的目标记录工厂/授权维修/RMA 恢复流程及生产 OTA 支持边界。
- 验证组件首版证书 API：应用/工厂提供初始身份；组件本地生成私钥和 CSR，私钥不可导出；证书导入校验公钥匹配、SAN/设备身份、TLS server authentication 用途和有效期，失败时保留旧证书，成功时原子切换。验证密钥存储/provider 适配及各目标的密钥保护能力。
- 产品试产/发布验证制造商 factory ID 唯一分配、工厂身份绑定、厂商证书签发、工厂证书安装、根证书分发、标签地址/指纹准确对应；若产品提供 SoftAP 配网，再验证其凭据绑定。验证厂商恢复门户、恢复码/账户核验、授权服务点和 RMA 责任链。
- 组件首版验证证书有效期处理、CSR 文件往返、签发证书匹配校验、原子切换及失败回滚；产品试产另验证 CA 授权策略和远程/现场恢复运营。证书有效期、到期告警、可信时间来源及芯片保护能力的具体值/边界仍须按目标板确定。
- 由产品厂商运营一次性恢复码、购买账户/订单核验、签发授权、限速、审计/通知及服务连续性；定义恢复码生成/交付和服务端摘要存储细节，并在产品试产/发布验收中验证成功后作废及遗失后的授权服务点/RMA流程。组件只提供规定的本地身份恢复导入/导出机制，不实现上述远程授权业务。
- 验证物理触发、独立密码保护、限时 SoftAP 恢复窗口及仅文件导入/导出的 HTTP 端点；确认恢复通道不暴露普通管理/RPC，且不会收集远程恢复凭据。
- 产品厂商负责 ESP-Cockpit 专用根 CA、中间 CA 及签发/恢复门户的运营；产品试产/发布验收定义并验证离线保护、设备用途限制、签发审计、中间 CA 轮换、新旧根迁移和根密钥泄露/算法淘汰时的应急流程。
- 定义出站 TLS 客户端的信任库、服务器证书链/主机名校验及可选用户 CA 配置；其生命周期与入站证书配置分离。
- 验证首版首次使用流程：应用负责网络接入，用户先核验并安装厂商根证书，再通过标签中的稳定地址访问 HTTPS/WSS，并以物理触发开启的 10 分钟窗口初始化管理员；常规管理服务不得因网络或证书错误降级为明文。
- 若产品应用或后续可选插件提供 SoftAP 配网，验证其受限明文 HTTP 例外、物理触发/限时边界、隔离方式、仅允许的初始联网操作和关闭条件。
- 由产品合规评估方确认 RED/EN 18031-1 的适用性、适用版本及符合性评估路径；本需求文档的 TLS-first 设计不构成标准符合性结论。

**文件系统与前端资源**

- 文件系统选择：SPIFFS 与 LittleFS 的可用性、空间需求、资源包打包/校验、写入及升级方式。
- 单一 gzip 前端资源包的内部内容组织（建议自包含单页 HTML）、HTTP `Content-Encoding`/浏览器解压方式，以及缓存、更新和内存行为。
- 固件内嵌前端资源的构建集成方式（建议应用通过构建配置提供资源路径，构建时检查资源存在并替换组件默认资源，不要求修改组件源码）、Flash 文件系统 gzip 资源包校验方式，以及与后端 RPC/API 的版本兼容检查和浏览器缓存失效策略。

**持久化**

- 若未来实现独立可选的持久化辅助模块，需再确定 `persist_id` 约束、写回节流、立即写入范围及批量一致性；当前通用 Schema 的持久化和迁移由应用负责。

**芯片兼容性**

- ESP-IDF v6.1 官方 target 名称核验，以及“原生以太网”是否允许 MAC 外接 PHY 的定义。

### 6.3 配置持久化与写入语义

- 第 4.3 节通用 Schema 属性的持久化和迁移由应用负责；组件不根据 Schema 自动写 NVS。Write 成功表示应用状态已接受，不隐含持久化；同步持久化的成功/失败须遵守应用声明的持久性承诺，延迟写回须以 Applied/Pending/Persisted/Failed 等可读状态呈现，掉电可丢失待写值。这样避免核心注册 API 与应用配置格式绑定，并让应用控制持久化策略、迁移和闪存写入节流。
- 若未来增加独立可选的持久化辅助模块，需由应用显式启用并标记持久化属性；参数显示名称、JSON/RPC 路径和持久化身份应分离，UI 名称或 RPC 路径变化不得改变持久化身份。
- 此类未来辅助模块应使用稳定且唯一的短 `persist_id`，符合 ESP-IDF NVS key 限制（最多 15 个字符）；不得截断长名称或只用 CRC32 自动生成 key，碰撞检查不得省略。任意长 ID/动态映射须另行设计版本化映射、碰撞处理、损坏恢复和迁移语义。
- 若实施持久化辅助模块，应定义 `volatile`、`debounced`、`immediate` 等策略、Applied/Pending/Persisted/错误状态、受控任务上下文写回和掉电语义；默认逐项报告，不承诺多参数全有或全无。该模块及具体策略不属于当前通用 Schema 的既定行为。

### 6.4 前端资源与固件版本一致性

- 组件默认前端静态资源随组件编译并链接进固件；应用可以提供自己的编译期默认前端资源，构建时由应用资源替换组件默认资源。应用编译资源是文件系统资源不可用时的产品级保底前端。
- 建议在构建期选择应用前端或组件默认前端，避免将两份编译期资源同时打入固件；应用应通过受支持的 CMake 构建配置或 Kconfig 选项提供自定义资源，不应修改组件源码。具体注入机制待确定，且构建时应检查指定资源存在和可读。
- Flash 文件系统可存放独立于固件、运行时可更新的前端资源；资源包为单一 gzip 压缩文件。运行时优先级为：**可读取并成功解压的 Flash 文件系统前端 > 应用编译前端 > 组件编译前端**。
- 文件系统前端存在时，运行时尝试使用该资源；文件读取、gzip 解压、校验或兼容性检查失败时，回退到固件内嵌前端（应用资源优先于组件资源），并记录/显示可读诊断。文件系统资源不存在时，直接使用固件内嵌前端。
- 建议将 Web 前端构建为自包含的单页 HTML，再生成一个 gzip 文件，避免多文件前端更新不完整或文件版本不一致；HTTP 服务应设置正确的 MIME 类型和 `Content-Encoding: gzip`，由浏览器解压。需在目标芯片上验证传输、缓存及解压行为。
- 文件系统资源加载应能在 HTTP 响应头发送前确认资源可读且 gzip 流有效；若采用边读边发送，则响应开始后发生的 I/O/解压错误无法替换为固件内嵌资源，因此需选择有界的预验证/缓存策略，避免为支持回退而无界占用 RAM。
- 建议更新流程为：接收至临时文件 → 检查长度/边界并验证 gzip 完整性 → 执行资源完整性及版本检查 → 原子替换正式资源。任一步骤失败应保留旧资源；具体文件系统是否支持所需原子操作须验证。
- gzip 自带 CRC 可辅助发现压缩数据损坏，但不证明发布来源可信。可采用 SHA-256 做完整性核验；若威胁模型要求防止恶意替换，还需数字签名或等效真实性验证。算法、密钥管理和是否强制签名仍待安全设计决定。
- 需要定义前端资源包内容组织、存在性判定、兼容性策略、单文件 Flash 更新原子性、升级失败恢复及浏览器缓存失效策略。前端资源以单一文件打包，避免运行时出现多文件资源不一致。若回退的固件内嵌前端仍与后端协议主版本不兼容，WebUI 进入只读诊断状态，显示版本/能力信息和刷新或恢复受支持固件的指引，并禁止 Write、Invoke 等状态变更操作；不得静默降级或尝试未知接口。
- 应定义前端与后端的协议/能力版本协商，并考虑浏览器缓存失效、单文件资源的原子更新、外部文件系统升级失败及固件回滚后的兼容性。
- 前端构建资源的注入机制、版本标识及校验方式应由组件构建配置或应用接口明确；不能仅依赖文件路径存在来判定资源兼容。

## 7. 兼容性验证与测试范围

完整测试框架和全目标自动化实机 CI 暂不纳入首版；首版仍须提供可重复的构建检查及核心单元/协议测试 CI，并完成本节最低兼容性验收。组件维护者负责 CI、跨目标构建、单元/协议/安全测试及仓库支持矩阵；产品集成/硬件责任方负责对应生产配置的实机验收和证据；发布负责人按矩阵检查等级与证据，缺少必需证据时不得按该支持等级发布。

- 单元测试：Unity / CMock。
- 集成测试和系统测试：包括 pytest-embedded。
- 测试环境：Host/Linux、模拟器或 QEMU（按目标支持情况）、实际硬件。
- 辅助机制：Mock、日志及逻辑分析仪 / sigrok-cli。
- 前端构建与 ESP-IDF 构建的自动化集成；应避免污染应用顶层工程的构建配置。

### 7.1 必需的兼容性验收

- **所有支持配置**：支持声明绑定精确配置，至少记录 SoC target/revision、模组/板卡、PSRAM 配置、网络接口/驱动、ESP-IDF 精确版本、TLS 后端、安全构建选项、组件/固件版本和 commit。未测试配置不从同 target 外推。仓库[组件支持矩阵](./esp-cockpit-support-matrix.md)记录配置、验证等级和证据引用；完整日志、报告及其他大体积证据作为不可变发布附件归档。
- **首版目标配置**：确认 `esp32s31` IDF Target 映射，并以 ESP-IDF v6.1 对指定板卡的 Wi-Fi、Ethernet 两种生产配置分别完成组件构建。ESP32-S31 的 v6.1 target 支持已由用户确认；实际构建仍须留证。
- **核心功能验证**：在指定板卡的 Wi-Fi 与 Ethernet 配置上分别实机验证基础 WebUI、HTTP JSON-RPC/WebSocket、应用扩展接入及首版安全防护。原生 HTTP 文件流在相应可选插件纳入交付后另行专项验收。
- **首版 WebUI 验收**：在支持矩阵列出的受维护稳定浏览器版本上验证根证书信任及核心流程，并记录精确系统/浏览器版本；验证核心流程的 WCAG 2.2 AA 目标，包括手动键盘、焦点、标签/错误关联、对比度及主流屏幕阅读器检查。
- **并发连接验证**：在指定板卡的 Wi-Fi 与 Ethernet 配置上分别实机验证 5 个短 HTTP 请求并发处理，同时维持 5 个 WebSocket 客户端连接；按 1.1.3 节的基线执行并记录结果。首版不提供 SSE。
- **后续 OTA 能力（非首版门槛）**：仅当后续产品版本选择启用 OTA 时，才按明确的产品生产配置逐目标/修订版执行以下生产 OTA 验收；此处约束不构成组件首版发布阻塞项。需验证 ESP-IDF v6.1 原生签名验证、A/B 分区布局、回滚、健康确认及反降级状态更新。ESP-IDF [OTA 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32/api-reference/system/ota.html)描述了启用回滚配置及应用确认/拒绝新映像的流程；该文档和 Secure Boot 文档均须结合具体 target/revision 核验，不能从一个芯片外推整个支持清单。
- **生产 OTA 支持证据**：对应生产配置须有硬件记录，覆盖有效签名映像升级并健康启动、无效签名及产品/硬件不匹配映像被拒绝、失败回滚或掉电恢复、映像大小和上传超时边界；全部适用项目通过后才可标记生产支持。
- **OTA 发布回归（启用 OTA 的产品版本适用）**：每个正式版本在每个适用的已支持生产配置上至少实测一次升级成功并正常启动；OTA 代码或可能影响升级、签名/映像校验或启动/回滚行为的配置变化时执行完整适用 OTA 验收。完整验收还应确认直接跨版本升级时的数据兼容；不兼容旧数据的升级必须明确拒绝，只能提供已验证的中间版本路径，否则提示受控维修。
- **OTA 数据迁移与失败恢复**：每个产品版本公布经迁移测试通过的可直接迁移数据格式名单；对名单内格式逐项验证迁移成功，对名单外格式验证拒绝及已验证的中间升级/受控维修提示。注入迁移失败，确认原始配置未被部分结果覆盖、新固件未完成健康确认且设备回滚到旧固件。
- **OTA 验收失败处置**：验证未通过的候选版本被阻止发布；若完整验收暴露生产 OTA 能力回归，则支持矩阵将受影响配置标为“OTA 验证中”，保留最后已知可用正式版本记录，并要求修复后通过完整验收才能恢复生产支持。
- **OTA 映像适配与构建边界**：验证产品型号和适用硬件版本匹配检查；未达到生产支持等级的配置只可在明确标记的测试构建中启用 OTA，正式产品构建不得启用未验收配置。
- **OTA 支持声明**：每个 target/revision 分别处于“构建兼容”“OTA 验证中”或“生产 OTA 支持”；生产支持绑定到已验收的产品生产配置，关键升级/签名/启动回滚配置变化后须重新验收。维护[仓库 OTA 支持矩阵](./esp-cockpit-ota-support-matrix.md)，记录 target/revision、产品配置、等级和详细证据位置；完整报告/日志作为相应正式发布附件保存。
- **OTA 容量与超时**：实测各产品 target/revision 的最大签名映像、非活动分区可用容量及最慢受支持网络停顿分布，确认有限 Kconfig 上限、分区容量约束和空闲超时裕量满足已定规则。
- **OTA 版本与制品**：构建/CI 验证严格 SemVer、`PROJECT_VER` 与镜像元数据一致性、字段长度和溢出安全比较；验证相同产品/target-revision 范围/构建配置/SemVer 只能发布同一签名制品摘要。
- **OTA 板级兼容**：验证产品可选回调只补充原生检查、对回调失败采取拒绝策略，且不能覆盖 ESP-IDF/目标原生拒绝。
- **首版生产支持门槛**：Wi-Fi、Ethernet 两条配置均须完成构建、核心功能、安全及 5+5 性能验收，并在[组件支持矩阵](./esp-cockpit-support-matrix.md)登记实际数值、结果和证据；未完成前只能称为候选目标配置。
- 测试结果应记录芯片/模组/板卡、target/revision、IDF 版本、构建配置、网络接口、PSRAM 配置、TLS/安全选项、组件与固件版本、commit、连接组合及测试结论。仓库保留支持矩阵摘要和证据位置；完整报告/日志归档为不可变发布附件。组件维护者、产品硬件方及发布负责人的职责按本节总则执行。

## 8. 待决事项与验证计划

以下事项仍需在接口和模块设计阶段确定，或在实现/目标板测试阶段验证；前文已确认的架构决策不再列为开放选择。

按主题分类的未决事项如下；具体协议和网络状态细节分别见对应设计补充文档。

### 芯片兼容与验收

- ESP32-S31（`esp32s31`）的 ESP-IDF v6.1 支持已由用户确认；指定板卡上的实际构建以及 Wi-Fi、Ethernet 集成仍待分别验证。
- p95/p99 延迟上限、每种接口配置的最低空闲内部 RAM/PSRAM 安全余量、资源 limits 的生产数值及 TLS/KDF 配置，须经目标板基线测试确定并登记。当前没有实测数值或验收结果；5+5 验收适用范围、负载、成功/拒绝标准已确定。

### 网络生命周期与接口

- 每个实例必须且只能选择托管 Wi-Fi 或外部网络模式；Kconfig 控制能力编译，实例配置选择模式。仍需确定 Kconfig 选项的具体名称/依赖，以及外部网络就绪状态 API 的具体参数（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。
- 首版每进程一个托管 Wi-Fi 实例、单个活动 ESP-Cockpit HTTP/WebSocket 服务及事件资源所有权约束已确定；需在实现阶段验证并发启动保护、HTTP 端口冲突错误传播和资源回滚（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。
- 外部网络模式下由应用/网络管理器明确选择监听接口、地址和范围，组件按显式配置绑定，不推断默认路由；网络失效时关闭服务及现有连接，恢复后重新 TLS 握手、认证、读取能力并重订阅。Captive Portal 探测适配不属于首版，仅在未来隔离 SoftAP 插件中按目标客户端矩阵验收。
- 如未来产品启用托管 Wi-Fi 配网插件，再细化其异步状态机、SoftAP 客户端断连恢复和状态查询；已确认的 ONLINE/SoftAP 关闭规则及过渡时长仍须按目标板与 UX 验证。此类插件不属于首版。
- 公共 API 的最终 C 类型/函数签名、外部网络就绪通知参数及插件禁用时错误码；实例在 `stop()` 完整结束后允许再次 `start()`（详见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)）。

### JSON-RPC、数据模型与扩展 API

- 组件与 WebUI/示例客户端并行实现前必须冻结最小互操作契约，范围见[JSON-RPC 协议契约](./esp-cockpit-json-rpc-contract.md)第 8 节；下列方法/字段/C API 等待决项均须在该门禁前完成，不可作为未定接口直接进入并行实现。
- JSON-RPC 方法名/参数、稳定错误码和 HTTP 状态码映射，以及公共 C 注册/回调 API。
- Schema 分页的剩余字段契约、游标失效错误、资源上限、版本兼容和读写状态码；不透明游标绑定 Cluster Schema 修订号已确定。
- 事件型可靠投递是否为未来需求；首版状态订阅合并语义及连接生命周期已确定。
- Operation 状态/进度字段、未知 ID 错误及容量和保留期数值；活动 Operation 不驱逐，容量压力下优先回收最旧终态，无可回收记录时拒绝新 Operation。
- JSON-RPC Batch 与 SSE 首版不支持；混合式 Matter-inspired 交互模型及 Endpoint/Cluster/Attribute/Command 标识规则已确定（详见[Matter 交互模型与 JSON-RPC 映射](./esp-cockpit-interaction-model.md)）。

### 认证、安全与信任边界

- Session Cookie 的具体生成/存储实现、CSRF token 机制、CSP 指令及浏览器兼容验收；单管理员、WebSocket Cookie 鉴权和会话失效即关连接已确定。
- 组件与 WebUI/示例客户端并行实现前，冻结最小互操作契约：核心 RPC/通知/错误码、HTTP 状态映射、认证与初始化流程、公共 C 注册/回调 API 及生命周期、协议版本与未知能力处理、资源上限字段名称/单位。资源上限数值待逐生产配置实测后填定。
- TLS 后端与 HTTPS/WSS 资源预算，以及目标芯片量产配置下的设备侧密钥生成和保护可行性。
- 主流桌面/移动平台的厂商根证书安装/信任行为、通用指南与设备二维码/标签指纹流程、工厂随机标识分配、mDNS 名称冲突处理、企业 DNS/PKI 配置及证书 SAN 匹配。
- Windows、macOS、iOS/iPadOS 和 Android 的浏览器信任安装验收矩阵及用户指南；无法可靠验证设备身份的平台/浏览器组合的正式支持排除规则。
- 首次使用端到端验收：由应用提供网络接入并报告就绪；用户先安装并核验根证书，再通过稳定 mDNS 名称打开 HTTPS/WSS，以物理触发的 10 分钟初始化窗口创建管理员；确认失败时无明文/IP 管理降级。
- 管理员初始化窗口、密码输入规则、会话 Cookie/超时/撤销、同源与 Origin/CSRF 防护、登录渐进延迟和全局限速的兼容性与阈值验收。
- 候选密码 KDF 在最低配置目标上的时间/RAM基准、带盐与参数版本化、当前密码再认证、改密后的全会话撤销，以及 KDF 前限速和全局验证并发/队列资源上限验收。
- 有界本地审计日志的容量、掉电一致性、闪存磨损与查询/导出体验。
- 物理恢复出厂和二手转让验收：未登录时可物理清除旧用户数据并重新配网；设备身份不变、旧会话/凭据失效，且不能读取旧配置或借此直接进入管理面。
- 证书有效期、到期告警提前量、设备时间可信度、设备证书吊销的离线限制与补偿控制；过期后仅保留受控物理身份恢复通道的原则已确定。
- 至少 15 年离线本地管理目标下的可信时间来源、CSR 文件往返轮换、旧密钥签名授权、原子安装和失败回滚。
- 旧身份私钥故障时的恢复码封装/摘要存储、原购买账户/订单核验、尝试限速/审计/通知、成功后撤销旧身份，以及本地物理触发 SoftAP 文件恢复通道和 RMA 备用流程。
- ESP-Cockpit 专用根 CA 的离线保护、中间 CA 常规轮换、签发用途限制/审计、重大事件下的根信任迁移由产品厂商负责；组件设备证书更新、企业证书配置接口的具体 C API、密钥存储/provider 接口和调用授权契约仍需在 API 设计中细化，更新失败回滚等安全语义已确定。
- 恢复出厂设置保留设备出厂身份而清除用户凭据/配置的具体实现与验收；设备替换、退役和疑似私钥泄露的处置流程。
- 出站 TLS 客户端的信任锚配置、主机名校验、可选 CA 生命周期与资源验收。
- 若产品应用或后续可选插件提供 SoftAP 配网，其物理触发/时间边界、允许操作、隔离及关闭条件；Captive Portal 探测适配不得引入常规明文管理接口。该能力不属于 ESP-Cockpit 首版范围。
- 组件核心安全验收用例，包括 TLS 证书链/身份与稳定名称匹配、错误证书拒绝、无明文降级、授权/限速、并发 TLS 资源、证书更新失败回滚及恢复出厂身份保留；产品试产/发布另验真实 PKI、工厂绑定、根信任建立、恢复及 RMA 责任链。受限配网窗口仅在产品应用或可选插件提供该能力时验收。
- RED/EN 18031-1 对本产品的适用性、采用标准版本及最终符合性评估结论，由产品合规评估流程确认。
- 参考[嵌入式设备免证书安全通信方案](../ref/嵌入式设备免证书安全通信方案.pdf)仅作为背景资料；其 Shelly 行为和安全结论需以一手资料核实，不作为规范。

#### 产品级信任与长期维护验收分级

信任生命周期分为组件首版门槛与产品试产/发布门槛，二者不得合并成一项“组件安全通过”。组件维护者负责实现并验证通用机制；产品厂商仍对量产 PKI、身份运营、平台支持和法规结论承担端到端责任。每项通过结论均须有责任人、精确配置/版本、测试日期、结果和不可变证据；没有证据即为未通过。

### 后续可选能力：OTA 与大文件传输

以下 OTA 详细设计不属于组件首版交付或发布门禁；仅在后续产品版本选择启用 OTA 时适用。

- HTTP OTA 已确定为组件内置、默认关闭且可由 Kconfig 显式启用的可选插件；首版采用本地 HTTPS 上传、非活动分区、A/B 回滚和完整映像校验，不支持断点续传或未签名 OTA 旁路。
- OTA 专用任务资源操作集合、创建/上传输入约束、request_id 去重及创建后 2 分钟上传启动期限已确定；设备级维护锁及供应用大规模 Flash 维护使用的公共 acquire/release API 已确定，最终 URL/字段、HTTP 错误映射及锁 API 签名/所有权规则仍待接口设计确定。
- 有限 Kconfig 上传大小和空闲超时的具体数值仍需按产品 target/revision 实测确定；上限取配置值与非活动分区容量的较小值，映像按完整签名制品原始字节计量，超时按实际字节进展重置且不限制持续进展的总时长，确定方法已明确。
- 严格 SemVer、无法识别当前版本时拒绝 OTA、不可变制品标识及发布侧摘要一致性、ESP-IDF 原生兼容检查与可选板级回调边界、每个 target/revision 的三级 OTA 支持等级均已确定；仍需验证各项实现及验收结果。
- 生产 OTA 支持绑定明确生产配置；可能影响升级、签名/映像校验或启动/回滚的代码/配置变化须重新执行完整适用验收，无关界面改动不触发全套 OTA 重验。每个正式版本在适用生产配置上实测一次成功升级并正常启动。
- 生产验收覆盖有效映像升级、无效签名及产品/硬件不匹配映像拒绝、回滚/掉电恢复及大小/超时边界；仅全部适用项目通过后才能标记生产支持。[仓库 OTA 支持矩阵](./esp-cockpit-ota-support-matrix.md)记录配置、等级及证据位置，完整报告/日志随正式发布保存。
- 产品须公布每个正式版本可直接迁移的数据格式名单，且仅列入迁移测试通过的格式。名单外版本拒绝直接升级；只提供经过验证的中间版本路径，没有已验证路径时提示受控维修。迁移失败须保留原始配置、不确认新固件并回滚旧固件。
- 验收失败的候选版本不得发布；完整验收发现能力回归时，受影响配置暂停生产 OTA 支持并退回“OTA 验证中”，保留最后已知可用版本记录，修复并通过完整验收后再恢复支持。
- 映像须匹配产品型号和适用硬件版本。未生产验收配置只允许在明确标记的测试构建启用 OTA，正式产品构建仅启用生产支持配置。
- 具体 IDF API/Kconfig/分区布局，以及逐目标反降级和签名密钥更新能力仍需设计、构建核验与实机验证。
- OTA 状态持久化的掉电一致性、设备时钟可信度来源、公共维护锁 API 的调用生命周期与应用自有 Flash 写操作验收，以及各稳定错误码的最终枚举/兼容策略仍需在实现设计和目标板验收中确定。
