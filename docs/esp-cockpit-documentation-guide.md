# ESP-Cockpit 文档地图与治理规则

本文是仓库文档导航和状态标记的唯一说明，不替代产品需求、协议规范或验收记录。文档状态描述其规范效力；“实现/验收状态”必须另由对应支持矩阵和证据说明。任何设计稿、规范稿都不因此代表代码已实现。

## 文档状态定义

| 状态 | 含义 | 可否作为实现依据 |
|---|---|---|
| 需求基线 | 对产品范围、要求或验收门槛作规范性约束；未决项须明确标为待决 | 可以；不得据此宣称已实现或已验收 |
| 冻结规范 | 规范性接口契约已冻结；兼容实现须遵守字段、语义、错误和版本规则 | 必须 |
| 补充规范 | 规范性细节补充；不得覆盖或改变对应冻结规范 | 可以；冲突时冻结规范优先 |
| 设计说明 | 解释架构、理由或候选方案；除非被明确晋升为需求/规范，不作为规范性要求 | 不可以单独作为 |
| 验收记录 | 登记特定配置的构建、测试结果、支持等级及证据；不定义协议或架构 | 只用于判定所记录配置的验证状态 |
| 治理规则 | 定义文档状态、职责划分和变更流程；不定义产品或接口行为 | 仅用于维护和审阅文档 |

状态不表示进度。“待验证”“未验收”应写在具体条目/矩阵中，不替代文档类型状态。证据不足时不得把候选配置、讨论结论或规范要求表述为已支持行为。

## 更新规则

1. 修改冻结互操作基线前，先记录变更理由、兼容影响和迁移方案；保持 JSON-RPC 主/次版本及 C API 主版本规则。破坏性变更不得仅在补充文档中发布。
2. 冻结规范变化时，在同一变更中更新所有受影响的专门规范、示例/测试和本文件导航；其他文档只保留简要摘要与权威链接，不复制字段表或完整规则。
3. 设计说明中的候选内容只有经评审并明确标为需求基线或规范后才生效。文档状态/权威范围变化须同步更新本地图和受影响文档的状态栏。
4. 验收矩阵只登记实际执行的数据、精确配置、版本、日期、结论和可复核证据。无测量或证据时写明未测/未验收，不填推测值。
5. 已发布规范应保留变更历史或关联的版本控制记录；文档间相互引用采用相对链接，避免重复维护同一规范内容。
