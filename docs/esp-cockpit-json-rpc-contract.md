# ESP-Cockpit JSON-RPC 协议契约

> 状态：规范性设计稿。本文定义 ESP-Cockpit 客户端与设备间的 JSON-RPC 契约边界；具体方法名、字段、错误码和数值资源上限仍按本文标注逐项细化后才能作为最终 API。

## 1. 协议定位与版本

- 消息协议必须符合 JSON-RPC 2.0，包括请求/响应信封、`id` 关联和 Notification 不带 `id` 等规则。首版所有客户端发往设备的方法调用都必须带非空字符串 `id`，并受有限的 UTF-8 字节长度上限约束；具体上限由目标资源测试确定。同一连接上所有尚未收到响应的请求必须使用不同 `id`，收到对应响应后可重用。选字符串是为避免浏览器数字精度导致关联标签被改写；`id` 只用于请求/响应关联，不提供去重或重试安全保证。不接受客户端发起的 Notification；设备向客户端推送的 Notification 不带 `id`。首版不接受 JSON-RPC Batch 数组；不支持 Batch 是采用的协议子集，不改变单条消息的 JSON-RPC 2.0 语义。
- 若客户端发送无 `id` 的方法消息，该消息按 Notification 处理：设备丢弃且不执行方法、不发送响应，并仅在设备本地记录诊断；连接保持可用。JSON-RPC Notification 没有响应关联 ID，按协议不能返回错误信封，因此客户端必须为所有方法调用提供 `id`。
- 若同一连接上收到与尚未完成请求重复的 `id`，设备不得执行第二个请求；应记录本地诊断并关闭该连接，避免无法区分的响应。此前已开始执行的回调仍按客户端断连规则处理。
- Read、Write、Invoke、Subscribe 的组织方式受 Matter Interaction Model 启发，但 ESP-Cockpit 使用自有路径、Schema 和 JSON-RPC over HTTP/WebSocket，不声明 Matter 语义合规或 Matter 协议互操作。
- JSON-RPC 线协议与公共 C API 分别版本化；不得用一个版本号代替另一者的兼容性。公共 C API 在同一主版本内保持源码兼容；不承诺跨 ESP-IDF、工具链或构建配置的预编译二进制 ABI。分开版本能使客户端和组件集成方独立判断升级影响；源码兼容符合组件随应用编译的使用方式。
- 能力发现必须公布 JSON-RPC 应用协议的主、次版本，并同时报告当前实例实际提供的方法、可选能力与有限资源上限。协议版本提供快速兼容判断，能力清单则反映插件和构建配置差异；不得仅凭版本号推定某个可选方法存在。
- 兼容扩展可在不破坏旧客户端的前提下增量加入；改变或移除已发布方法、字段含义或既有行为属于破坏性变更，须提升 JSON-RPC 应用协议主版本。新增响应字段应允许旧客户端忽略；服务端不得因此接受未知请求字段。

## 2. 方法组织与命名空间

- 核心交互采用通用的 Read、Write、Invoke 和 Subscribe；支持显式取消单个订阅，以及查询设备级长操作 Operation。通用交互使客户端可以复用一套路径处理逻辑，而不必为每个属性实现独立调用方式。
- 需要整体事务或专用长流程的能力可以使用具名 RPC；具名 RPC 与通用方法必须共用授权、校验和一致的业务语义，避免同一操作的权限或结果不一致。
- 组件核心方法及组件内置插件方法使用保留的 `esp_cockpit.*` 命名空间；应用业务方法必须处于应用自己的命名空间，不得占用该前缀。禁止隐式别名，以避免插件之间名称冲突和难以发现的路由差异。
- 组件方法使用全小写、点分层级命名；通用交互方法采用动词形式并位于 `esp_cockpit` 命名空间下，具体正式名称仍待 API 定义冻结。
- 能力发现方法名固定为 `esp_cockpit.capabilities.get`；分页 Schema 查询方法名固定为 `esp_cockpit.schema.list`。请求/响应字段和具体边界条件仍待细化。
- 每个 Invoke/Command 的机器可读描述必须声明其重试安全策略；客户端只有在明确识别为安全时才能提供重试。元数据缺失或无法理解时一律按不可安全重试处理，不得根据方法名或说明文字推断。
- 耗时 Invoke 可返回通用 Operation ID，客户端再通过统一的状态查询方法读取状态/进度；首版不提供通用 Operation 取消语义。统一查询减少每个长操作重复设计轮询协议的需要。
- 客户端超时或连接断开时，若 RPC 请求尚未开始执行，组件取消排队请求；若请求已开始，组件继续执行其中的应用回调（多路径请求继续处理剩余路径），但不再向已关闭连接发送响应。Read 可由客户端重新发起读取；Write 和 Invoke 的结果可能未知，客户端不得自动重试。若已取得 Operation ID，应先查询 Operation；只有命令明确声明可安全重试时，客户端才可提供 Invoke 重试选项，避免非幂等动作重复执行。
- 除已固定的能力发现和分页 Schema 查询方法名外，其他核心方法的正式名称、完整参数/结果字段和精确通知名称尚未确定；实现与客户端不得将本文中的逻辑分类或其他文档中的示例名称视为已冻结的线协议。

## 3. 参数、响应与兼容性

- JSON-RPC 方法只接受命名参数对象，不接受位置参数数组。命名参数便于按名称校验和扩展，也可避免参数顺序错误造成误操作。
- 服务端严格校验请求：未知或拼错的字段、类型不符及结构不符必须明确报错，不得静默忽略或截断。
- Invoke 方法声明每个参数为必填或可选；缺少必填参数时必须在调用处理器前拒绝。省略可选参数与显式传入 JSON `null` 必须区分，且不得因省略而自动应用 Schema 默认值。
- 多路径 Read/Write 请求不得重复包含同一路径；发现重复时必须在调用任何回调前拒绝整个请求，不得静默去重，以避免结果归属不明确或重复执行 Write。
- 多路径 Read/Write 按请求中的路径顺序逐项处理，响应中的逐项结果也按相同顺序排列。
- 多路径请求作为整体一次性通过队列准入并预留完整队列字节预算；准入失败时任何路径都不得执行。准入成功后仍按逐路径语义处理，业务失败可以部分成功，这不构成事务保证。
- 应用 RPC 回调按请求成功入队的先后顺序串行执行；同一多路径请求的所有路径处理完成后才处理下一请求。该顺序保证不构成多路径 Write 的原子性保证。
- Write 未包含的路径保持不变；显式 JSON `null` 仅在该路径的 Schema 明确允许时才是合法值，否则必须明确报错，不得把 `null` 当成省略值处理。
- 每个 Write 路径必须携带客户端最近从 Read 或 Subscribe 获得的该路径值版本。服务端须在应用写入时比较版本；版本已变化则拒绝该路径且不修改其值，并返回可识别的冲突错误。多路径 Write 仍逐路径处理，冲突路径失败不阻止其他路径成功。通用 WebUI 必须向用户说明冲突，不得自动读取新版本后重试并覆盖并发修改。
- 发生过期版本冲突时，通用 WebUI 应重新读取并展示该路径的当前设备值，同时保留用户尚未提交的草稿；用户核对后可明确选择以新版本重新提交。多路径 Write 仅重提冲突路径，不得重复提交已成功路径。
- 客户端处理响应时应忽略其不认识的新增字段，以允许服务端增加兼容信息而不破坏旧客户端。
- JSON-RPC 已定义的协议错误使用 JSON-RPC 2.0 标准错误码；组件和业务错误使用 ESP-Cockpit 定义的稳定机器码。组件核心错误与各应用命名空间必须分配不重叠的数值范围，各应用范围在应用版本间保持稳定，且不得占用 JSON-RPC 2.0 标准错误码。客户端按机器码分支处理，未知错误码按通用失败处理；用户可见消息仅用于展示且可以改进措辞。处理器未提供用户提示、提示不是合法 UTF-8 或超过提示字节上限时，组件生成通用提示并保留原错误码，不截断提示。不得将 ESP-IDF 或底层库错误码直接作为协议错误码，也不得向客户端泄露堆栈、凭据或内部状态。这样可在更换底层实现时保持客户端契约稳定。
- 首版应用业务错误只包含错误码和可选消息，不接受任意 JSON-RPC `error.data`；若未来需要结构化错误细节，必须另行定义稳定 Schema。
- 请求整体无法执行时使用 JSON-RPC 顶层 `error`；Read/Write 处理器的单路径失败位于对应逐项状态中，多路径调用允许其他路径部分成功；Invoke 处理器失败使用顶层 `error`。必须全有或全无的业务动作使用专用事务操作。
- Invoke 成功响应必须包含符合方法声明结果类型和约束的 `result`；若方法没有业务返回值，`result` 必须为 `null`，不得省略。

## 4. HTTP 与 WebSocket

- HTTP JSON-RPC 只使用 `POST` 和 `application/json`；`GET` 不承载 RPC 且不得改变状态。
- HTTP 状态码表示请求/传输层是否能够将请求交给 RPC 处理，例如认证失败、无效 HTTP 请求或预分发的整体资源拒绝。请求进入 JSON-RPC 处理后，无论成功还是协议/RPC 错误（包括解析错误、未知方法和无效参数），均使用 HTTP 200，并在 JSON-RPC 信封的 `result` 或 `error` 中表达。这样 HTTP 与 WebSocket 共用同一套 RPC 错误语义。
- WebSocket 建立后不再有逐消息 HTTP 状态码；每条 RPC 的业务成功或失败均使用 JSON-RPC `result` 或 `error`。
- Read、Write 和 Invoke 可通过 HTTP 或 WebSocket 承载；Subscribe/Unsubscribe 使用 WebSocket。单个订阅可独立取消，避免为停止一个订阅而关闭含有其他活动订阅的连接。
- 对格式有效但在当前连接上不存在或已结束的订阅 ID 调用 Unsubscribe 时，返回成功并作为 no-op；客户端可在响应丢失、重连清理或订阅已被设备终止后安全重试。无效的 ID 参数格式仍返回参数错误。
- 多路径 Subscribe 必须全有或全无：任一路径不可订阅或无法取得其初始值时，整体返回错误且不得创建部分订阅。持续推送的部分成功容易造成客户端误以为所有路径都受监控，也会增加订阅清理复杂度；该规则不改变多路径 Read/Write 的逐项结果语义。
- 单次多路径 Subscribe 中重复出现同一路径时，整个请求按无效参数拒绝且不得创建订阅；服务端不静默去重，以保持请求与结果的明确对应。该规则不影响不同 Subscribe 调用之间允许重叠路径并创建独立订阅。
- 同一 WebSocket 连接重复 Subscribe 相同路径时，每次成功调用都创建独立订阅 ID；重叠路径的更新按各自订阅 ID 分别推送，Unsubscribe 只取消指定 ID。独立订阅使每次调用都能单独管理和取消，避免共享订阅的引用计数及所有权歧义；重复订阅分别计入该连接和设备的订阅资源上限。
- Subscribe 成功响应必须包含订阅 ID，以及每个订阅路径的当前值和对应版本/序列号；每条路径的初始快照与开始观察更新之间必须有明确的衔接点，使变化要么包含在快照中，要么作为后续 Notification 推送，不得遗漏。服务端必须先发送成功响应，再发送该订阅的任何 Notification；响应发送前发生的更新须按序暂存，且受既定待发资源上限约束。这样客户端可先取得订阅 ID 和快照，再关联后续更新。多路径初始值不承诺跨路径原子快照。若初始快照超过资源上限，必须明确拒绝订阅，不得返回部分初始值并表现为成功。
- 服务端允许合并同一路径尚未发送的多个状态更新，只推送该路径的最新值和最新序列号，不保证交付每个中间值。订阅表达当前状态而非事件日志；合并可限制慢客户端的待发内存和带宽。客户端按路径应用比当前更新的通知并忽略重复或较旧通知；序号跳跃表示中间状态可能已合并，较新的通知携带该路径最新值，因此跳号本身不要求重读。连接中断后仍须重新订阅并获取新快照。
- 单个订阅持续超过其待发资源上限时，服务端必须终止该订阅，并发送 JSON-RPC Notification `esp_cockpit.subscription.terminated`，参数包含订阅 ID `subscriptionId` 和稳定原因码 `reason`；首版因待发资源上限终止时，`reason` 为 `resource_limit`。通知不携带自由格式内部诊断信息。服务端先释放该订阅的待发状态更新，再使用有限的预留控制消息额度发送终止通知；若 WebSocket 传输仍无法交付该通知，则关闭连接。控制消息额度计入连接资源预算。其他订阅和 WebSocket 连接继续可用；连接级队列或总资源达到硬上限时关闭 WebSocket。客户端可重新订阅已终止的订阅。
- 具体 HTTP 状态码到请求/传输失败类别的映射，以及稳定错误码清单，须在逐方法 API 定义中补齐。

## 5. 能力发现与 Schema

- 客户端先读取能力发现，再依设备公布的方法、可选能力、Schema 版本和资源限制选择调用；能力发现报告实际可用状态，而非产品理论上可能编入的全部插件。
- 未编译或未启用的插件、方法和能力必须从能力清单中完全省略，不以 `enabled: false` 形式发布；通用 WebUI 仅根据清单中实际可用的条目呈现入口。
- 能力发现仅包含协议兼容所需的信息：JSON-RPC 版本、实际可用方法/能力、各 Cluster Schema 版本和生效资源上限；不包含产品型号、固件版本或动态运行状态。此类设备信息由可选运行信息插件提供，避免核心协议依赖该插件。
- 能力发现结果按职责分组表达协议版本、可用方法、可选能力、Cluster 及其 Schema 版本、资源限制；不将所有信息压入单一扁平列表。各组的正式 JSON 字段名与编码仍待细化。
- 可用方法清单必须列出当前实例实际可调用的全部方法，包括组件核心、已启用插件和应用注册方法；不可调用或未注册的方法不得列出。
- 能力清单中的 `capabilities` 只列当前实例实际启用的语义功能标识，不重复列出 RPC 方法名；`methods` 是可调用方法清单，Cluster/Schema 描述数据模型。客户端应按各组的明确定义判断功能，不从方法名或 Schema 猜测其他能力。
- 能力标识按所有者命名空间区分：组件核心及内置插件使用 `esp_cockpit.*`，应用功能使用应用自己的前缀。标识采用全小写、点分层级格式，在所属命名空间内稳定且唯一；标识独立于方法名，不得由 RPC 方法名隐式推导。具体 ID 分配和注册规则仍待细化。
- 能力发现必须在单个有界响应中完整返回，不分页；详细 Cluster Schema 单独按页查询。若完整能力清单无法放入响应上限，服务端必须明确报错，不得分页替代、静默截断或返回部分清单。单次完整读取可让客户端基于同一份清单判断功能和资源限制。
- 客户端必须在每个新认证会话开始时及断线重连后重新读取能力发现；同一会话内可复用已成功读取的清单。读取失败时不得回退到前一会话的缓存。
- 能力发现成功前，客户端不得发起其他业务 RPC。能力发现失败时，WebUI 必须明确显示失败并允许重试；不得根据默认假设或旧能力信息继续调用业务方法，避免误用未启用能力或超出设备资源上限。
- 通用 WebUI 先读取能力发现，再在需要展示某个 Cluster 时按需加载该 Cluster 的 Schema，并在当前会话内缓存；重连或能力发现显示该 Schema 版本变化时，必须使对应缓存失效并重新读取。不要求启动时读取所有 Cluster 的 Schema，以免未使用功能拖慢首屏并浪费请求与内存。
- 只有该 Cluster 的所有 Schema 分页均成功读取，或存在当前会话内仍有效的完整缓存时，WebUI 才可提供其交互。若某页读取失败且无有效完整缓存，须隔离该 Cluster、明确提示失败并允许重试；不得将部分 Schema 渲染成完整界面，其他 Cluster 仍可使用。
- `esp_cockpit.schema.list` 每次只查询一个 Cluster，并在该 Cluster 内按 `offset + limit` 分页；其他 Cluster 的 Schema 独立请求、缓存和失败处理，避免单个 Cluster 的数据或错误影响其他功能。
- 请求当前能力清单中未公布的 Cluster 时，服务端必须返回稳定 RPC 错误，不得伪装成合法的空 Schema；客户端不得将该错误缓存为空清单。
- 每个 Schema 分页响应都必须携带所属 Cluster 的 Schema 版本。客户端发现同一轮读取的页面版本不一致时，必须丢弃该轮全部结果、重新读取能力发现并重试，不得拼接或缓存混合版本的 Schema。
- Schema 采用按规范化完整路径 ASCII 字典序固定排序的 `offset + limit` 分页，并公布最大 `limit`；排序依次比较 Endpoint、Cluster、成员类型和成员标识，不依赖注册先后。`offset` 从 0 开始且必须非负；`limit` 必须为正且不超过公布的最大值，越界时明确报错而不静默夹取。`offset` 到达或超过总条目数时返回空条目及稳定总数。每页必须报告该 Cluster 在对应 Schema 版本中的稳定总条目数；客户端以 `offset + 本页返回条数` 与总数比较确认是否读完。注册表在服务启动后保持不变，因此各页总数和顺序一致，客户端可重复读取任意页，不需要设备维护有状态游标。
- Schema 使用足以支撑通用 WebUI 的机器可读描述，包括数据类型、读写权限、值约束、枚举/单位和可用操作；特殊业务流程可由应用提供专用界面。
- 首版通用 Schema 子集仅支持标量字段：字符串、整数/数值、布尔、枚举、基本范围/长度约束和展示元数据；枚举在线上使用稳定字符串标识，显示名称作为独立的本地化元数据，调整显示顺序不得改变值；普通字符串有全局 UTF-8 字节上限，字段 Schema 可声明更小的上限，字符串长度约束均按 UTF-8 字节数计算，超限必须拒绝且不得截断；整数限定为有符号 `int32_t` 范围，确保浏览器可精确表示并简化跨平台转换；带小数的数值在 C API 中使用 `double`，减少与浏览器数字之间的精度损失，且必须为有限值。不支持数组、嵌套对象、条件规则、引用或组合 Schema。复杂业务表单由应用提供专用界面，避免 MCU 和通用客户端承担完整 JSON Schema 的复杂度。
- Schema 声明的默认值仅作为界面建议，不得自动写入设备；当前值以设备 Read 结果为准。若尚无当前值，WebUI 可以展示建议值，但必须等用户明确保存后才发送 Write，避免页面加载或客户端升级意外改变设备配置。
- Schema 中的读写权限用于 WebUI 呈现和控件启用/禁用，不构成授权边界。服务端必须对每次 Read、Write、Invoke 和订阅请求独立执行授权与校验；客户端隐藏控件或被修改的 Schema 不得绕过服务端检查。
- Schema 仅采用明确限定的 JSON Schema 子集，不要求组件或客户端完整实现 JSON Schema 标准。客户端遇到可能影响数据含义或写入校验的未知规则时，必须隔离该 Cluster 并说明原因，不得静默忽略；只有契约明确标为可忽略的展示元数据才能忽略。限制子集可控制嵌入式校验成本和客户端实现复杂度。
- 每个 Cluster 的 Schema 独立使用主/次版本。兼容的可选属性或能力以次版本递增；同主版本的更高次版本可继续使用客户端已理解的能力，并忽略可安全忽略的可选新增项。改变既有字段类型/含义、移除能力或使新增内容成为既有功能必需条件时提升该 Cluster 主版本。客户端无法兼容某 Cluster 主版本时仅隔离该 Cluster 并说明原因，其他兼容 Cluster 仍可使用。

## 6. 资源上限与超限行为

- 所有影响客户端请求和设备资源使用的上限必须有限，并通过能力发现公布实际生效值；具体数值按目标硬件和生产配置实测确定，不在本稿中预设。
- 资源上限至少覆盖请求/响应大小、请求 `id` 字符串长度、普通字符串及错误提示字节数、Schema 页大小、多路径项目数、应用 RPC 回调工作并发数（首版固定为 1）、HTTP/WebSocket 共用的每实例等待队列容量（不含正在执行的请求）、队列参数总字节预算及最长排队等待时间、订阅数/路径/频率/待发字节，以及 Operation 容量和相关超时；最终公开字段清单随能力发现契约细化。
- 请求超过上限或整体资源不足时，使用稳定错误码明确拒绝；不得静默截断、丢弃项目或返回看似成功的部分结果。多路径逐项失败仍按既定规则置于 `result`，与整体资源拒绝区分。
- 应用 RPC 等待队列已满，或请求超过公布的最长排队时间仍未开始时，组件在调用回调前使用同一个稳定组件级 `busy` 错误拒绝请求；到期请求从队列移除。客户端展示设备忙碌提示，不自动重试。该期限不用于强制中断已开始的应用回调。
- 只有认证、请求格式、方法/路径、Schema 参数及组件可完成的授权校验通过后，请求才进入应用回调等待队列；这些校验失败不占用队列。依赖应用运行时状态的业务判断由应用回调处理。
- 入队请求使用组件拥有的参数副本，不引用传输缓冲区；待处理请求的参数总字节数不得超过公布的队列预算。预算不足时与队列已满相同，返回稳定组件级 `busy` 错误；请求完成、取消或过期后释放副本。
- 首版等待队列只执行每实例全局容量限制，不按认证会话或连接分配配额；协议不承诺不同客户端间的排队公平性。

## 7. 版本兼容规则

- JSON-RPC 协议版本、Cluster Schema 版本和公共 C API 主版本职责不同，分别演进。
- 用于并发写入检测的路径值版本与 Cluster Schema 版本及 JSON-RPC 协议版本相互独立；可写路径必须能在 Read/Subscribe 中返回可用于 Write 前置比较的当前值版本。
- 路径值版本仅在当前设备运行期有效；设备重启后所有旧版本失效，客户端重新认证后必须重新读取当前值再写入。设备不持久化版本计数器，避免为并发校验增加闪存写入；版本如何携带运行期标识仍待方法契约细化。
- 路径值版本仅在有效状态值实际变化时推进；将同一有效值重复写入不改变版本。Write 表示状态赋值，不应用于承载需要重复执行的业务副作用；此类操作应使用 Invoke。
- 同一 Cluster Schema 版本内的新增属性和能力必须是可选的，不得让既有功能转而依赖新增内容；客户端可忽略不认识的新增字段并继续使用已知功能。会强制改变既有行为或使新增内容成为既有功能必需条件时，属于破坏性变更，须提升相应版本。
- 兼容的新增方法、可选能力和响应字段可增量发布；客户端按能力发现判断实际支持情况，并容忍响应中的未知新增字段。
- 破坏既有协议方法语义时提升 JSON-RPC 主版本；破坏某个 Cluster 的既有 Schema 语义时提升该 Cluster 主版本；破坏公共 C API 源码兼容时提升组件主版本。
- 设备与客户端的 JSON-RPC 主版本相同时，即使设备次版本更高，客户端也应继续兼容流程：先通过能力发现确认设备实际提供的功能，只调用自己理解的方法和能力，并忽略新增响应字段。不得仅因次版本不同就拒绝连接。
- 客户端发现设备的 JSON-RPC 协议主版本与自身不兼容时，必须明确提示版本不兼容，并禁止发送 Write 或其他会改变设备状态的 RPC。只有在客户端能够确认某只读方法及其响应语义可理解时，才可继续使用该只读能力；不得仅凭方法名称相同就假设兼容。同一主版本内则由能力发现确定实际可用功能。
- 客户端无法理解某个 Cluster Schema 版本时，只隐藏或禁用该 Cluster 的交互，并明确说明不兼容原因；其他兼容 Cluster 仍可使用。客户端不得猜测未知 Schema 字段或语义。
- 协议版本的具体编码格式、主次版本兼容范围表达及版本协商流程仍待细化。

## 8. 仍待细化的客户端契约

- 能力发现与 Schema 查询的请求/响应字段及剩余分页边界条件。
- 能力标识的具体 ID 分配和注册规则。
- JSON-RPC 与各 Cluster Schema 的版本编码和协商流程，以及协议主版本不兼容时只读能力的具体呈现方式。
- 路径值版本的字段表示和运行期标识编码。
- 有限 JSON Schema 子集的词汇表、标识符、约束表达、nullability 和默认值注解的具体表达、可忽略展示元数据分类，以及不兼容 Cluster 的具体 WebUI 呈现方式。
- 各核心方法的正式名称、参数/结果结构、通知结构、Invoke 重试元数据表示及错误码清单。
- JSON-RPC 标准错误码与组件/应用自定义错误码的具体数值范围和分配表。
- HTTP 状态码映射、请求/响应字节上限和各目标实际资源上限。
- C API 的具体头文件/函数/类型契约及公共回调和队列限制；源码兼容边界已定，二进制 ABI 保证不在范围内。
