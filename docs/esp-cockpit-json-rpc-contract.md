# ESP-Cockpit JSON-RPC 协议契约

> 状态：规范性设计稿。本文定义 ESP-Cockpit 客户端与设备间的 JSON-RPC 契约边界。首版最小互操作契约已由[冻结基线](./esp-cockpit-interoperability-baseline.md)定稿；组件与 WebUI/示例客户端可据此并行实现。目标配置的资源数值仍须经实测确定，但字段名称、单位和公布规则已冻结。

## 1. 协议定位与版本

- 消息协议必须符合 JSON-RPC 2.0，包括请求/响应信封、`id` 关联和 Notification 不带 `id` 等规则。首版所有客户端发往设备的方法调用都必须带非空字符串 `id`，其 UTF-8 字节长度不超过冻结的 `limits.maxIdBytes`。同一连接上所有尚未收到响应的请求必须使用不同 `id`，收到对应响应后可重用。选字符串是为避免浏览器数字精度导致关联标签被改写；`id` 只用于请求/响应关联，不提供去重或重试安全保证。不接受客户端发起的 Notification；设备向客户端推送的 Notification 不带 `id`。首版不接受 JSON-RPC Batch 数组；不支持 Batch 是采用的协议子集，不改变单条消息的 JSON-RPC 2.0 语义。
- 若客户端发送无 `id` 的方法消息，该消息按 Notification 处理：设备丢弃且不执行方法、不发送响应，并仅在设备本地记录诊断；连接保持可用。JSON-RPC Notification 没有响应关联 ID，按协议不能返回错误信封，因此客户端必须为所有方法调用提供 `id`。
- 若同一连接上收到与尚未完成请求重复的 `id`，设备不得执行第二个请求；应记录本地诊断并关闭该连接，避免无法区分的响应。此前已开始执行的回调仍按客户端断连规则处理。
- Read、Write、Invoke、Subscribe 的组织方式受 Matter Interaction Model 启发，但 ESP-Cockpit 使用自有路径、Schema 和 JSON-RPC over HTTP/WebSocket，不声明 Matter 语义合规或 Matter 协议互操作。
- JSON-RPC 线协议与公共 C API 分别版本化；不得用一个版本号代替另一者的兼容性。公共 C API 在同一主版本内保持源码兼容；不承诺跨 ESP-IDF、工具链或构建配置的预编译二进制 ABI。分开版本能使客户端和组件集成方独立判断升级影响；源码兼容符合组件随应用编译的使用方式。
- 能力发现必须公布 JSON-RPC 应用协议的主、次版本，并同时报告当前实例实际提供的方法、可选能力与有限资源上限。协议版本提供快速兼容判断，能力清单则反映插件和构建配置差异；不得仅凭版本号推定某个可选方法存在。
- 兼容扩展可在不破坏旧客户端的前提下增量加入；改变或移除已发布方法、字段含义或既有行为属于破坏性变更，须提升 JSON-RPC 应用协议主版本。新增响应字段应允许旧客户端忽略；服务端不得因此接受未知请求字段。

## 2. 方法组织与命名空间

- 核心交互采用通用的 Read、Write、Invoke 和 Subscribe；支持显式取消单个订阅，以及查询设备级长操作 Operation。通用交互使客户端可以复用一套路径处理逻辑，而不必为每个属性实现独立调用方式。
- 需要整体事务或专用长流程的能力可以使用具名 RPC；具名 RPC 与通用方法必须共用授权、校验和一致的业务语义，避免同一操作的权限或结果不一致。
- 组件核心方法及组件内置插件方法使用保留的 `esp_cockpit.*` 命名空间；应用根描述符始终声明一个稳定的小写 ASCII 反向域名风格命名空间，例如 `com.acme.greenhouse`，即使没有应用业务方法或其他注册项也必须提供。这样应用身份不会随注册项是否为空而改变，后续增加方法或能力时也无需另换命名空间。命名空间至少包含三个以点分隔的标签；每个标签仅由小写 ASCII 字母、数字和连字符组成，不得为空或以连字符开头/结尾。应用业务方法必须使用该命名空间，不得占用组件前缀。该命名空间是普通标识，不触发 DNS 查询；应用负责选择稳定且唯一的前缀。它只表示方法归属，与 Endpoint/Cluster/Attribute/Command 等数据路径分开；禁止隐式别名，以避免插件之间名称冲突和难以发现的路由差异。
- 组件方法使用全小写、点分层级命名；首版核心方法名、请求/响应字段及边界以[冻结基线第 2 节](./esp-cockpit-interoperability-baseline.md#2-冻结的核心-rpc)为准。
- 能力发现方法名固定为 `esp_cockpit.capabilities.get`；分页 Schema 查询方法名固定为 `esp_cockpit.schema.list`。两者完整字段和边界以[冻结基线第 3 节](./esp-cockpit-interoperability-baseline.md#3-能力发现schema-与通知)为准。
- 每个 Invoke/Command 的机器可读描述必须声明其重试安全策略；客户端只有在明确识别为安全时才能提供重试。元数据缺失或无法理解时一律按不可安全重试处理，不得根据方法名或说明文字推断。
- 耗时 Invoke 可返回通用 Operation ID，客户端再通过统一的状态查询方法读取状态/进度；首版不提供通用 Operation 取消语义。活动 Operation 不得因容量压力被驱逐；终态记录按有界容量和保留期管理，容量压力下优先回收最旧终态。若无可回收终态且容量已满，拒绝新 Operation 并返回明确资源不足错误。具体容量与保留期按目标资源测试确定并通过能力发现公布。
- 客户端超时或连接断开时，若 RPC 请求尚未开始执行，组件取消排队请求；若请求已开始，组件继续执行其中的应用回调（多路径请求继续处理剩余路径），但不再向已关闭连接发送响应。Read 可由客户端重新发起读取；Write 和 Invoke 的结果可能未知，客户端不得自动重试。若已取得 Operation ID，应先查询 Operation；只有命令明确声明可安全重试时，客户端才可提供 Invoke 重试选项，避免非幂等动作重复执行。
- 首版核心方法名、参数/结果字段和通知名称均已冻结，见[冻结基线](./esp-cockpit-interoperability-baseline.md)；实现与客户端不得将其他文档中的逻辑分类或示例名称视为替代契约。

## 3. 参数、响应与兼容性

- JSON-RPC 方法只接受命名参数对象，不接受位置参数数组。命名参数便于按名称校验和扩展，也可避免参数顺序错误造成误操作。
- 服务端严格校验请求：未知或拼错的字段、类型不符及结构不符必须明确报错，不得静默忽略或截断。
- Invoke 方法声明每个参数为必填或可选；缺少必填参数时必须在调用处理器前拒绝。省略可选参数与显式传入 JSON `null` 必须区分，且不得因省略而自动应用 Schema 默认值。
- 多路径 Read/Write 请求不得重复包含同一路径；发现重复时必须在调用任何回调前拒绝整个请求，不得静默去重，以避免结果归属不明确或重复执行 Write。
- 多路径 Read/Write 按请求中的路径顺序逐项处理，响应中的逐项结果也按相同顺序排列。
- 多路径请求作为整体一次性通过队列准入并预留完整队列字节预算；准入失败时任何路径都不得执行。准入成功后仍按逐路径语义处理，业务失败可以部分成功，这不构成事务保证。
- 应用 RPC 回调按请求成功入队的先后顺序串行执行；同一多路径请求的所有路径处理完成后才处理下一请求。该顺序保证不构成多路径 Write 的原子性保证。
- Write 未包含的路径保持不变；显式 JSON `null` 仅在该路径的 Schema 明确允许时才是合法值，否则必须明确报错，不得把 `null` 当成省略值处理。
- 每个 Write 路径必须携带客户端最近从 Read 或 Subscribe 获得的该路径值版本。服务端须在应用写入时比较版本；版本已变化则拒绝该路径且不修改其值，并返回可识别的冲突错误。多路径 Write 仍逐路径处理，冲突路径失败不阻止其他路径成功。通用 WebUI 必须向用户说明冲突，不得自动读取新版本后重试并覆盖并发修改。
- 应用负责在同一套同步机制下维护属性值及其版本，并在 Write 时原子地比较客户端版本和更新值：不匹配时报告冲突且不修改值；匹配时完成写入，并仅在值实际改变时推进版本。无论变更来自 RPC、按键还是应用任务，都必须遵守同一规则。Read 返回的值和版本必须来自同一一致状态；只写属性只提供版本及必要元数据。组件工作线程只串行化组件回调，不能单独防止应用其他任务与回调并发修改；由数据所有者同步可消除检查与写入之间的竞态。
- Write 成功表示应用状态已接受该值，不自动表示已持久化；通用组件不写 NVS。应用选择并负责持久化策略。若应用承诺同步持久化，回调只有在满足该持久化承诺后才能报告成功，失败须返回该路径的明确错误，不得伪报已持久化。若采用延迟持久化，应用须通过 Schema 可读状态表达 `Applied`、`Pending`、`Persisted` 或 `Failed`；前端须明确显示这些状态，持久化失败不得静默，产品须说明掉电可能丢失待写值。多路径 Write 仍逐路径报告并允许部分成功。
- 对只写属性，有该属性写入权限的客户端可通过 Read 获取当前值版本和必要元数据，但不得获得属性值；没有写入权限的客户端不得通过此方式获取版本。版本用于 Write 的并发检查，不改变只写值不能通过 Read/API 回显的约束。版本元数据可能暴露属性发生过变化，因此必须执行授权。
- 如果应用在只写属性的版本读取中意外返回属性值，组件不得将其发送给客户端或将该路径伪装成成功；必须返回稳定组件错误并记录不含属性值的本地诊断。多路径 Read 的其他路径仍可按逐项规则处理，既避免泄露也暴露处理器契约错误。
- 发生过期版本冲突时，通用 WebUI 保留用户尚未提交的草稿。对可读属性，应重新读取并展示当前设备值；对只写属性，须说明无法展示当前值，用户可决定是否获取新版本并明确重新提交。不得自动覆盖并发修改；多路径 Write 仅重提冲突路径，不得重复提交已成功路径。
- 客户端处理响应时应忽略其不认识的新增字段，以允许服务端增加兼容信息而不破坏旧客户端。
- JSON-RPC 已定义的协议错误使用对应的 JSON-RPC 2.0 标准错误码；组件自定义错误使用 `-32099..-32000`，应用业务错误使用各应用在 `1..INT32_MAX` 中声明的固定正整数范围。应用范围彼此不得重叠，且所有范围均不得占用其他 JSON-RPC 标准或保留错误码。客户端按机器码分支处理，未知错误码按通用失败处理；用户可见消息仅用于展示且可以改进措辞。处理器未提供用户提示、提示不是合法 UTF-8 或超过提示字节上限时，组件生成通用提示并保留原错误码，不截断提示。不得将 ESP-IDF 或底层库错误码直接作为协议错误码，也不得向客户端泄露堆栈、凭据或内部状态。这样可在更换底层实现时保持客户端契约稳定。
- 首版应用业务错误只包含错误码和可选消息，不接受任意 JSON-RPC `error.data`；若未来需要结构化错误细节，必须另行定义稳定 Schema。
- 请求整体无法执行时使用 JSON-RPC 顶层 `error`；Read/Write 处理器的单路径失败位于对应逐项状态中，多路径调用允许其他路径部分成功；Invoke 处理器失败使用顶层 `error`。必须全有或全无的业务动作使用专用事务操作。
- Invoke 成功响应必须包含符合方法声明结果类型和约束的 `result`；若方法没有业务返回值，`result` 必须为 `null`，不得省略。

## 4. HTTP 与 WebSocket

- HTTP JSON-RPC 只使用 `POST` 和 `application/json`；`GET` 不承载 RPC 且不得改变状态。
- HTTP 状态码表示请求/传输层是否能够将请求交给 RPC 处理，例如认证失败、无效 HTTP 请求或预分发的整体资源拒绝。请求进入 JSON-RPC 处理后，无论成功还是协议/RPC 错误（包括解析错误、未知方法和无效参数），均使用 HTTP 200，并在 JSON-RPC 信封的 `result` 或 `error` 中表达。这样 HTTP 与 WebSocket 共用同一套 RPC 错误语义。
- WebSocket 建立后不再有逐消息 HTTP 状态码；每条 RPC 的业务成功或失败均使用 JSON-RPC `result` 或 `error`。
- Read、Write 和 Invoke 可通过 HTTP 或 WebSocket 承载；Subscribe/Unsubscribe 使用 WebSocket。单个订阅可独立取消，避免为停止一个订阅而关闭含有其他活动订阅的连接。
- 对格式有效但在当前连接上不存在或已结束的订阅 ID 调用 Unsubscribe 时，返回成功并作为 no-op；客户端可在响应丢失、重连清理或订阅已被设备终止后安全重试。无效的 ID 参数格式仍返回参数错误。
- 多路径 Subscribe 必须全有或全无：任一路径不可订阅或无法取得其初始值时，整体返回错误且不得创建部分订阅。持续推送的部分成功容易造成客户端误以为所有路径都受监控，也会增加订阅清理复杂度；该规则不改变多路径 Read/Write 的逐项结果语义。
- 只写属性不可订阅；Subscribe 包含任何只写路径时必须明确返回错误，整条请求不得创建订阅。已授权客户端仍可通过 Read 获取该属性的版本及必要元数据。拒绝订阅可防止初始快照或后续通知泄露只写值，也无需为只写属性引入独立的仅版本订阅语义。
- 单次多路径 Subscribe 中重复出现同一路径时，整个请求按无效参数拒绝且不得创建订阅；服务端不静默去重，以保持请求与结果的明确对应。该规则不影响不同 Subscribe 调用之间允许重叠路径并创建独立订阅。
- 同一 WebSocket 连接重复 Subscribe 相同路径时，每次成功调用都创建独立订阅 ID；重叠路径的更新按各自订阅 ID 分别推送，Unsubscribe 只取消指定 ID。独立订阅使每次调用都能单独管理和取消，避免共享订阅的引用计数及所有权歧义；重复订阅分别计入该连接和设备的订阅资源上限。
- Subscribe 成功响应必须包含订阅 ID，以及每个订阅路径的当前值和对应版本/序列号；每条路径的初始快照与开始观察更新之间必须有明确的衔接点，使变化要么包含在快照中，要么作为后续 Notification 推送，不得遗漏。服务端必须先发送成功响应，再发送该订阅的任何 Notification；响应发送前发生的更新须暂存，且受既定待发资源上限及按路径合并规则约束。这样客户端可先取得订阅 ID 和快照，再关联后续更新。多路径初始值不承诺跨路径原子快照。若初始快照超过资源上限，必须明确拒绝订阅，不得返回部分初始值并表现为成功。
- 建立 Subscribe 时，组件先登记覆盖全部请求路径的有界临时订阅，再读取各路径初始快照；读取期间的变化通知仍保留路径刷新标记并按既定规则后续刷新。初始读取或其他建立步骤失败时撤销临时订阅，能安全发送时返回错误，否则关闭连接，不留下部分订阅；清理临时订阅不得丢弃其他订阅需要的共享刷新工作。先登记可消除先读值、后开始观察之间的空档，也无需应用为网络发送一直持锁。临时状态受既定资源上限约束；与响应发送期间更新的具体衔接仍须细化，并遵守成功响应先于 Notification 的规则。
- 在订阅成功响应尚未排入该连接发送顺序时，先保留该订阅的更新，同一路径的多个更新可按既定规则合并为最新值；成功响应排在前面后，更新才能排在它之后。发送机制必须保证这一顺序，具体队列实现留待细化。待发数据受既定资源上限约束；发送失败或连接断开按连接清理规则处理，不保证客户端收到。这样客户端可先取得订阅 ID 和初始值，再关联更新。
- 成功响应被接纳进连接的有序发送流程时，组件将临时订阅转为正式订阅；两者须作为不可分割的步骤，不能出现响应已排入而订阅尚未生效的空档。后续状态更新和终止通知均排在成功响应之后。接纳不代表客户端已收到；若后续发送失败或连接断开，关闭并清理该连接上的所有订阅，客户端重连后重新订阅。无需等待网络发送完成即可继续处理状态，但须保证连接失败时清理短暂存在的订阅。
- 若成功响应因资源不足无法进入有序发送流程，不得建立正式订阅；组件撤销临时订阅并释放其资源，保留其他订阅需要的共享刷新工作。若能安全发送明确的资源不足错误则返回该错误；错误也无法发送或已达到连接级队列或总资源硬上限时关闭连接，连接上的其他订阅随之终止。不得无限等待可用空间。这样不会留下客户端不知道的订阅，也避免无界等待。
- 成功响应进入有序发送流程之前，若临时订阅的更新即使按路径合并后仍无法在既定资源限额内安全保留，组件必须放弃建立并撤销临时订阅，释放其资源但保留其他订阅需要的共享刷新工作。能安全发送时返回资源不足错误，否则或达到连接级队列或总资源硬上限时关闭连接。此时不得发送订阅终止 Notification，也不得丢弃某个路径的最后更新后报告成功；成功响应已进入有序发送流程后则按正式订阅的资源限制规则处理。这样不会让客户端得到看似成功却可能遗漏更新的订阅。
- 可订阅属性的值实际变化时，应用主动通知组件相应路径发生变化，包括由 RPC、按键或应用任务引起的变化。应用先在同步保护下完成值与版本更新，释放保护后尽快通知；通知调用只标记路径需要刷新，不同步执行应用 Read 处理器，避免组件和应用互相等待。通知只携带路径，不携带值或版本；组件随后通过 Read 处理器取得一致的最新值和版本，并根据既定的初始快照衔接和有界背压规则向订阅者推送。路径通知避免组件持续轮询和在通知调用中传递长字符串，也允许合并同一路径的刷新。
- C 属性变化通知接口为 `esp_cockpit_attribute_changed()`，接收 Endpoint、Cluster、Attribute 标识及各自 UTF-8 字节长度；准确签名、返回码和所有权以[冻结互操作基线第 7 节](./esp-cockpit-interoperability-baseline.md#7-公共-c-注册回调-api)为准。
- 应用须保证本次通知的路径结构和标识在调用期间有效且不被并发修改；组件在调用期间校验和匹配，返回后不得继续引用本次路径输入，可用已注册路径的内部标记安排刷新。这样可使用临时变量且无需为每次通知动态分配并长期保存输入；注册描述符及其引用元数据仍须遵守原有生命周期要求。
- 首版属性变化通知接口仅允许任务上下文调用，不提供 ISR 专用接口。应用处理硬件中断时须先使用适合 ISR 的机制将信号交给应用任务，由任务更新状态和版本、释放应用锁后通知组件；应用须处理自身投递资源不足，不能静默丢失最后一次变化。这样组件不必在 ISR 中完成路径校验和同步，但应用需要自行安排任务接力。
- 实例尚未启动或已完成停止时，属性变化通知返回 `ESP_ERR_INVALID_STATE`，不缓存或在下次启动后补发；应用已完成的状态与版本更新不回滚。重新启动后客户端重新订阅并获取最新快照，避免停止期间积压刷新工作，也不会将未接收的通知误报为成功。
- 属性变化通知与 `start()` 并发时，以同步保护的开放接收分界点决定结果：跨过前返回 `ESP_ERR_INVALID_STATE`，不缓存、不回滚应用状态；跨过后按运行中规则接收，可能发生在 `start()` 返回前。组件仅在必需运行时资源准备好且同步启动已确定成功后、允许客户端订阅前跨过该点；同步启动失败不得进入接收状态。这样避免资源未准备好就接收通知，也避免允许订阅后仍拒绝通知；不要求等待网络服务就绪。
- 属性变化通知与 `stop()` 并发时，组件同步保护通知接收与停止后拒绝新通知的分界点：正常接收条件下有效通知先接收则设置或合并刷新标记并返回成功；停止先进入拒绝状态则返回 `ESP_ERR_INVALID_STATE`，不设置标记、不回滚应用状态。已接收不保证停止前一定送达客户端；连接关闭后客户端重新连接并订阅以获取新快照。该分界避免释放刷新资源时继续接收通知，并明确调用结果；已开始的工作仍遵守停止等待规则。
- 实例运行时，属性变化通知的路径为空或格式不合法返回 `ESP_ERR_INVALID_ARG`，路径不存在返回 `ESP_ERR_NOT_FOUND`，属性存在但不可订阅返回 `ESP_ERR_NOT_SUPPORTED`；失败不创建刷新工作，也不回滚应用已完成的状态和版本更新。明确区分这些错误可避免应用误以为错误路径的变化已被接收。
- C 属性变化通知接口按顺序检查：必需指针为 `NULL` 返回 `ESP_ERR_INVALID_ARG`；实例尚未运行或已进入停止返回 `ESP_ERR_INVALID_STATE`；实例运行中但刷新机制已故障返回 `ESP_FAIL`；随后依次检查路径是否为空或格式不合法、是否存在、是否可订阅，并返回对应路径错误。必需指针非 `NULL` 但路径标识为空时在路径检查阶段处理。生命周期、故障检查与通知接收须遵守既定同步分界；应用须保证非空实例句柄有效，不承诺检测已销毁的旧句柄。该顺序使多种错误同时存在时结果可预测，且停止或故障时不访问不可用的刷新资源。
- 每个已注册的可订阅路径预留一个待刷新标记；同一路径的多次通知可以合并。组件开始读取时清除本次标记，读取期间的新通知须保留标记并安排后续刷新；设置、清除和调度须同步，不能丢失并发通知。标记数量受注册路径的编译期上限约束，通知不等待网络发送；固定标记避免无界队列，同时保留读取期间的最后状态变化。
- 组件在启动时预先准备刷新标记及唤醒工作线程所需资源；资源准备失败时同步启动失败并按既有规则回滚。运行中接收合法通知不为每次调用动态分配内存，也不依赖普通 RPC 队列的空位；只有标记已保留且后续刷新已可靠安排时才返回成功。若内部故障使组件无法保证这一点，须返回明确错误并记录本地诊断，不得假装成功；同步、唤醒实现留待细化。预留资源使普通队列满或通知频繁时仍能保留最后状态；成功不保证刷新完成时间或客户端收到，停止和读取失败仍按既定规则处理。
- 若刷新机制内部故障导致无法可靠安排刷新，组件须向应用明确报告故障并记录本地诊断，停止接收新的属性变化通知并明确返回错误；故障期间不得成功建立新订阅，正在建立的订阅按建立失败规则清理。运行中的实例因该故障无法接收通知时，C 接口返回 `ESP_FAIL`，应用应查询刷新故障状态和原因，不得仅凭通用失败码推断具体原因。组件须关闭可能受影响的 WebSocket 连接；若无法可靠确定受影响范围，则关闭该实例所有 WebSocket 连接，连接上的订阅随之终止。故障不能因网络重新就绪而自行清除；应用须通过 `stop()`、`start()` 重新初始化，恢复后客户端重新连接并订阅以获取快照。这样避免旧值继续被当成有效订阅状态，代价是内部故障可能使多个客户端断线。
- 刷新内部故障期间，能安全响应的 Subscribe 请求须返回 JSON-RPC 顶层组件错误 `-32010`，表示刷新机制内部故障导致当前不能建立订阅，不得报告成功；无法安全发送响应时关闭连接。此码属于组件自定义错误范围，不能用于其他错误含义；它与 C API 的 `ESP_FAIL` 相互独立。通用 WebUI 按数字识别并提示实时更新暂不可用，不将旧数据标记为实时状态，也不得无限自动重试；组件重新初始化后用户可重新连接并订阅。错误只提供适合客户端的安全原因，不包含 `error.data`，也不暴露内部堆栈或底层诊断。错误消息仅供展示，可调整措辞；明确错误可区分支持订阅但暂时故障与不支持订阅。

  例如请求 `id` 为 `"1"` 时，错误响应可为：

  ```json
  {
    "jsonrpc": "2.0",
    "id": "1",
    "error": {
      "code": -32010,
      "message": "Subscription temporarily unavailable"
    }
  }
  ```
- Subscribe 通过认证、请求格式及组件可完成的授权等既定入队前校验后，组件在进入普通工作队列前检查刷新故障；已故障时在队列外返回上述稳定错误，不依赖可能失效的刷新工作线程。请求入队或建立过程中才发生故障时，也不得让该请求在故障期间建立订阅：故障状态检查与成功响应接纳及订阅生效须同步，若故障先成立则按建立失败规则清理并能安全发送时返回错误，否则关闭连接；若订阅先成功生效，后续故障按既定规则关闭受影响连接。已开始的应用回调仍遵守既定不强制中断规则。这样避免故障检查与订阅生效之间的竞态，也不向未经必要校验的请求泄露故障信息。
- 发现故障时先同步记录故障并禁止接收新通知和建立新订阅，再通过启动时预留、独立于刷新工作线程的信号通知生命周期控制器，由控制器安排连接关闭和高阶事件提示；信号资源准备失败时同步启动失败并回滚。通知调用线程不直接关闭网络连接或等待客户端，关闭为异步操作且不承诺固定完成时间。故障处理不依赖可能无法唤醒的刷新工作线程；具体信号机制留待细化。
- 故障与有效的停止流程并发时，同步保留已发现的故障并拒绝新通知和订阅；连接关闭和资源释放由同一个协调流程执行，停止已开始时由停止流程接手尚未完成的故障清理。事件无法送达时故障状态仍可在停止后查询，已开始的工作项仍按既定规则等待完成。已停止实例上的通知调用只返回既定状态错误，不因此产生新的刷新故障；统一清理避免重复释放或互相等待。
- 刷新故障及稳定、可识别的原因须保留为应用可查询的实例状态，并通过高阶事件提示；查询是最终依据，不依赖事件一定送达。事件投递失败须记录本地诊断，不能阻止故障保护措施。故障状态在停止期间和重新启动失败后仍可查询，成功重新初始化后才清除；实例销毁后不要求保留。这样应用即使错过事件也能发现故障，具体查询字段和事件机制留待细化。
- 生命周期状态与刷新故障状态分别查询；前者描述网络和 Web 服务生命周期，后者独立表示刷新内部故障及原因。Web 服务仍可访问时无需因刷新故障将生命周期状态改为网络错误；`READY` 单独不表示订阅刷新或所有功能均健康，应用须结合刷新故障状态判断订阅是否因该故障被禁止。分开表示可避免把服务可访问与订阅不可用混为一谈。
- 即使合法的可订阅路径当前没有订阅者，正常接收条件下运行中的实例仍接收通知、设置或合并刷新标记并返回成功；组件按既定调度读取最新状态，当时没有订阅者则无需推送。成功只表示刷新工作已接收或合并，不表示客户端已收到；之后建立订阅仍需读取最新初始快照。统一处理使应用不必判断订阅者，也避免仅因通知时没有订阅者就忽略变化，代价是可能产生无订阅者时的 Read；订阅建立过程的并发衔接仍须满足既定不遗漏要求。
- 状态刷新与普通 RPC 回调共用实例的单个工作线程，不并发调用应用处理器。两类工作同时等待时，工作线程完成一条普通请求后处理一个待刷新路径，再处理下一条普通请求；待刷新路径按轮转顺序选择。没有普通请求时可继续处理待刷新路径；刷新不占用普通 RPC 等待队列槽位，也不打断已开始的多路径请求。普通请求仍按成功入队顺序执行。交替处理避免持续的普通请求或刷新使另一类工作无法开始，但不保证回调执行时间有上限。
- 服务端允许合并同一路径尚未发送的多个状态更新，只推送该路径的最新值和最新序列号，不保证交付每个中间值。订阅表达当前状态而非事件日志；合并可限制慢客户端的待发内存和带宽。客户端按路径应用比当前更新的通知并忽略重复或较旧通知；序号跳跃表示中间状态可能已合并，较新的通知携带该路径最新值，因此跳号本身不要求重读。连接中断后仍须重新订阅并获取新快照。
- 状态刷新时 Read 处理器失败，服务端必须终止包含该路径的所有活动订阅；多路径订阅整体终止，不包含该路径的订阅不因该失败而终止。每个受影响订阅使用 `esp_cockpit.subscription.terminated` 通知，`reason` 为 `read_failed`；客户端可在了解失败后重新订阅，组件不得无限自动重试。这样不会把过期值伪装成持续有效的状态。建立订阅时无法读取初始值仍按整条 Subscribe 请求失败处理。
- 单个订阅持续超过其待发资源上限时，服务端必须终止该订阅，并发送 JSON-RPC Notification `esp_cockpit.subscription.terminated`，原因码 `reason` 为 `resource_limit`。无论原因是 `resource_limit` 还是 `read_failed`，通知均包含订阅 ID `subscriptionId` 和稳定原因码 `reason`，不携带自由格式内部诊断信息；服务端先释放该订阅的待发状态更新，再使用有限的预留控制消息额度发送终止通知。若 WebSocket 传输仍无法交付该通知，则关闭对应连接，连接上的其他订阅也随之终止。控制消息额度计入连接资源预算；未关闭连接上的其他订阅继续可用。连接级队列或总资源达到硬上限时关闭 WebSocket。客户端可重新订阅已终止的订阅。
- HTTP 状态码映射与稳定错误码清单以[冻结基线第 4、5 节](./esp-cockpit-interoperability-baseline.md)为准。

## 5. 能力发现与 Schema

- 客户端先读取能力发现，再依设备公布的方法、可选能力、Schema 版本和资源限制选择调用；能力发现报告当前实例实际提供并启用的功能，而非产品理论上可能编入的全部插件，也不保证每次调用都能成功。
- `esp_cockpit.capabilities.get` 不需要参数：请求可省略 `params`，也可传入空对象 `params: {}`，两者均查询完整能力清单。`params: null`、数组或包含任何字段的对象均按无效参数拒绝。接受两种空参数写法便于 JSON-RPC 客户端调用，同时保持命名参数和拒绝未知字段的约束。
- 未编译或未启用的插件、方法和能力必须从能力清单中完全省略，不以 `enabled: false` 形式发布；通用 WebUI 仅根据清单中实际提供并启用的条目呈现入口。
- 刷新内部故障期间，能力清单仍列出已启用的 Subscribe；暂时无法执行由该方法的稳定组件错误表达，不因故障临时移除方法。刷新故障不等于功能未编译或未启用；保留方法可避免客户端把暂时故障误认为设备不支持订阅，也意味着客户端不能仅凭清单假设调用一定成功。
- 能力发现仅包含协议兼容所需的信息：JSON-RPC 版本、实际提供并启用的方法/能力、各 Cluster Schema 版本和生效资源上限；不包含产品型号、固件版本或动态运行状态。此类设备信息由可选运行信息插件提供，避免核心协议依赖该插件。
- 能力发现成功响应的 JSON-RPC `result` 是对象，直接包含五个字段：`protocolVersion`（包含 `major`、`minor`）、`methods`、`capabilities`、`clusters`（每项包含 `id` 和正整数 `schemaVersion`）及 `limits`；这五个字段不放在 JSON-RPC 响应信封的顶层，也不另加一层包装。字段名和类型以[冻结基线第 3 节](./esp-cockpit-interoperability-baseline.md#3-能力发现schema-与通知)为准。
- `limits` 中的字段名、单位和公布规则以[冻结基线第 8 节](./esp-cockpit-interoperability-baseline.md#8-limits-字段名及单位)为准；每个值均为设备当前实际生效的有限上限，数值按目标硬件和生产配置实测确定。
- `limits` 只公布稳定的容量上限，不包含当前已用量或剩余量；名称应明确表达上限（例如 `maxQueuedRequests`）。瞬时资源使用情况若需展示，应由独立的运行信息能力提供，避免客户端缓存已过期的动态数值。
- `methods` 和 `capabilities` 按完整标识符的 ASCII 字典序排序；`clusters` 按其 `id` 的 ASCII 字典序排序，不依赖注册顺序。稳定排序使注册顺序变化不会造成能力响应无意义地变化。
- 能力发现中的 `clusters[].id` 是完整 Cluster 标识字符串，格式为 `endpoint/cluster`，例如 `room1/temperature`；Schema 查询的 `clusterId` 使用相同字符串。Endpoint 和 Cluster 子标识遵循各自的数据路径标识规则，`/` 仅作分隔符，不属于子标识。完整标识可区分不同 Endpoint 下同名的 Cluster，无需要求 Cluster 子标识在整台设备内唯一。
- JSON-RPC 协议版本使用包含 `major`、`minor` 两个非负整数的对象表示，不使用合并版本字符串；每个 Cluster 的 Schema 版本使用正整数。分开的协议主、次版本便于客户端明确判断兼容性，整数表示避免字符串解析和比较歧义。
- 只要某个 Cluster 对客户端发布的 Schema 内容发生变化，其 Schema 版本就必须递增，包括路径、类型、权限、约束、枚举标识和展示元数据；普通运行时值变化不递增 Schema 版本，由路径值版本表达。这样客户端可用 Schema 版本判断缓存是否仍有效。
- 方法清单必须列出当前实例实际提供并启用的全部方法，包括组件核心、已启用插件和应用注册方法；未启用或未注册的方法不得列出。方法存在不保证每次调用成功，刷新故障期间的 Subscribe 按上述规则保留并返回稳定错误。
- `methods` 列表项只包含完整方法标识，不内嵌参数或结果 Schema。应用方法的参数、结果和所属 Cluster 描述通过对应 Cluster 的分页 Schema 提供；组件核心方法的参数和结果契约由本协议直接定义。这样避免在能力发现中重复传输详细描述或产生两处定义不一致。
- 每个应用注册的专用 RPC 方法必须且只能归属一个已注册的 Cluster；同一个完整方法名不得在其他 Cluster 重复登记。方法详情只在所属 Cluster 的分页 Schema 中提供，并由该 Cluster 的 Schema 版本管理，避免多处描述不一致。应用命名空间仍用于标记方法归属，与方法所属的 Cluster 是不同概念。
- 能力清单中的 `capabilities` 只列当前实例实际启用的语义功能标识，不重复列出 RPC 方法名；`methods` 是可调用方法清单，Cluster/Schema 描述数据模型。客户端应按各组的明确定义判断功能，不从方法名或 Schema 猜测其他能力。
- `capabilities` 的每个列表项是完整 capability ID 字符串，例如 `["com.acme.greenhouse.telemetry"]`；不使用包含 ID 的对象。字符串格式与 `methods` 一致，便于客户端判断能力是否存在，并减小响应体积。能力详情由协议或应用文档说明；以后如需结构化详情，须采用兼容扩展或遵循协议版本演进规则，不得直接将现有字符串项改成对象。
- 能力标识按所有者命名空间区分：组件核心及内置插件使用 `esp_cockpit.*`，应用功能使用根应用描述符声明的命名空间前缀；应用业务错误码范围也归属于该命名空间。应用自行分配能力 ID 后缀，采用全小写、点分层级格式，并在所属命名空间内保持稳定且唯一；能力 ID 不得由 RPC 方法名或 Endpoint/Cluster 数据路径隐式推导。能力表示应用支持的功能，方法表示调用操作，分别命名可避免把功能发现和调用接口耦合。
- 应用 capability ID 由完整应用命名空间、分隔点和至少一个后缀标签组成；后缀各标签沿用命名空间标签规则：仅含小写 ASCII 字母、数字和连字符，不得为空或以连字符开头/结尾。例如 `com.acme.greenhouse.telemetry` 和 `com.acme.greenhouse.sensor.temperature` 合法；单独的 `com.acme.greenhouse`、含下划线的后缀或连续分隔点不合法。统一标签规则便于理解和校验，必需的后缀则区分应用身份与具体能力。
- 能力发现必须在单个有界响应中完整返回，不分页；详细 Cluster Schema 单独按页查询。若完整能力清单无法放入响应上限，服务端必须明确报错，不得分页替代、静默截断或返回部分清单。单次完整读取可让客户端基于同一份清单判断功能和资源限制。
- 客户端必须在每个新认证会话开始时及断线重连后重新读取能力发现；同一会话内可复用已成功读取的清单。读取失败时不得回退到前一会话的缓存。
- 客户端必须校验能力发现响应中自己理解的必需字段及其值：缺少必需字段、类型不符或值不符合契约时，将整次能力发现视为失败，不得使用有效部分继续调用业务方法。例如，缺少 `methods` 或 `capabilities` 为 `null` 均属于失败。通用 WebUI 必须提示错误并允许重试，不回退到旧会话缓存；这样可避免依据不完整清单误判设备能力。必需内容有效时，客户端仍应忽略不认识的新增响应字段，以保留兼容扩展能力。
- 能力发现成功前，客户端不得发起其他业务 RPC。能力发现失败时，WebUI 必须明确显示失败并允许重试；不得根据默认假设或旧能力信息继续调用业务方法，避免误用未启用能力或超出设备资源上限。
- 通用 WebUI 先读取能力发现，再在需要展示某个 Cluster 时按需加载该 Cluster 的 Schema，并在当前会话内缓存；重连或能力发现显示该 Schema 版本变化时，必须使对应缓存失效并重新读取。不要求启动时读取所有 Cluster 的 Schema，以免未使用功能拖慢首屏并浪费请求与内存。
- 只有该 Cluster 的所有 Schema 分页均成功读取，或存在当前会话内仍有效的完整缓存时，WebUI 才可提供其交互。若某页读取失败且无有效完整缓存，须隔离该 Cluster、明确提示失败并允许重试；不得将部分 Schema 渲染成完整界面，其他 Cluster 仍可使用。
- `esp_cockpit.schema.list` 每次只查询一个 Cluster，并在该 Cluster 内按不透明游标分页；其他 Cluster 的 Schema 独立请求、缓存和失败处理，避免单个 Cluster 的数据或错误影响其他功能。
- Schema 查询的 `params` 必须是包含 `clusterId` 和 `limit`，并可选包含 `cursor` 的命名参数对象；首次请求省略 `cursor`，后续请求原样传递服务端返回的游标。`clusterId` 使用能力发现的 `clusters` 条目所公布的 `id`；`limit` 必须为正整数且不超过公布的最大值。未知字段、缺少必需字段或字段类型错误时拒绝请求。客户端不得解析、构造或修改游标。
- Schema 分页成功响应的 JSON-RPC `result` 对象直接包含四个必填字段：`clusterId` 为完整 Cluster 标识字符串，`schemaVersion` 为正整数，`items` 为本页条目数组，`nextCursor` 为不透明游标字符串或 `null`。`clusterId` 必须与请求一致；`nextCursor: null` 表示本 Cluster 的 Schema 已读完。客户端须以响应中的 `nextCursor` 请求后续页，不得自行计算游标。
- `items` 中的条目种类、必需字段和 Schema 约束词汇以[冻结基线第 3 节](./esp-cockpit-interoperability-baseline.md#3-能力发现schema-与通知)为准。首版支持 `attribute`、`command` 和 `method`；事件（Event）的交付语义另待设计，此处不承诺已支持事件条目。
- 客户端遇到不认识的 `kind` 时，不得猜测其语义或静默忽略该条目；通用 WebUI 必须将所属 Cluster 标记为不兼容，隐藏或禁用其交互并说明原因，其他兼容 Cluster 仍可使用。未知条目可能影响操作的含义或安全，隔离受影响的 Cluster 比假定其无关更可靠。
- 每个条目均有必填字符串字段 `id`：`attribute` 和 `command` 使用所属 Cluster 内的局部标识，所属 Cluster 由分页结果的 `clusterId` 指明；`method` 使用完整应用 RPC 方法名，与能力发现 `methods` 中公布的名称一致。统一字段方便客户端识别条目；局部标识避免重复传输属性和命令的完整路径，完整方法名则可直接用于调用。
- 同一 Cluster 内的属性和命令共用局部标识名称空间，不得同名；不同 Cluster 可以使用相同的局部标识。组件在 `start()` 校验时发现同一 Cluster 内有冲突，必须报告错误并拒绝启动，不得接受部分注册。避免跨种类同名可减少阅读 Schema 和日志时的歧义。
- 请求当前能力清单中未公布的 Cluster 时，服务端必须返回稳定 RPC 错误，不得伪装成合法的空 Schema；客户端不得将该错误缓存为空清单。
- 客户端必须将每个 Schema 页的 `schemaVersion` 与当前能力发现中该 Cluster 的版本及本轮其他页面的版本核对。发现不一致时，必须丢弃该轮全部页面、重新读取能力发现，并在该 Cluster 仍被公布时按新的结果从头重试；不得拼接或缓存不匹配的 Schema。若游标绑定的 Schema 版本已失效，服务端返回稳定的游标失效错误；客户端丢弃该轮页面并按上述规则重新开始。每次加载最多自动重试一次：若重试中仍出现版本不一致或游标失效，则丢弃重试页面、停止自动重试并明确提示失败，允许用户手动发起新的加载。其他读取错误仍遵循各自规则，不因此自动重试。重新读取能力发现失败时遵循能力发现失败规则；刷新后对应缓存的失效及其他 Cluster 的处理仍遵循各自的缓存和版本规则。
- Schema 条目按规范化完整路径 ASCII 字典序固定排序，依次比较 Endpoint、Cluster、成员类型和成员标识，不依赖注册先后。游标绑定其 Cluster 和 Schema 修订号；Schema 修订变化后旧游标失效，不得把旧页与新版本页面拼接。注册表在服务启动后保持不变，同一修订中的游标遍历顺序稳定。
- 服务端按游标位置返回后续条目，数量不得超过请求的 `limit`；为遵守响应字节上限，可返回少于 `limit` 的短页，但只要仍有后续条目就必须返回能推进遍历的 `nextCursor`。当无法在响应大小限制内容纳下一条条目时，必须明确报错，不得返回空页面或伪装为遍历完成。空 Schema 可返回 `items: []` 和 `nextCursor: null`。客户端发现非空 `nextCursor` 但页面没有条目时，必须将本轮读取视为失败，避免无进展循环。
- Schema 使用足以支撑通用 WebUI 的机器可读描述，包括数据类型、读写权限、值约束、枚举/单位和可用操作；特殊业务流程可由应用提供专用界面。
- 首版通用 Schema 子集仅支持标量字段：字符串、整数/数值、布尔、枚举、基本范围/长度约束和展示元数据；枚举在线上使用稳定字符串标识，显示名称作为独立的本地化元数据，调整显示顺序不得改变值；普通字符串有全局 UTF-8 字节上限，字段 Schema 可声明更小的上限，字符串长度约束均按 UTF-8 字节数计算，超限必须拒绝且不得截断；整数限定为有符号 `int32_t` 范围，确保浏览器可精确表示并简化跨平台转换；带小数的数值在 C API 中使用 `double`，减少与浏览器数字之间的精度损失，且必须为有限值。不支持数组、嵌套对象、条件规则、引用或组合 Schema。复杂业务表单由应用提供专用界面，避免 MCU 和通用客户端承担完整 JSON Schema 的复杂度。
- Schema 声明的默认值仅作为界面建议，不得自动写入设备；当前值以设备 Read 结果为准。若尚无当前值，WebUI 可以展示建议值，但必须等用户明确保存后才发送 Write，避免页面加载或客户端升级意外改变设备配置。
- Schema 中的读写权限用于 WebUI 呈现和控件启用/禁用，不构成授权边界。服务端必须对每次 Read、Write、Invoke 和订阅请求独立执行授权与校验；客户端隐藏控件或被修改的 Schema 不得绕过服务端检查。
- Schema 仅采用明确限定的 JSON Schema 子集，不要求组件或客户端完整实现 JSON Schema 标准。客户端遇到可能影响数据含义或写入校验的未知规则时，必须隔离该 Cluster 并说明原因，不得静默忽略；只有契约明确标为可忽略的展示元数据才能忽略。限制子集可控制嵌入式校验成本和客户端实现复杂度。
- 每个 Cluster 的 Schema 使用独立的正整数修订号；该值只用于识别客户端可见 Schema 内容是否变化，不表示兼容级别。兼容的新增属性、能力或字段必须保持可选，不得让既有功能转而依赖新增内容。客户端按实际 Schema 内容和自己支持的规则判断能否使用该 Cluster；遇到不理解的类型或影响数据含义的规则时，只隔离该 Cluster，其他兼容 Cluster 仍可使用。

## 6. 资源上限与超限行为

- 所有影响客户端请求和设备资源使用的上限必须有限，并通过能力发现公布实际生效值；具体数值按目标硬件和生产配置实测确定，不在本稿中预设。
- 活动订阅数和待发通知字节数同时受每条 WebSocket 连接的上限及每个 ESP-Cockpit 实例的总上限约束；单个订阅也有独立的待发字节上限。能力发现必须分别公布连接级与实例级的实际容量上限，防止单一连接耗尽实例的全部持续订阅资源。该规则只针对持续订阅资源，不改变 RPC 等待队列不按连接分配配额的既定设计。
- 创建新订阅若会超过连接级或实例级订阅数/待发字节上限，服务端拒绝整个 Subscribe 请求，不创建部分订阅，也不终止或修改现有订阅；拒绝使用明确、稳定的资源上限错误。该规则与已创建的单个订阅后来持续超限时终止该订阅相区分。
- 运行中若实例级待发字节预算无法容纳某条订阅更新，只终止该更新所属的订阅、释放其待发数据，并按既定规则发送 `resource_limit` 通知；不因此关闭该连接或终止其他订阅。
- 资源上限须覆盖 HTTP/WebSocket 连接、请求/响应、字符串和版本 token、Schema 页、多路径、回调队列、订阅及待发通知、Operation、认证验证和注册表容量；完整字段名、单位及限制语义以[冻结互操作基线第 8 节](./esp-cockpit-interoperability-baseline.md#8-limits-字段名及单位)为准，实际值按目标配置测量后公布。
- 请求超过上限或整体资源不足时，使用稳定错误码明确拒绝；不得静默截断、丢弃项目或返回看似成功的部分结果。多路径逐项失败仍按既定规则置于 `result`，与整体资源拒绝区分。
- 应用 RPC 等待队列已满，或请求超过公布的最长排队时间仍未开始时，组件在调用回调前使用同一个稳定组件级 `busy` 错误拒绝请求；到期请求从队列移除。客户端展示设备忙碌提示，不自动重试。该期限不用于强制中断已开始的应用回调。
- 只有认证、请求格式、方法/路径、Schema 参数及组件可完成的授权校验通过后，请求才进入应用回调等待队列；这些校验失败不占用队列。依赖应用运行时状态的业务判断由应用回调处理。
- 入队请求使用组件拥有的参数副本，不引用传输缓冲区；待处理请求的参数总字节数不得超过公布的队列预算。预算不足时与队列已满相同，返回稳定组件级 `busy` 错误；请求完成、取消或过期后释放副本。
- 首版等待队列只执行每实例全局容量限制，不按认证会话或连接分配配额；协议不承诺不同客户端间的排队公平性。

## 7. 版本兼容规则

- JSON-RPC 协议版本、Cluster Schema 版本和公共 C API 主版本职责不同，分别演进。
- JSON-RPC 协议中的向后兼容新增内容递增 `minor`；删除或重命名既有方法、改变既有字段或语义、或其他会使旧客户端无法安全工作的变更递增 `major`。协议版本不设 `patch` 字段；固件发布版本属于运行信息，不混入协议版本。
- 用于并发写入检测的路径值版本与 Cluster Schema 版本及 JSON-RPC 协议版本相互独立；可写路径必须能通过 Read 获取可用于 Write 前置比较的当前值版本，只写属性只返回版本及必要元数据，不返回值。
- 路径值版本仅在当前设备运行期有效；设备重启后所有旧版本失效，客户端重新认证后必须重新获取当前版本再写入，可读属性可同时读取当前值，只写属性不得返回值。设备不持久化版本计数器；版本以不透明字符串传输，客户端不得解析或构造。
- 路径值版本仅在有效状态值实际变化时推进；将同一有效值重复写入不改变版本。Write 表示状态赋值，不应用于承载需要重复执行的业务副作用；此类操作应使用 Invoke。
- Cluster Schema 采用递增修订号，任何客户端可见的 Schema 变更都递增该 Cluster 的版本，不单独定义 Schema 主/次版本。新增属性、能力和字段必须保持可选，不得让既有功能转而依赖新增内容；客户端可忽略不认识的新增字段并继续使用已知功能。若客户端无法理解变更后的 Schema 语义，则只隔离该 Cluster。
- 兼容的新增方法、可选能力和响应字段可增量发布；客户端按能力发现判断实际支持情况，并容忍响应中的未知新增字段。
- 破坏既有协议方法语义时提升 JSON-RPC `major`；破坏公共 C API 源码兼容时提升组件 C API 主版本。
- 设备与客户端的 JSON-RPC 主版本相同时，即使设备次版本更高，客户端也应继续兼容流程：先通过能力发现确认设备实际提供的功能，只调用自己理解的方法和能力，并忽略新增响应字段。不得仅因次版本不同就拒绝连接。
- 客户端发现设备的 JSON-RPC 协议主版本与自身不兼容时，必须明确提示版本不兼容，并禁止发送 Write 或其他会改变设备状态的 RPC。只有在客户端能够确认某只读方法及其响应语义可理解时，才可继续使用该只读能力；不得仅凭方法名称相同就假设兼容。同一主版本内则由能力发现确定实际提供并启用的功能。
- 请求当前能力清单中未公布或服务端不认识的方法时，服务端返回标准 JSON-RPC `Method not found` 错误，不执行请求。客户端可忽略不认识的可选 capability ID，但不得据此推断或调用对应方法；新增但不认识的响应字段按兼容扩展忽略。对协议规定为必需但客户端不理解的字段/语义，客户端不得继续使用受影响功能；未知 Schema kind 或影响数据含义的规则按 Cluster 隔离规则处理。
- Write/Invoke 已开始执行但客户端超时或断线时，结果可能未知；WebUI 提示用户刷新设备实际状态并保留可恢复的用户草稿，不自动重放。只有明确声明可安全重试的 Invoke 才可向用户提供重试选项。
- 客户端无法理解某个 Cluster 的 Schema 内容或语义时，只隐藏或禁用该 Cluster 的交互，并明确说明不兼容原因；其他兼容 Cluster 仍可使用。客户端不得猜测未知 Schema 字段或语义。
- 协议版本字段固定为能力发现 `protocolVersion: {major, minor}`，首版为 `1.0`；版本兼容规则见本节前述规则。

## 8. 实现前冻结门槛与剩余细化

**最小互操作冻结门槛已完成。**核心 RPC/通知字段、错误码、HTTP 映射、认证及管理员初始化、公共 C 注册/回调 API、协议版本与资源上限字段均以[冻结基线](./esp-cockpit-interoperability-baseline.md)为规范来源。组件、WebUI 和示例客户端可并行实现；其他文档中的逻辑分类或临时示例不得覆盖该契约。

实现前仍须补齐各目标生产配置的资源上限数值，并验证 TLS/KDF 参数和目标板性能。有限 Schema 子集的展示元数据及可忽略字段可以按兼容规则逐步细化，但不得改变冻结基线已定义的线协议、错误码、字段名、单位、C API 所有权或回调线程语义。冻结后破坏性变更须遵循协议主版本及 C API 主版本策略。
