# ESP-Cockpit 交互模型与 JSON-RPC 映射

> 文档状态：设计说明（非规范性）。本文解释 Matter-inspired 交互模型的设计理由，不声明 ESP-Cockpit 实现 Matter 协议或具备 Matter 互操作性。线协议和客户端行为以[冻结互操作基线](./esp-cockpit-interoperability-baseline.md)及[JSON-RPC 补充规范](./esp-cockpit-json-rpc-contract.md)为准；文档治理规则见[文档地图](./esp-cockpit-documentation-guide.md)。

## 1. 结论与首版决策

**首版采用受 Matter Interaction Model 启发的四类交互语义作为应用层操作模型，并通过 JSON-RPC 2.0 over HTTP/WebSocket 承载；订阅报告使用 WebSocket 通知。不应把它描述为“JSON-RPC 采用 Matter 协议”，也不应把 Matter IM 直接等同于 JSON-RPC。**

建议将交互抽象为：

- **Read**：读取一个或多个状态/属性。
- **Write**：设置一个或多个状态/属性。
- **Invoke**：执行一个有明确输入和结果的操作/命令。
- **Subscribe**：建立有生命周期的状态订阅，并接收后续报告。

JSON-RPC 负责方法调用、请求/响应关联和通知封装；Endpoint、Cluster、Attribute、Command 等路径作为应用数据模型中的目标标识。首版采用自有字符串标识、受限 Schema 和独立版本规则，不复用 Matter 标识来暗示兼容。

应用命名空间与上述数据路径分工不同：Endpoint/Cluster/Attribute/Command/Event 用于定位设备模型中的目标；应用命名空间用于标记应用 RPC 方法、capability ID 和业务错误码的归属，例如 `com.acme.greenhouse`。它是小写 ASCII 反向域名风格的普通名称前缀，至少包含三个点分标签，每段仅含小写 ASCII 字母、数字和连字符且不得以连字符开头或结尾；不进行 DNS 查询，也不是额外的 Endpoint 或 Cluster 层，不改变数据路径结构。

这是一种**受 Matter 启发的应用交互模型**。除非实现并验证 Matter 所要求的完整数据模型、交互语义、安全、发现、传输和一致性要求，否则不能声称“兼容 Matter”或“Matter 网关”。

传输安全、PKI 生命周期责任链、首次信任建立、管理员初始化、会话保护及本地安全审计的规范性要求见[需求与初步设计第 5.3 节](./esp-cockpit-requirements.md#53-安全性)；网络管理模式与所有权边界见[网络生命周期设计补充](./esp-cockpit-network-lifecycle.md)。

## 2. 分层与寻址建议

目标路径作为参数传递，而不是将每一种属性/命令都编码进 JSON-RPC `method` 名称（线协议中完整 Cluster 标识为 `endpoint/cluster`）：

```json
{
  "jsonrpc": "2.0",
  "id": "31",
  "method": "esp_cockpit.read",
  "params": {
    "items": [
      {
        "clusterId": "device/switch",
        "attributeId": "on_off"
      }
    ]
  }
}
```

首版数据模型概念：

- **Endpoint**：设备中可独立寻址的功能实例，使用设备内稳定唯一的字符串标识。
- **Cluster**：一组相关属性、命令和事件的能力集合，使用稳定字符串标识并独立版本化。
- **Attribute**：可读取/订阅、在授权和策略允许时可写的状态值。
- **Command**：通过 `Invoke` 执行的操作，具有独立参数和结果类型。
- **Path**：完整目标（例如 endpoint + cluster + attribute/command）。所有标识使用小写 ASCII 字母、数字、下划线和连字符；子标识在父对象内唯一。禁止空白、控制字符和 Unicode；长度上限按资源测试确定。

能力发现和 Schema 查询使用 `endpoint/cluster` 字符串标识完整 Cluster，例如 `room1/temperature`。由于子标识不包含 `/`，可以用它区分不同 Endpoint 下的同名 Cluster，而不要求 Cluster 子标识在设备内全局唯一。

同一 Cluster 中的属性与命令共用局部标识名称空间，不能同名；不同 Cluster 可以使用相同名称。启动时发现冲突则报告错误并拒绝启动，避免 Schema 和日志中的名称产生歧义。

不要因 Matter Endpoint 0 的语义或某个既有产品的通道编号，普遍执行 `endpoint = id + 1`。Endpoint 是数据模型标识，不是可安全推导的数组下标；任何旧接口兼容映射都必须是针对明确旧协议的显式适配器，并逐项验证身份、范围和语义。

本组件目前没有已确认的 Shelly 兼容需求。`Switch.Set`、`Cover.Calibrate` 等旧方法别名不应默认加入核心设计。若未来确有兼容目标，可在独立兼容层定义静态映射、冲突策略、版本和测试，不应让核心 IM 模型依赖某厂商旧 API。

## 3. 四类交互与 JSON-RPC 映射

首版采用混合模型：通用路径化交互用于常见状态读写和订阅，少数专用工作流允许显式具名 RPC；两种入口必须共用授权、校验和一致的业务语义。Read、Write、Invoke 可通过 HTTP 或 WebSocket 承载，Subscribe 仅通过 WebSocket 建立及推送。正式方法名/参数以[冻结互操作基线](./esp-cockpit-interoperability-baseline.md)为准；下表中的 `im.*` 仅为逻辑示意，不是线协议名称。

| 交互 | JSON-RPC 请求/响应建议 | 需定义的语义 |
|---|---|---|
| Read | 带 `id` 的 `im.read` 请求（HTTP 或 WebSocket），响应在 `result` 中逐 Path 返回值/状态和可用版本 | 逐路径 best-effort；不承诺多路径原子快照；只写属性经写入授权后仅返回版本和必要元数据，不返回值 |
| Write | 带 `id` 的 `im.write` 请求（HTTP 或 WebSocket），响应在 `result` 中逐 Path 返回结果 | 逐项授权和范围校验，按路径值版本拒绝过期写入，允许部分成功；仅实际状态值变化推进版本，重复设置同值不推进；冲突时保留草稿，可读属性展示当前值，只写属性说明无法展示值，用户明确确认后才重提冲突路径；未包含的 Path 不变，显式 `null` 仅在 Schema 允许时有效；业务副作用用 Invoke/专用 Command，原子事务用专用 Command/RPC |
| Invoke | 带 `id` 的 `im.invoke` 请求（HTTP 或 WebSocket），响应返回命令结果或 Operation ID | Command 以机器可读元数据标注重试安全性；不提供通用去重或“恰好一次”；超时不自动重试，优先查询 Operation/当前状态，仅对明确安全的命令提供重试 |
| Subscribe | 带 `id` 的订阅请求，返回订阅句柄及各路径的初始值/版本；后续报告以无 `id` Notification 推送 | 全部路径成功才创建订阅；连接生命周期、快照重订阅、版本/序号和有界背压 |

### 3.1 Subscribe 生命周期

JSON-RPC 2.0 的请求/响应关联是一问一答；这与长生命周期订阅并不冲突。订阅应拆分为：

1. 客户端以带 `id` 的 JSON-RPC 请求创建订阅。
   - 多路径订阅必须全有或全无；任一路径不可订阅时整体失败，且不保留部分订阅。
   - 只写属性不可订阅；请求包含只写路径时整体报错且不创建订阅，以防止初始快照或通知泄露值。已授权客户端可通过 Read 获取版本元数据。
   - 组件先登记覆盖全部请求路径的有界临时订阅，再读取初始快照；读取期间的变化保留刷新标记。建立失败时撤销临时订阅，能安全发送时返回错误，否则关闭连接，不丢弃其他订阅需要的共享刷新工作。先登记避免读取与开始观察之间出现空档。成功响应因资源不足无法进入有序发送流程时同样撤销临时订阅；能安全发送时返回资源不足错误，否则或达到连接级队列或总资源硬上限时关闭连接。
   - 成功响应进入有序发送流程前，若临时订阅的更新合并后仍无法在限额内安全保留，撤销临时订阅；能安全发送时返回资源不足错误，否则或达到连接级队列或总资源硬上限时关闭连接。此时不发送订阅终止 Notification，不丢弃最后更新后报告成功，也不丢弃其他订阅需要的共享刷新工作。
2. 设备返回一次普通 JSON-RPC 响应，包含订阅 ID、每个订阅路径的当前初始值及对应版本/序号；首版不协商其他订阅参数。该快照按路径标记版本，不承诺多路径间原子一致。响应尚未排入连接发送顺序时保留后续更新，同一路径可合并为最新值；响应被接纳进有序发送流程与临时订阅转为正式订阅作为不可分割的步骤，后续更新及终止通知均排在响应之后，避免客户端先收到无法关联订阅 ID 的通知。接纳不代表客户端已收到；后续发送失败或连接断开时关闭并清理该连接上的所有订阅。
3. 后续状态报告由设备通过不带 `id` 的 JSON-RPC Notification 发送；通知可包含订阅 ID、路径、值、版本/序列号和时间信息，并按对应路径的初始版本/序列号接续更新。若初始快照超出已公布资源上限，必须明确拒绝订阅，不得返回部分快照并表现为成功。
4. 订阅与当前 WebSocket 连接同生命周期；连接关闭、会话过期或权限撤销时终止。首版不提供断线补发/恢复；重连后客户端重新订阅并获取新快照。

HTTP JSON-RPC 仅接受 `POST` 与 `application/json`，用于一次性请求/响应；`GET` 不承载 RPC 且不得修改状态。首版不支持 SSE，状态订阅统一使用 WebSocket。

可订阅属性的值实际变化时，应用在同步保护下更新值和版本，释放保护后尽快主动通知组件相应路径发生变化。通知只携带路径且不在调用中同步执行 Read；组件随后通过实例的单工作线程执行 Read，取得一致的最新值和版本，再按订阅契约推送。这避免同步调用引起死锁，也不必持续轮询应用数据。刷新 Read 失败时终止包含该路径的活动订阅并通知 `read_failed`，避免旧值被误认为持续有效；通知无法送达时关闭对应连接。

客户端应能在断线后重新认证、重新订阅并读取新快照。状态订阅使用有界队列，待发更新按路径合并为最新值并携带版本/序号；单个订阅持续溢出时仅终止该订阅，并通过包含订阅 ID 和稳定机器可读原因的 JSON-RPC Notification 通知客户端；连接级资源达到硬上限时关闭 WebSocket，不无限缓存。客户端应用比当前更新的路径通知，忽略重复或较旧通知；序号跳跃可能来自中间状态合并，不要求单独重读，因为新通知已携带该路径最新值。该机制不保证每次中间状态变化均送达；必须逐条送达的业务事件另行设计。

刷新内部故障期间，能安全响应的 Subscribe 返回 JSON-RPC 组件错误码 `-32010`，否则关闭连接；WebUI 按错误码提示实时更新暂不可用，不将旧数据标记为实时状态，也不无限自动重试。组件重新初始化后用户可重新连接并订阅。错误不包含 `error.data`，不暴露内部堆栈或底层诊断，使客户端能区分临时故障与不支持订阅；消息措辞不作为机器判断依据。

订阅数、每订阅路径数、报告频率、每客户端待发送字节数必须受限。慢客户端应触发路径更新合并；单个订阅持续溢出时终止该订阅，连接级资源溢出时断开连接，而不能阻塞状态生产者和设备控制任务。

**不要把任意 `callback_url` 作为通用 Subscribe 参数。**设备向用户提供的 URL 主动发起 HTTP 请求会引入 SSRF、凭据泄露、网络访问控制、TLS 信任、重试和资源耗尽等额外风险。若产品确有 Webhook 需求，应作为独立功能设计注册/验证、允许目标范围、认证、TLS、限速、重试和禁用策略；不应仅因存在 Subscribe 就自动推导出 Webhook。

### 3.2 路径和方法命名

采用通用 `im.read` / `im.write` / `im.invoke` / `im.subscribe` 方法有利于统一分发及注册扩展，但会使方法本身不再表达具体业务能力。需配套能力发现、Schema、Cluster/Command 注册、访问控制和版本管理。

也可保留业务语义清晰的 RPC 方法（如 `wifi.configure`、`device.reboot`），同时让状态读取/订阅采用统一的数据模型。两种风格可以共存，但应明确边界，避免同一操作既能通过通用 IM 路径又能通过业务 RPC 执行而出现不一致的权限、校验或持久化语义。

不建议默认实现“任何非 `im.*` 方法都查别名表并转换”的双模解析。JSON-RPC 已经有方法路由语义；开放式别名可能导致方法冲突、隐式访问控制差异、兼容负担和调试困难。只有为明确的外部兼容协议提供适配时，才考虑显式、可禁用的别名映射。

## 4. 结果与错误

JSON-RPC 响应必须在 `result` 和 `error` 之间二选一。首版不接受 JSON-RPC Batch 数组，但单条 Read/Write RPC 可包含多个 Path；对这类多路径操作，错误分层如下：

- **整体请求错误**：请求封装、未知方法、参数结构或 RPC 层授权/资源拒绝导致请求无法执行时，使用顶层 JSON-RPC `error`。HTTP 请求进入 RPC 处理后，即使返回 JSON-RPC `error` 也使用 HTTP 200；认证和 HTTP 接入等 RPC 前失败由 HTTP 状态码表达。
- **逐路径结果**：多路径 Read/Write 的单项失败放在 `result` 的逐项状态中，允许部分成功。这样客户端可区分“请求整体无法执行”和“部分路径处理失败”。
- JSON-RPC 标准协议错误使用 JSON-RPC 2.0 标准错误码；组件自定义错误码及各码语义、HTTP 接入失败映射均以[冻结互操作基线](./esp-cockpit-interoperability-baseline.md)为准。应用业务错误码使用各应用根命名空间声明的、互不重叠的正整数范围 `1..INT32_MAX`。未知错误码按通用失败处理。错误码保持稳定，用户可见消息不得泄露堆栈、凭据或内部状态。

例如，单条多路径 Write 可以返回：

```json
{
  "jsonrpc": "2.0",
  "id": "32",
  "result": {
    "items": [
      {
        "path": {
          "clusterId": "device/switch",
          "attributeId": "on_off"
        },
        "status": "ok",
        "version": "12"
      },
      {
        "path": {
          "clusterId": "device/level",
          "attributeId": "current_level"
        },
        "status": "error",
        "error": {
          "code": 1001,
          "message": "Target level out of allowed range"
        }
      }
    ]
  }
}
```

多路径 Write 逐项授权和校验，允许部分成功，不承诺跨路径事务原子性；需全有或全无语义的业务操作由专用 Command/RPC 实现。单路径业务拒绝及交互状态码的具体枚举仍在 API 设计阶段定义。

多路径操作仍须明确：

- 多路径上限、响应大小和执行超时上限。
- 应用回调失败时，如何准确报告已执行与未执行项。
- 错误码与消息的向后兼容策略。

JSON-RPC `id` 只用于请求/响应关联，不作为幂等键。首版不提供通用去重缓存或“恰好一次”保证；每个 Command 必须声明是否可安全重试，客户端不得盲目重放非幂等操作。

应用 Read/Write/Invoke 回调经有界队列投递到单一执行上下文串行运行；回调须短时、非阻塞，长操作异步化。队列满时明确返回忙碌/资源不足。长操作可创建设备级 Operation，返回 ID、状态和可选进度；首版状态固定为 queued、running、succeeded、failed，不提供通用取消语义，需要取消的操作由该操作单独定义取消接口。任一有效管理员会话可查询，登出/断线不自动取消；Operation 仅驻留 RAM，重启后旧 ID 变为未知，客户端须重新读取设备实际状态。活动任务与历史记录均有界；达到活动任务上限时拒绝新任务，终态记录可淘汰，不丢弃活动任务。具体容量由目标板资源测试确定。

## 5. 属性写入与命令调用边界

`Write` 与 `Invoke` 应按**目标数据模型的语义**区分，而不应通过任意字段存在与否隐式改写操作类型：

- 写入期望的持久状态（例如设定开关目标值）通常建模为属性写入。
- 执行一次性动作、触发带参流程或启动定时行为通常建模为命令调用。
- 若设备 API 把属性设置和瞬态参数放在同一请求（例如设置开关同时要求定时关闭），应定义明确的业务命令/组合操作，或定义经过 Schema 描述的显式映射；不得静默地把 `Write` 改成另一个命令。
- 具体是否映射到 Matter On/Off Cluster 的标准命令（例如某个 timed-on 命令），需核对 Matter 版本、方向、约束和具体命令语义。JSON-RPC 参数名 `toggle_after` 本身不足以证明等价映射。

这可避免“相同请求因可选字段而突然变成不同权限、不同副作用或不同幂等性”的隐式行为。

## 6. Matter 兼容性及编码边界

- 四类交互借鉴 Matter IM 不能单独带来 Matter 互操作性；Matter 还定义/依赖数据模型、访问控制、安全会话、错误状态、订阅行为、发现、传输与一致性要求。
- Matter 原生消息编码使用 **Matter TLV**，不能将 Matter 编码概括为 CBOR。ESP-Cockpit 当前选择的 JSON-RPC over WebSocket 是独立的 JSON 表达和传输设计。
- 若未来需要对接 Matter Fabric/设备，建议通过独立 Matter 适配层把 Matter 操作映射到应用能力，不要把 Matter 协议栈和安全模型塞入通用 JSON-RPC 核心。
- 首版使用自有字符串标识，不复用 Matter 数字 ID/名称来暗示兼容；未来若增加 Matter 适配器，须逐项核对许可、版本和语义，不得只借用标识就宣称兼容。

## 7. 首版决策摘要

首版采用**Matter-inspired、非 Matter 兼容**的数据交互抽象：

1. 保持 JSON-RPC 2.0 作为消息协议，Read/Write/Invoke 可通过 HTTP 或 WebSocket 承载；Subscribe 默认使用 WebSocket。
2. 通用路径化 Read/Write/Invoke/Subscribe 与少量具名 RPC 并存；两类入口共用授权、校验和一致的业务语义。
3. 订阅只绑定当前 WebSocket 连接；断线后重订阅获取新快照，通知使用有界队列并按路径合并为最新状态。
4. 不支持 JSON-RPC Batch 数组、SSE、通用幂等键或“恰好一次”；HTTP 仅接受 `POST` + `application/json`，GET 不承载 RPC 或状态变更。
5. 多路径 Read best-effort；多路径 Write 逐项授权/校验、允许部分成功，事务由专用 Command/RPC 实现。整体请求错误使用顶层 `error`，逐项失败使用 `result` 状态。
6. 不自动支持 Webhook callback URL；如有需求另行做安全设计。
7. 核心数据模型使用组件自有字符串标识与 Schema；只有未来确有需求时才评估独立 Matter 互通适配器。

## 8. 后续实现细化

### 交互模型与 RPC 边界

- 首版 JSON-RPC 方法名、参数/结果字段、稳定错误码和 HTTP 状态码映射已由[冻结互操作基线](./esp-cockpit-interoperability-baseline.md)确定；各目标配置的资源数值仍需目标板实测。

### 数据模型与访问控制

- 受限 Schema 的完整展示元数据词汇及可忽略展示字段仍可兼容细化；游标失效码、分页结构、资源字段和版本协商已按冻结基线确定。
- 各属性/命令逐项的读写权限、值约束及业务级授权。

### 订阅与长时操作语义

- 目标配置的订阅队列/慢客户端和 Operation 容量数值仍需实测；通知序号、Operation 状态字段和资源超限错误语义已由冻结基线确定。活动项不驱逐，容量压力下优先回收最旧终态，无法回收时拒绝新 Operation。

### Matter 兼容与外部回调

- 未来是否存在真正 Matter 互操作需求，以及是否为此增加独立适配器。
- Webhook 是否为产品需求；如是，独立定义安全和运维策略。
